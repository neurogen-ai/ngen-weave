# Step 9 — run lifecycle over the backend

PRD reference: "Execution" (canonical backend), "Human review over the network", v0.1 CLI semantics retained.

## Goals

- `loom run/resume/status` operate against langgraph-server as the canonical backend. Human review works both remotely (JSON over interrupt/resume endpoints) and locally (file artifact), with identical payloads.

## Detailed steps

1. Backend client (`packages/core/src/backend.ts`): thin HTTP client for the configured langgraph-server endpoint (`LOOM_SERVER_URL`, default `http://localhost:8123`). Methods: create run, resume run (with payload), get status, get final output. Maps transport errors to `InfraError`.
2. Local default: if no server is reachable, `loom run` starts one as a child process against the generated `langgraph/` config, waits for readiness, proceeds, and leaves it running (print the PID; `loom status --server` reports health). Keep this under ~60 lines; it is a convenience, not a supervisor.
3. `loom run <workflow-dir> [-i input.json]`: validate, resolve workflow name, dispatch to backend, print run id and poll until terminal state or interrupt. On interrupt of a human node, write BOTH artifacts:
   - `.loom/runs/<id>/reviews/<node>.yaml` — local file form, exactly as v0.1
   - keep the interrupt pending on the server (do not auto-resume)
4. `loom resume <run-id> [--review <file>] [--json '<payload>']`: submit the review payload through the server's resume endpoint. Payload is validated against the step 2 `reviewArtifact` schema before submission so both forms carry identical data.
5. File-based local path preserved: completing `<node>.reviewed.yaml` then running `loom resume <id>` reads the file, converts to the same JSON payload, submits. One code path after conversion.
6. `loom status <run-id>`: fetch state from backend, merge with local events.jsonl via `EventReader`, print node statuses and last events.
7. `max_steps` budget bounds call duration on the backend side (already enforced in generated code); the client additionally applies an HTTP timeout derived from budget × average-step-estimate — actually simpler: no client timeout beyond the server's own; document that budget enforcement is authoritative in the graph.

## Success criteria

- Full lifecycle works against a real local langgraph-server: run → human interrupt → resume with approve → completion, and the reject path routes to revision.
- The YAML file form and the `--json` form produce byte-identical payloads on the wire (test asserts this).

## Tests

- Client unit tests against a stub HTTP server (create/resume/status/error mapping).
- E2E test (spawns real server, marked slow/skippable via env): full approve and reject lifecycles.
- Equivalence test: yaml-file resume vs json resume produce identical request bodies.
