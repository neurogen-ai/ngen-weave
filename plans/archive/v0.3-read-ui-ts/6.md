# Step 6 — workflow list view

PRD reference: "Scope" item 1, "Invalid workflows", "Data freshness".

## Goals

- `/` lists every workflow in the project as a card: name, description, validity badge. Invalid cards show an errors affordance one click away. Client polls every 3 seconds and skips refetch/re-render when hashes are unchanged.

## Detailed steps

1. Polling store (`apps/web/src/lib/poll.ts`): a Svelte store wired by a `setInterval` (3000ms) that calls `listWorkflows()`, compares the array of `{ name, hash }` against current state, and updates only on change. Cleanup on component destroy. Single instance at the list route.
2. List route `/`: grid of cards. Card contents:
   - workflow name (heading), graph-level description or placeholder text when absent
   - validity badge: "valid" (success color) / "invalid" (danger color)
   - invalid card gains an "N validation errors" button opening a dialog listing every error string verbatim from the API. No reformatting, no truncation of individual messages.
   - card links to `/<name>` (the canvas route, step 7). Invalid cards link too, but the target shows the error dialog state rather than a graph.
3. Loading and error states: initial skeleton cards while first fetch resolves; a dismissible banner if polling fails repeatedly (server down) — the app keeps retrying, no dead-end screen.
4. Success criteria check (PRD #1, #3): all workflows visible with zero clicks after load; any validation error reachable in one click from the list.

## Tests

- Store test: fake API returning same hashes twice → fetch called twice, subscribers notified once; changed hash → update propagates.
- Component tests (vitest + svelte testing library): valid card renders name/description/badge; invalid card renders error button; clicking it shows all error strings.
- Poll interval teardown: no leaked timers after unmount.

## Out of scope (tempting, do not build)

- Run-status columns or anything run-related. Runs do not exist for v0.3 (PRD reserves them as a future seam).
- Sorting/filtering the list. One list, alphabetical default is fine; PRD's sorting rules concern node sidebars (step 8).
- Search across workflows. The PRD's search is within-graph node search.
- Optimistic transitions, view-state persistence in URL beyond what step 7 needs.
- Manual refresh button alongside polling — harmless, but not asked for; skip unless trivially free during review.
