# Step 10 — `loom ui` command + release gate

PRD reference: "Serving", "Success criteria", "Non-goals".

## Goals

- `loom ui [dir]` starts one process serving the static web app and the web API. Then verify every PRD success criterion and close the release.

## Detailed steps

1. Static build: `apps/web` builds to `apps/web/build` via adapter-static (step 5). The CLI serves that directory's files with a static-file handler plus SPA fallback to `index.html` for non-`/api` paths.
2. Build strategy: the monorepo root gains a script building the app once (`pnpm build` at root). `loom ui` requires the built assets; if missing, error with "run the workspace build first" rather than invoking the toolchain implicitly (users without Node dev setup is a v1.0 concern, not now).
3. Command wiring in `packages/cli`: 
   ```
   loom ui [dir] [--port 4173]
   ```
   - default dir = cwd; project root resolution identical to the MCP server (manifest, else scan)
   - mounts the Hono app from `packages/web-api` under `/api`, static serving elsewhere
   - binds `127.0.0.1` only — localhost tool, PRD explicit
   - prints the URL and the number of workflows discovered; Ctrl-C exits cleanly
4. Integration tests (vitest, supertest-style against the composed handler):
   - `GET /` serves index.html; deep link like `/draft-review?node=draft` serves index.html too
   - `/api/workflows` works through the same port/process
   - server refuses non-loopback bind if an option is passed (test the guard, not actual external binding)
5. Release checklist — verify each PRD success criterion and record evidence in the commit message:
   1. All workflows visible within two clicks of opening the app (list → card → canvas = two).
   2. A ≤15-node workflow fully legible without scrolling at 1440×900 after fit-view. Test manually with the largest example; adjust layout rank separation if it fails.
   3. Any validation error findable from the list view (break an example fixture temporarily, confirm the error dialog shows it, restore).
   4. **Zero write capability**: grep `packages/web-api` and `apps/web` for `fs.write|appendFile|writeFile|POST|PUT|PATCH|DELETE` — no hits outside tests asserting their absence. Also confirm no route mutates disk by running the full API test suite against a fixture tree and asserting its hashes are unchanged afterward.
6. Update root README: the `loom ui` section, screenshot optional, the read-only statement, and "runs/auth/deployment come later" pointer to plans/v1.0.

## Tests

Summarized above per item; additionally:
- Full suite green across all packages.
- The hash-immutability assertion in item 5.4 runs as part of CI so write-capability creep is caught automatically going forward.

## Out of scope (tempting, do not build)

- Auth, tokens, HTTPS, non-loopback binds. Localhost only, PRD explicit.
- Docker/deployment story. Waits until runs and auth exist.
- Hot-reload of the UI or API during development beyond what vite/HMR already gives in dev mode.
- Electron/desktop packaging (v1.0 territory).
- Serving run data "read-only anyway" — invisible to v0.3, full stop.
