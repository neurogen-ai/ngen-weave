# Step 4 — detail + schema endpoints (lossless read API)

PRD reference: "Read API contract", property 1: lossless round-trip.

## Goals

- `GET /api/workflows/:name` — the full parsed structure plus every raw source file, so a future editor could reconstruct the workflow directory byte-faithfully.
- `GET /api/workflows/:name/schemas/:file` — resolved JSON Schema documents.

These two endpoints are the seam future write capability inverts. Their completeness is contractual; treat any un-representable construct as a bug fixed now.

## Detailed steps

1. Extend `packages/core/src/api-types.ts`:

   ```ts
   export interface WorkflowDetail {
     name: string;
     description: string | null;
     hash: string;
     graph: ParsedGraph;          // core's validated graph structure, verbatim
     files: Record<string, string>; // relPath -> base64 raw bytes
   }
   ```

   `ParsedGraph` is whatever core's loader already returns for a validated workflow: graph config, nodes with all frontmatter fields (including `description`, model, variant, observers), edges including control pass/fail and human routes, fan-in `inputs` maps, schema file references. Do not reshape or summarize it — verbatim pass-through is the point.

2. Route `GET /api/workflows/:name`: discover (step 2), match by name. Invalid → 200 with `{ valid: false, errors }` (a minimal body; the list view links here). Valid → full `WorkflowDetail`. Unknown name → 404.
3. `files` map: walk the workflow dir recursively, base64-encode each file. This is what makes round-trip lossless: prompt bodies, frontmatter comments, formatting quirks all survive.
4. Route `GET /api/workflows/:name/schemas/:file`: serve the parsed/resolved JSON Schema for a referenced schema file (`file` is the path as referenced from graph.yaml or node frontmatter, e.g. `schemas/input.json`). Resolve through core's existing schema-resolution logic so `$ref`s are already handled the way validation handles them. Unknown file → 404. Response type:
   ```ts
   export interface SchemaResponse { file: string; schema: object; hash: string; }
   ```
5. Round-trip proof test (the step's centerpiece): reconstruct the workflow directory from a fetched `WorkflowDetail` — decode each `files` entry to `<tmp>/<relPath>` — then byte-compare against the original directory. Every file identical. Run this over every example workflow. If any construct fails this test, fix the API, not the test.

## Tests

- Detail returns all nodes with every frontmatter field present, edges with pass/fail targets, fan-in maps, human routes.
- Byte-faithful reconstruction test above passes for all examples.
- Schema endpoint returns parseable JSON Schema matching what's on disk (compare deep-equal to the file's parsed JSON).
- 404s for unknown workflow, unknown schema file.
- Invalid workflow: detail returns the errors body; schema endpoint 404s (nothing served for unvalidated structures).
- 405 coverage extends to new routes automatically (loop from step 3).

## Out of scope (tempting, do not build)

- Any write endpoint, even behind a flag. The contract is designed for inversion later; inversion is not built now.
- Diff/patch endpoints, file-level granularity beyond the whole-dir `files` map.
- Serving arbitrary files outside the workflow dir (path traversal guard exists implicitly by walking the dir yourself — keep it that way; do not accept absolute paths).
- Stripping or normalizing fields from `graph` "for the UI". Verbatim means verbatim.
- GraphQL or query parameters to select substructures. Three endpoints, whole payloads; payloads are small.
