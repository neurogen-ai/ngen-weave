# Step 5 — sequential engine core

PRD reference: "Execution semantics", "File-based state" in Goals.

## Goals

- A thin, single-threaded executor that walks the graph one node at a time, persists `state.json` after every transition, and can resume from it. Worker/control/human bodies are stubbed behind a narrow node-executor interface; steps 7–9 fill them in.
- The error taxonomy (data vs infra) and retry policy live here.

## Detailed steps

1. `src/engine/types.ts` — the narrow engine interface:

   ```ts
   interface NodeExecutor {
     execute(node: ResolvedNode, input: unknown, ctx: RunContext): Promise<ExecResult>;
   }
   interface ExecResult {
     output: unknown;              // validated value
     next: { kind: "edge" } | { kind: "passfail", pass: boolean }
         | { kind: "route", target: string } | { kind: "wait" } | { kind: "stop" };
     observerEvents: ObserverEvent[];
     metadata: ObserverMetadata;   // six PRD fields
   }
   ```

   The engine holds a map of node type → NodeExecutor. Steps 7–9 register implementations. For this step ship a `StubExecutor` returning `{ output: input, next: {kind:"edge"} }` so the walk is testable end to end.

2. `src/engine/run.ts`:
   - `RunContext`: workflow, run dir, state read/write helpers, logger.
   - `startRun(workflow, input, runsRoot)`: validate input against workflow input schema (Ajv), create `.loom/runs/<run-id>/`, write initial `state.json`.
   - `stepRun(ctx)`: load state, find current node, call its executor, apply result:
     - `edge` → set outputs, move to sole child (declaration order for fan-out).
     - `passfail` → follow pass/fail edge targets.
     - `route` → jump to named target.
     - `wait` → status becomes `waiting_human` or `paused`; run halts.
     - `stop` → status `stopped`.
   - After every transition write `state.json` atomically (write temp file + rename).
   - Increment `steps_used`; if it reaches `max_steps`, fail the run with a clear budget-exhausted report.
   - Fan-in assembly: when entering a multi-parent node with an inputs map, assemble input as `{ mappedFieldName: parentOutputs[parentName] }`. Single parent without map → parent output passes through.
3. Retry policy: wrap executor calls in a helper that retries on `InfraError` only, per workflow `retries` (attempts, exponential backoff from `backoff_ms`). On exhaustion rethrow; run fails. `DataError` propagates immediately, no retry. Any thrown non-Loom error is treated as InfraError.
4. `resumeRun(runId, runsRoot)`: reload state.json + workflow (re-validate hash matches; mismatch = `ConfigError` telling the user the workflow changed), continue stepping until halt condition or done.
5. Run id: short uuid (`crypto.randomUUID().slice(0,8)`), overridable via option for tests.

## Success criteria

- With StubExecutors everywhere, a linear graph runs start to done, state.json updates each step, resume after simulated crash mid-run completes the graph.
- Data errors abort without retries; infra errors retry the configured number of times with backoff.

## Tests

- Linear two-node graph reaches `done`; final outputs present in state.json.
- max_steps budget: a two-node cycle with max_steps 10 fails at 10 with a budget message.
- Fan-out: both children ran in declaration order, each got the parent's full output.
- Fan-in: assembled object maps parents to fields correctly.
- InfraError retried twice then succeeds when attempts=3 (use fake timers for backoff); DataError never retried.
- Crash simulation: stop after first step (throw once from executor), resume, run finishes; state file valid JSON throughout.
- Workflow hash mismatch on resume throws ConfigError.
