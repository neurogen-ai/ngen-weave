# Step 3 — expression evaluator

PRD reference: "Expression evaluator (shared)" section.

## Goals

- One sandboxed JS expression evaluator, used by observer triggers (step 10) and human routes (step 9). Compile once at validation time, evaluate many times at runtime.

## Detailed steps

1. `src/engine/expr.ts` exporting exactly two functions:
   - `compile(expr: string): CompiledExpr` — throws `ConfigError` on syntax errors.
   - `evaluate(compiled: CompiledExpr, bindings: Record<string, unknown>): boolean`.
2. Sandbox rules:
   - No `new Function`, no `eval` with scope access to module state. Preferred implementation: `new Function("bindings", "with (bindings) { return (<expr>); }")` is acceptable only if identifiers are pre-validated; the simpler safe route is to parse with a tiny hand-written or dependency-based expression parser supporting: identifiers, string/number/boolean literals, `&& || ! == != < > <= >= + - * /`, parentheses, member access on plain objects via dot notation, and array/string `.includes`. If you use a library, it must be small and dependency-free in spirit (e.g. `jexl`-style); otherwise write the parser. Do not pull in heavyweight runtimes.
   - Reject at compile time: function calls (except the whitelisted method above), property assignment, `=>`, template literals, any identifier not present in the bindings prototype passed at compile time.
3. Identifier checking: `compile` takes no bindings; instead expose `validateIdentifiers(compiled, allowed: string[]): void` used by the validator (step 4) so unknown identifiers fail statically.
4. Comparison semantics: strict equality for `==`/`!=` (treat as `===`/`!==`). Numbers compare numerically. Undefined identifier comparisons throw `DataError` at runtime (a trigger evaluating over missing metadata is a data problem).
5. Tests cover both consumers' use cases from the PRD: `"cost_usd > max_cost"`, `"tokens_in_context > max_tokens"`, `"decision == 'approve'"`.

## Success criteria

- Compiling and evaluating works for every expression appearing in the PRD.
- Non-compiling expressions throw `ConfigError`; runtime violations throw `DataError`.
- No I/O, imports, globals, or function definitions possible inside an expression (proven by tests).

## Tests

- Each PRD example evaluates correctly with sample bindings including params (`max_cost` bound alongside metadata).
- `process.exit(1)`, `require('fs')`, `(() => {})()` all rejected at compile time.
- Unknown identifier (`foo > 1`) passes compile but fails `validateIdentifiers` when `foo` not allowed; at runtime it throws `DataError`.
- Operator precedence sanity: `1 + 2 * 3 === 7`.

## Commits

- `feat(engine): sandboxed expression compiler and evaluator`

## Out of scope
- Template interpolation (`{{ }}`) inside expressions — forbidden by PRD
- Async evaluation, SQL syntax, regex literals, string methods beyond `.includes`
- Wiring observers or routes to it (steps 9–10)
