# ngen-weave v0.2 release requirements

Status: draft
Prerequisite: plans/releases/v0.1.md complete (Workflow classes on LangGraph, registration/config layer, checkpointing, provenance records, CLI, canonical examples).

## What v0.2 adds

v0.1 made ngen-weave runnable. v0.2 makes it reachable, observable, and supervisable: workflows exposed as MCP tools, runs managed over a long-lived process, events as a queryable stream, human review working when the reviewer is not sitting at the filesystem, and supervision (observers) living in the scheduler itself. The agent-node seam from v0.1 gets its first real exercise, still mocked.

No new node vocabulary. No UI. Everything here is backend and protocol.

## Supervision: observers in the scheduler

All author-facing supervision moves here from the earlier v0.1 plan, and changes shape: observers are baked into the scheduler rather than existing as a parallel graph-level facility. Every activation boundary is already a point where the scheduler holds the six-field metadata object (iterations, tokens_in_context, tokens_total, cost_usd, elapsed_ms, last_output_valid) that v0.1 writes into provenance; supervision evaluates predicates against exactly that object at exactly those boundaries. No new evaluation sites, no second mechanism.

The exact mechanism is settled while designing this version's scheduling work, not before; what is fixed now:

- Predicates are structured builders (`gt`, `lt`, `and_`, `or_`, ...), never bare lambdas or expression strings. Each node renders its own description, so the descriptor shown in the UI and written to provenance is mechanically generated from the evaluated object and cannot drift from it.
- Actions start at pause only: a firing suspends the run through the same mechanics as budget breach and human interrupts, resumable via `ngw resume`. Stop may follow when a run needs it. Reroute is deferred to post-1.0; it alone requires runtime graph rewiring and everything else shares plumbing that exists regardless.
- Budget enforcement (below) is the first consumer of this machinery and its reference implementation; an author-declared cost predicate is the same check with configurable thresholds.

## Serving: decide, don't assume

v0.1 runs graphs in-process. v0.2 needs a long-lived process for run management and MCP dispatch. Two candidate paths:

1. **langgraph-server** (self-hosted): gives durable serving, interrupt/resume endpoints, and a run API for free. Cost: another moving part, ngen-weave semantics living partly behind someone else's API.
2. **Own FastAPI service**: full control, more to build and maintain.

Both paths get built in this version. langgraph-server runs as a fully separate deployment reachable only through the protocol; alongside it we ship a basic FastAPI implementation of the same interface, minimal but real (in-process engine, SQLite checkpointer, HTTP endpoints). Owning the service is required by 1.0, so this early start makes the eventual switch a config change. Evidence recorded either way decides which is default through v0.x. The seam both implement:

```python
class RunService(Protocol):
    async def launch(self, workflow, input) -> RunHandle
    async def resume(self, run_id, payload) -> RunHandle
    async def status(self, run_id) -> RunStatus
    async def cancel(self, run_id) -> None
    async def list_runs(self, filters) -> list[RunSummary]     # threads
```

Everything in this PRD talks to `RunService`, never to LangGraph directly.

## Run state file

One JSON file per run at `.ngen-weave/runs/<run-id>/run.json`, per the v0.1 format: metadata plus the full event/provenance stream in a versioned envelope. Node transitions, supervision firings, retries, interrupts, model-call usage, artifact writes all land there, written atomically at each transition so the file is always valid and always sufficient to re-run. Nothing emits events outside this stream, so any future UI has exactly one thing to read.

## Human review over the network

The local YAML review artifact stays the default path. Added: a canonical JSON form of the identical payload, submitted through whatever interrupt/resume endpoint the chosen `RunService` exposes. Both forms carry the same fields, so any future UI submits either without translation.

## Workflow-as-tool: MCP server

ngen-weave ships an MCP server exposing workflows as tools. Any MCP client can call them (pi, opencode, Codex, anything speaking MCP); no client is special.

- Manifest: project-root `ngen-weave.json` listing workflow modules/paths.
- One tool per workflow. Tool name is the workflow name; description comes from the workflow's `description` attribute (now required for MCP exposure), because agents choose tools by description. Input schema is the workflow's top-level input JSON Schema; result content is the validated output object.
- Static validation runs at server startup. A broken workflow fails loudly there.
- Transport: stdio for local clients, HTTP for remote.
- Execution blocks from the caller's view with an explicit caller-supplied timeout (no heuristic derived from step budgets). This is deliberately the machine-speed calling path: workflows that run without human pauses return their validated output directly, and a run that reaches a human pause or budget pause returns promptly with the run id and waiting node so the caller can resume later through the runs API. Intermediate node traffic never crosses the boundary.

## Run management and threads

`RunService.list_runs` plus a small Python API (and thin CLI surface: `ngen-weave runs`, `ngen-weave cancel`) giving:

- Launch a workflow, get a run handle.
- List runs with status, workflow name, started-at, cost-so-far, waiting-on-human flags.
- Cancel, pause/resume, attach notes.

This is deliberately an API, not yet a UI. v0.4's management screens sit on exactly these calls.

Budget caps move from concept to enforcement here: a run-level budget (cost_usd, steps) checked by the engine between transitions against running totals kept in the run file's metadata (updated at each transition, never recomputed by rescanning records); breach pauses the run with a budget_exhausted event rather than killing it silently.

## AgentNode: mock becomes stub-real

The v0.1 mocked AgentNode executor gets replaced by a harness that can drive a *real* model through the CompletionProvider with a tool registry, while permissions are enforced by the engine wrapper (deny-listed calls raise, budgets checked per call, forced return-to-review points honored). What stays out of scope: exposing ngen-weave itself as the agent's tool source via MCP loopback, and any claim of good agentic behavior. The point is proving that PermissionSet, budgets, and provenance constrain a real model loop, not that the loop is smart.

## Non-goals for v0.2

- Web UI of any kind.
- Parallel execution within a workflow.
- Plugins or third-party node registration.
- Artifact diffing, display, export formats.
- Collaboration, notifications.
- ngen-weave-owned REST API beyond what the chosen serving path provides.

## Success criteria

1. A workflow called through MCP from an external client (pi) runs to completion or human pause, with correct blocking semantics.
2. Remote JSON review submission resumes a paused run identically to the local file path (same e2e test, both transports).
3. `run.json` replays a completed run faithfully: every transition, supervision firing, and usage record present exactly once, ordered.
4. An AgentNode with a deny-listed tool attempts the denied call mid-run; the engine blocks it, records it, and routes per its configured policy.
5. A run exceeding its cost budget pauses instead of dying; resuming after raising the cap completes it.
6. The identical test suite passes against both RunService implementations (langgraph-server-backed and FastAPI-owned), proving the seam.
