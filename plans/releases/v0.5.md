# ngen-weave v0.5 release requirements

Status: draft
Prerequisite: plans/releases/v0.4.md complete (editor, storage format, run management, artifact versioning, provenance export).

## What v0.5 adds

Extensibility, and nothing else. Plugins that define node types, services, workflow packs, namespaced API routes, and declarative UI widgets; built-ins refactored onto the same registration surface plugins use; notification providers as the first reference plugins; and real agentic autonomy with human-drawn boundaries, exercising both the tool surface and the permission gate. Collaboration (roles, multi-reviewer, tickets) waits for v0.8, where auth gives roles principals to attach to.

## Plugin system

A plugin is a Python package registered through entry points (`ngen-weave.plugins`). One plugin, any combination of parts; a backend-only or frontend-only plugin is just a plugin with the other sections empty:

1. **Node types**: subclasses of `Node` (or of Worker/Control/Human/Agent) plus UI metadata: how the editor renders its fields, which icon/badge it gets, plain-language summary template. Unknown-to-core types already render generically (v0.3 seam); plugins make them first-class.
2. **Services**: implementations of ngen-weave interfaces — CompletionProvider, artifact stores, diff renderers for specific file types.
3. **Workflow packs**: prebuilt workflows installable into a project.
4. **API routes**: HTTP handlers the server mounts under `/api/plugins/<plugin-id>/...`. Namespaced by construction, so route collisions are impossible; routes inherit the server's auth middleware like every core route — plugin endpoints are never a side door around it.
5. **UI widgets**: declarative element specs rendered by a generic host component in ngen-weave-web (see "Plugin UI" below).

Rules:

- Plugins are sandboxed by convention, not by interpreter tricks: they get the same capability interfaces core uses, nothing else. Capability grants are explicit in project config.
- Every built-in node type ships as a reference plugin layout so the plugin API is exercised by ngen-weave's own code, keeping it honest.
- Plugin node outputs still cross schema validation like everything else; provenance records mark their records with the providing plugin id.
- Element specs and API declarations are validated when a plugin is enabled: spec trees schema-checked, referenced routes must exist in the same plugin's API declaration, Tailwind class strings present verbatim (see design/plugins-and-ui.md). Most render-time surprises become load-time ones. Each mounted widget gets its own error boundary so one bad plugin cannot take down the canvas around it.
- A badly behaved plugin is handled operationally, not by policing its declarations: `ngw plugins disable` / `ngw plugins remove`, fast and boring. CSS classes are not policed for the same reason arbitrary Python is not: plugins already run code server-side under "sandboxed by convention", so scanning class strings for `fixed inset-0` would be inconsistent theater. Widgets render inside a constrained container (clipped, z-index bounded) as hygiene, not security.
- The registry is static at process start. Installing a plugin means installing a package and enabling it in config; no hot-reload in v0.5.

## Plugin UI

One widget mechanism for everything, core included. A widget is data: an HTML element tree with complete literal Tailwind class strings plus declared data bindings to HTTP endpoints (the plugin's own namespaced routes). The web app ships one generic renderer that knows the spec format and nothing about any plugin; core's own field renderers are expressed as the same spec format consumed by the same host, keeping the API honest the way reference plugins keep the plugin API honest.

Rules and constraints:

- Class strings are complete literals living verbatim in the spec files, data-only like workflow config. This is not a special burden on plugins; it is Tailwind's own contract (the compiler greps source for exact strings), which core's UI already follows. State variation uses full literal alternatives in lookup maps, never string concatenation. Validation rejects specs where expected strings cannot be found statically.
- Styling is applied by utility strings, so no stylesheet ships per widget and no scoped-CSS machinery applies to rendered elements (Svelte scoping needs compile-time components; spec markup has none). SvelteKit scoping still covers core's hand-written components as usual.
- Data bindings poll only (`poll_ms` per binding); the product targets locally hosted deployment where polling at zero latency and zero cost is fine. No streaming bindings in v0.5.
- The binding/action vocabulary stays deliberately tiny: fetch-and-update, nothing else. Conditionals, loops, transforms, and client-side state wait for post-1.0; growing a JSON programming language is the failure mode to avoid.
- The interactivity escape hatch arrives early rather than late: a plugin may ship prebuilt frontend component bundles compiled at authoring time against the published SDK (`ngw plugin build`), loaded generically by the web app into declared mount slots. Pip distributes one artifact; the host never rebuilds and never sees source. Host-build compilation of plugin source is rejected outright — it would make every plugin install a frontend build event, break prebuilt web-app distribution, and fork the author story. Mount points are named and stable now because they are the seams these bundles plug into.
- Tailwind class collection runs at install/enable/disable time: scan enabled plugins' spec files for literal strings, emit one safelist stylesheet, cache it. Cost is once per registry change, not per request; dynamic browser JIT is rejected (two rendering paths means every bug hides twice). Enabling/disabling regenerates through the same hook that writes capability grants.

The cost this design accepts deliberately: spec-rendered elements get none of Svelte's compile-time guarantees or fine-grained reactivity. The mitigations are the enable-time validator and per-widget error boundaries above, both owned by v0.5, not assumed.

## Notifications (as reference plugins)

First out-of-tree-style plugins: email (SMTP) and text (e.g. Twilio). They exist here because they are the cheapest end-to-end proof that the plugin API works, not as a feature push. They consume the run event stream (v0.2 format) with filter rules per project/run ("notify me when a run waits on human review", "when cost crosses X", "when a run fails"). Delivery is best-effort with retry; failure to notify never fails a run, but the attempt lands in the run's provenance records like anything else.

## Agentic autonomy with human-drawn bounds

The AgentNode seam from v0.1/v0.2 becomes real:

- **Free roam**: an AgentNode receives tool access including ngen-weave itself exposed over MCP loopback — it can inspect projects, read artifacts, launch constrained sub-workflows. External agent hosts (pi, opencode, Codex) reach the same surface through the v0.2 MCP server; ngen-weave is agnostic about which source provides the agent's generation.
- **Boxing**: PermissionSets gain composition — allow/deny per tool and workflow, budget caps per activation and per run subtree, step ceilings, mandatory return-to-review checkpoints after N actions or on entering named territories ("touch nothing under .ngen-weave/projects/finance without approval").
- Bounded autonomy is enforced engine-side (the wrapper around every agent action), not by prompting. A boxed action is blocked and recorded, whatever the model claims it is doing.

Deliberately unsolved here: guaranteeing termination quality of open-ended exploration beyond budgets. Budgets and boxes bound damage; they do not promise usefulness.

## Non-goals

- Real-time collaborative editing (Google-docs-style simultaneous cursors).
- Collaboration slice (multi-reviewer, run/project roles, tickets): v0.8, with auth.
- External document links: v0.7.
- Plugin marketplace/distribution infrastructure (install is pip; discovery is docs).
- Unbounded autonomy or self-modifying workflows (an AgentNode cannot edit its own definition mid-run).
- Interpreter-level sandboxing of plugin code.
- Host-build compilation of plugin frontend source into the web app bundle.
- Rich client-side interactivity in spec widgets (client state, dependent inputs, streaming bindings); these go through the component-bundle path or wait for post-1.0 SDK growth.

## Success criteria

1. A third-party demo plugin defining one new node type plus a spec-driven widget backed by its own namespaced API route installs via pip, passes enable-time validation, appears correctly in editor/canvas/detail views, and its runs carry plugin-tagged provenance.
1b. A malformed plugin (spec referencing a nonexistent route, dynamically built class string) fails enable-time validation with an actionable error; disabling it removes its widget and restores the page without residue.
2. An email notification fires on human-review-waiting within seconds of the event, and a failed SMTP host never disturbs the run.
3. A boxed AgentNode attempting a denied workflow launch is blocked engine-side with a recorded event, while an allowed sub-workflow launch completes and attributes cost to the parent.
4. The same MCP surface serves both the internal AgentNode and an external client driving the identical workflow.
