# ngen-weave v0.3 release requirements

Status: draft
Prerequisite: plans/releases/v0.2.md complete (RunService with both implementations, run JSON state, MCP server).

## What v0.3 adds

A read-only web interface for viewing workflows and their projects: the graph as a navigable canvas, per-node detail views, workflow-level contracts, and a first look at `.ngen-weave/projects` artifacts. No write capability of any kind. The value is the foundation: clean primitives, a read API, and UI seams sized so run management, editing, and custom-node editing land later without redesign.

ngen-weave-web is its own published repository (generic graph/project manager), not a workspace package. It consumes only the HTTP API described here; nothing ngen-weave-specific may leak past that boundary. This version builds it with plugins in mind so v0.5 node types render without frontend rewrites.

## Stack

Decided up front, and why:

- **FastAPI** — serves the read API from the ngen-weave process itself, reusing the same loader/validator modules the CLI and MCP server use. One parser rule survives: there is no second implementation of workflow parsing anywhere.
- **SvelteKit + TypeScript** — maintainer preference; frontend only, talks to the FastAPI endpoint.
- **Svelte Flow** (xyflow) — graph canvas with pan/zoom/fit-view/filtering.
- **shadcn-svelte / bits-ui + Tailwind CSS** — accessible primitives; design tokens via CSS variables (light/dark is a variables file); Tailwind is the styling vocabulary agents maintain most reliably.
- Layout: separate `ngen-weave-web` repository; the backend serves its built static assets. One command: `ngen-weave ui` starts one process serving app + API.

## Scope

In:

1. Workflow list view with validation status.
2. Graph canvas: auto-laid-out nodes and typed edges, pan/zoom, filtering, hover highlighting.
3. Node detail views: metadata, schemas as structured tables, prompts rendered or verbatim.
4. Projects view: browse `.ngen-weave/projects` artifact trees.
5. Read-only HTTP API exposing parsed workflows losslessly-in-structure.
6. Light and dark themes from day one.
7. Docs site begins: MkDocs Material in the backend repo, versioned with releases, quickstart covering install to first run.

Out (named so absence is a decision):

- Any mutation: creating/editing workflows or nodes, writing review artifacts, launching or controlling runs.
- Live run inspection. Run state, run JSON, checkpoints stay invisible to v0.3.
- Auth, multi-user, remote deployment.
- LLM-generated summaries.
- Websockets / push updates.

## Serving

One command: `ngen-weave ui [dir]`. Single process serving both the static app and the API. Localhost tool; deployment waits until runs and auth exist.

The API reads the project-root `ngen-weave.json` manifest when present (same manifest the MCP server uses), falling back to convention-based discovery of workflows registered in Python modules on disk.

## Data freshness

Polling, not push. The client polls the list endpoint every 2–5 seconds; each response carries a content hash per workflow, so unchanged graphs skip refetch entirely. File-watching plus a websocket channel buys little for a viewing tool. Revisit when run management lands in v0.4; this PRD does not preclude push then.

## Invalid workflows

Workflows failing `ngen-weave validate` appear in the list marked invalid, full error list one click away. They do not render a best-effort graph; tolerant-parsing machinery is large and low-value, and hiding them entirely would hide signal. Fixing the definition and watching the card flip valid on the next poll is the loop.

## Read API contract

Two contractual properties:

1. **Structural fidelity.** The API exposes enough structure that a future editor can reconstruct an equivalent definition: graph config, nodes with all fields, edges, fan-in maps, schema documents, prompt bodies, plus raw source bytes alongside the parsed form. Byte-faithful round-trip is *not* guaranteed yet because the storage/serialization format is not chosen until v0.4; when it is, this contract tightens to byte fidelity without endpoint changes.
2. **Validator-gated.** Everything served has passed `ngen-weave validate`. The UI never renders unvalidated structures.

Endpoints (paths indicative):

- `GET /api/workflows` — name, description, content hash, validity + errors.
- `GET /api/workflows/:name` — full parsed structure.
- `GET /api/workflows/:name/schemas/:file` — resolved JSON Schema documents.
- `GET /api/projects` and `GET /api/projects/:path` — artifact tree listings for `.ngen-weave/projects`.

## Graph canvas

Auto-layout via dagre/elk, left-to-right, cycles as back-edges. Baseline navigation: fit-to-view, minimap, keyboard zoom, smooth pan, click-to-focus opening the detail panel, hover highlighting that dims unconnected elements, filters applying to sidebar and canvas alike.

Filtering specifics:

- Node type chips: worker / control / human / agent(mock).
- Edge kind chips: normal, control pass, control fail, human route, observer reroute. Filtering by the kind of node an edge targets included; this is what makes "hide all observer wiring" possible.
- Search matches node names and prompt text.
- Sorting applies to sidebar lists only; canvas position encodes topology.

## Detail views

Every node shows: name, type badge, model + variant, observers, input/output schema names, `description` if present.

Two presentation modes everywhere, tab-selected, plain language default:

- **Plain-language tab**: deterministic template-generated summaries ("Calls model kimi-k3 to draft a response; passes output to quality_gate"). Mechanical, derived purely from structure. Richer prose later slots into the same tab without UI changes.
- **Author tab**: raw fidelity — prompt bodies with rendered/verbatim toggle, schemas expandable to property tables (verbatim JSON behind a further toggle).

Workflow views show input/output contracts and run configuration (`max_steps`, retries, budgets) in both modes.

## The `description` field

Workflows gain a required `description` (v0.2 already requires it for MCP tool registration). Nodes carry optional free-text `description`. Naming deliberately matches across levels; they are distinct things (workflow description is what an LLM sees about the tool; node description is prose for humans) and ngen-weave does not rename either. All shipped example workflows populate node descriptions so the plain-language tab works out of the box.

## Future seams (designed now, built later)

| Future capability | Seam reserved now |
|---|---|
| Creating / editing workflows | Structural-fidelity read API, inverted; tightened to byte fidelity in v0.4 |
| Launching / managing runs | Polling upgrades to push; list gains run-status columns backed by RunService |
| Human review in UI | Canonical JSON review payloads (v0.2) through interrupt/resume |
| Custom node editing for non-technical users | Node descriptions + plain-language tabs; author tabs stay technical |
| Plugin node types (v0.5) | Type badge/filter system treats unknown types generically from day one |

Design rule: simple maintainable code over speculative scaffolding. Seams are contracts and naming decisions, not stub modules.

## Success criteria

1. All workflows in a repo visible within two clicks of opening the app.
2. A ≤15-node workflow fully legible at typical laptop size without scrolling.
3. Any validation error findable from the list view.
4. Artifact trees under `.ngen-weave/projects` browsable with producing-node provenance shown.
5. Zero write capability; verified by review (no mutating route exists).

## Non-goals

Everything under Scope → Out, plus parallel-execution visualization, subworkflow display beyond the recursive node rendering, artifact diff previews, mobile layout beyond "usable", internationalization.
