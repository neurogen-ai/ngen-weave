# ngen-weave v0.8 release requirements

Prerequisite: plans/releases/v0.7.md complete (langgraph-server adapter retired, external document links, debt sweep).

## What v0.8 adds

The collaboration slice, pulled out of the pre-split v0.6 so platform storage could land alone: real identity on the server, roles for people, and the run-level features that only make sense once both exist — multi-reviewer human nodes, run-level roles, tickets, plus `import-project` to bring pre-v0.6 file-mode projects into Postgres.

## Plugin-first

These features should ship as plugins through the v0.5 mechanism where the seams carry them: multi-review behavior as node-kind or subclass registrations, tickets and role enforcement consuming published interfaces (`RunService`, store protocols, HTTP API mounting). Anything that requires a core change is a bug in those extension seams, reported there before falling back to core. Token auth itself stays core: it is infrastructure every plugin consumer shares, not a contribution kind. Whether each piece lands in or out of tree is decided with evidence at implementation time and recorded in the plan.

## Auth and roles

Two steps inside one version:

1. **Token auth**: every API and MCP request authenticated; tokens issued per user; the deployed server is no longer implicitly localhost-trusted.
2. **Roles**: owner, reviewer, observer enforced at the RunService and web API boundaries. Who can launch, cancel, answer reviews, edit workflows, install plugins.

The old ordering argument still holds, just within this version: run-level roles without authenticated principals are untestable; auth arrives first here.

## Collaboration slice

- **Multi-human review**: a HumanNode may require N distinct reviewers before resuming; artifacts track per-reviewer completion. How N submissions resolve into the state that routes the node's out-edge is a `review_policy` class attribute on the Human node: a code-bearing callable over (context, per-reviewer submissions), referenced by registry name in serialized definitions like every other code-bearing member. The default policy is last-submission-wins; custom policies (unanimity, owner-decides, quorum merge) are ordinary Python.
- **Run-level roles** on top of project roles: per-run assignments (reviewer, observer, owner) checked at the RunService boundary.
- **Tickets**: workflow progression can create tickets assigned to members by role (minimal task list attached to a run; no external tracker integration yet).

## Import

- `ngen-weave import-project <dir>` migrates a pre-v0.8 (or current file-mode) project directory — runs, provenance records, artifact manifests — into Postgres. This is also the file-mode upgrade path for existing local projects, which is why it ships with the collaboration slice rather than with the database.

## Non-goals

- Multi-tenancy beyond projects-per-user.
- SSO/OIDC federation.
- Live collaborative editing (post-1.0).
- Distributed execution (1.1).

## Success criteria

1. An unauthenticated request to any mutating endpoint is rejected; a reviewer-role token can answer reviews but cannot launch workflows.
2. Two reviewers must both approve before a multi-review HumanNode releases; roles prevent a non-reviewer from submitting.
3. Tickets create on human-wait via workflow declaration, close through the API under role checks, and land in provenance like any other record.
4. A pre-v0.6 project directory imports cleanly into Postgres: runs, provenance, artifacts all addressable after import, and export back to JSON matches the original file's semantics.
