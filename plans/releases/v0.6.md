# ngen-weave v0.6 release requirements

Prerequisite: plans/releases/v0.5.md complete (plugins, notification reference plugins, boxed autonomy).

## What v0.6 adds

The platform layer ngen-weave has been running without: a real database, real auth, and the collaboration features that only make sense on top of both. Until now everything lived in files under `.ngen-weave/`, which was honest and simple and stops being enough once multiple people, roles, and long-lived server deployments exist. The v0.5 collaboration slice lands here rather than there because run-level roles without authenticated principals are untestable; auth arrives first in this same version.

## Postgres becomes canonical

- Migration of run state, events/provenance records, artifact manifests, workflow registrations, and (from v0.5) tickets/roles into Postgres.
- SQLAlchemy 2.0 async engine, Alembic migrations from day one. Schema churn is guaranteed through 1.0; migration tooling pays immediately.
- Artifact blobs stay content-addressed on disk or object storage; the database holds their hashes and manifests. Hashes are the join key.
- JSON export stays a first-class operation, not an afterthought: any run exports to the same single-file JSON format used before v0.6, byte-compatible with the pre-DB writer where practical. Reproducibility handoffs never require database access.
- `ngen-weave import-project <dir>` migrates a pre-v0.6 project directory (runs, provenance records, artifact manifests) into Postgres.
- SQLite remains the zero-config local mode (`ngen-weave run` on a laptop still touches no server). The database is required only in server deployments.

## Auth and roles

Two steps inside one version:

1. **Token auth**: every API and MCP request authenticated; tokens issued per user; the deployed server is no longer implicitly localhost-trusted.
2. **Roles**: owner, reviewer, observer enforced at the RunService and web API boundaries. Who can launch, cancel, answer reviews, edit workflows, install plugins.

## Collaboration slice (moved from v0.5)

- **Multi-human review**: a HumanNode may require N distinct reviewers before resuming; artifacts track per-reviewer completion.
- **Run-level roles** on top of project roles: per-run assignments (reviewer, observer, owner) checked at the RunService boundary.
- **Tickets**: workflow progression can create tickets assigned to members by role (minimal task list attached to a run; no external tracker integration yet).

## Non-goals

- Multi-tenancy beyond projects-per-user.
- SSO/OIDC federation.
- Live collaborative editing (post-1.0).
- Distributed execution (1.1).

## Success criteria

1. A fresh server deployment runs against empty Postgres with Alembic up-migrations only; no manual schema steps.
2. A pre-v0.6 project directory imports cleanly: runs, provenance, artifacts all addressable after import, and export back to JSON matches the original file's semantics.
3. An unauthenticated request to any mutating endpoint is rejected; a reviewer-role token can answer reviews but cannot launch workflows.
4. Two reviewers must both approve before a multi-review HumanNode releases; roles prevent a non-reviewer from submitting.
