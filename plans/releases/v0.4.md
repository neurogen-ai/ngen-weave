# ngen-weave v0.4 release requirements

Status: draft
Prerequisite: plans/releases/v0.3.md complete (read-only UI, structural-fidelity API, projects browsing).

## What v0.4 adds

The MVP product loop: create, edit, launch, and manage workflows from the UI, with artifacts that have history. This is the first version where ngen-weave is usable by someone who never opens the Python source, and the version where the deferred storage/config question finally gets answered because editing forces it.

## The storage decision (deferred no longer)

Workflows are currently Python objects. Editing in a UI needs a persistent representation that survives process restarts, diffs cleanly, and loads back into the object model. v0.4 designs and ships it:

- A declarative serialization of the node/graph object model, **data only**: structure (children, edges with branch labels including human state branches and `into` slot targets), schemas as canonicalized JSON Schema documents — the same documents pydantic's `model_json_schema()` emits, stored verbatim so the served form and the stored form are one artifact (no parallel type language exists), prompt templates, parameters, observer declarations (description string plus action), thresholds. YAML primary (clean diffs for humans reviewing changes), JSON accepted as an equivalent dialect, matching the config-layer decision from v0.1. This is the v0.1 config format widened to full coverage of every serializable field; same syntax, same file roles. The v0.1 subset remains valid input unchanged.
- Code-bearing members (`run()` overrides, method-form prompts, observer predicate functions) never serialize. A definition references a registered Python workflow by name for anything carrying code; ngen-weave serializes data and names primitives, git owns code history, provenance owns run history.
- Round-trip contract: `load(dump(x))` reproduces the data subset exactly, byte for byte, for every shipped workflow. Code-bearing members round-trip as their registry-name references.
- Hand-editing the files is allowed but secondary; the objects remain canonical. Validation gates everything exactly as today.
- Git is the change-history mechanism. No database in v0.4.

This format replaces nothing that exists; it wraps what exists. `ngen-weave validate` gains a `--format` path so serialized definitions check statically.

## Scope

In:

1. Workflow editor: create/edit nodes and graphs on the canvas (add/remove/connect nodes, edit fields, prompts, schemas, observers), writing through the storage layer.
2. Run management screens: launch with inputs, list/filter runs (threads), status detail, cancel, pause/resume, budget display.
3. Human review in the UI: review artifacts rendered from the canonical JSON payload, submitted through interrupt/resume.
4. Artifact diff tracking on the content-addressed store fixed in v0.1: every artifact write versions content as hash-keyed blobs with small JSON manifests; diffs computed over arbitrary file types (text gets line diffs; binaries get size/hash change indicators). Display is best-effort per type; tracking is universal.
5. Provenance export: a run's full provenance graph exported as W3C PROV-JSON (activity = node activation, entity = input/output/artifact, agent = model call), plus the single-file run JSON alongside. Aimed at open-science reproducibility: given the export plus the workflow definition, an outsider can re-derive what produced an artifact.
6. Budget controls in the UI: set cost/step caps at launch or mid-run; breach behavior as built in v0.2 (pause, not die).

Out:

- Plugins / third-party node types (v0.5).
- Collaboration, roles, tickets (v0.5).
- Notifications (v0.5).
- Scheduling workflows for future launch (simple "launch now" only; cron-style scheduling deferred until someone asks).
- Live-updating run views beyond polling (push lands here if run screens need it; decided by evidence during implementation).
- Real AgentNode autonomy (still harness-grade from v0.2).

## Architecture notes

- All mutation flows through the same validation gate. The UI never writes a file it hasn't validated; the API rejects invalid definitions with the full error list, identical to `ngen-weave validate` output.
- One write path rule: editor saves go API → storage layer → disk → reload through the standard loader. The browser never writes YAML/JSON itself.
- Diff engine lives in core (`ngen-weave.diff`), not the frontend: content-addressed artifact versions, language-agnostic diff records the UI renders.
- Provenance exporter reads the run JSON and checkpoints only; no new instrumentation is added to workflows. If the export is missing something, the fix is in the record stream, not the exporter.
- Editor canvas reuses the v0.3 read-only canvas component with mutation handlers attached; unknown or future node types render generically (the v0.3 seam) so v0.5 plugins do not require editor rewrites.

## Non-goals carried forward

Parallel execution within a workflow; subworkflow nesting beyond what v0.1 recursion already supports; auth/multi-user; remote deployment; templating in artifacts.

## Success criteria

1. A user creates a two-node workflow entirely in the UI, launches it, answers a human review in the browser, and gets the final output. Zero source files touched.
2. Every saved workflow round-trips its data subset exactly through the storage layer, and code-bearing members round-trip as registry-name references (property test over all example workflows).
3. An artifact edited across three runs shows three versions with inspectable diffs and a provenance export tracing each version to its producing activation.
4. A PROV-JSON export validates against the W3C schema and contains no reference to entities absent from the run JSON.
5. Mid-run budget reduction pauses a running workflow at the next transition.
