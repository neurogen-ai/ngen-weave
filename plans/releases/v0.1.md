# ngen-weave v0.1 release requirements

Status: draft
Prerequisite: none. First version.
Scope: the Python core. Everything here is testable as a vertical slice: define a workflow in Python, configure it in YAML, run it locally on LangGraph, resume it after a crash or human pause.

## What v0.1 delivers

The Workflow abstraction, done right once so nothing later reworks it:

- A single `Workflow` class family (no generics). Subclasses declare `input_type` and `output_type` as pydantic models, validated strictly at every boundary. The same classes generate the JSON Schema consumed by config, validation, and later MCP/UI.
- Composite workflows wire their structure inside a `build(g)` method over a narrow `GraphBuilder` protocol (`add_node`, `add_edge`, `add_conditional_edges`) that delegates to an ordinary LangGraph StateGraph. Routing is declared with conditional edges whose branch-map keys are the possible runtime values (a control's `pass`/`fail`, a human's submitted verdict); there is no separate branch-label vocabulary. Example:

```python
class CodeReview(Workflow):
    name = "code_review"
    input_type = ReviewRequest
    output_type = ReviewedDiff

    def build(self, g):
        g.add_node(self.draft)
        g.add_node(self.gate)
        ...
        g.add_conditional_edges(self.gate, pass_router,
                                {"pass": self.finalize, "fail": self.human_review})
        g.add_conditional_edges(self.human_review, verdict_router,
                                {"approve": self.finalize, "reject": self.draft})
```

Structure is code, never serialized into config: validation is an import-time dry-run compile of `build()`, one build against a throwaway StateGraph, plus a static lint over `build()`'s source rejecting stateful or environment-dependent wiring.
- Fan-in is opt-in and typed, with two forms, both checked at compile time. **Named slots** for few heterogeneous parents: an edge may carry `into="<field>"`, targeting a field of the child's `input_type`; every required field is covered by exactly one slot edge, and each source's `output_type` must validate against the targeted field's type.

```python
class Synthesize(Workflow):
    input_type = MergeInput          # draft: DraftOut, critique: CritiqueOut

def build(self, g):
    g.add_edge(self.draft, self.synth, into="draft")
    g.add_edge(self.review, self.synth, into="critique")
```

  **Collected fan-in** for many homogeneous parents: the child's `input_type` contains exactly one `list[<model>]` field, and pydantic's own `Field(min_length=..., max_length=...)` on that list bounds how many parents it accepts — arity lives in the schema, so "at most four inputs" needs no separate attribute. The engine collects every parent's validated output into that field and validates the assembled model normally.

```python
class ReduceInput(BaseModel):
    reviews: list[ReviewOut] = Field(min_length=2, max_length=5)
```

  Anything else multi-parent fails the import-time compile naming the nodes: duplicate slots, uncovered required fields, parent count outside list bounds, more than one list field (the collector must be unambiguous; widen with an explicit marker attribute only if a real model ever needs two). Human nodes stay single-parent regardless of form. Default remains one parent feeding its whole validated output as the input. There is no merge-overwrite behavior anywhere: a field's value never depends on edge declaration order.
- Worker prompts are a `prompt` class attribute: a template string rendered against validated input fields (`{request.diff}`), overridable by a `prompt(self, input)` method when generation needs logic. Templates stay data so they serialize, diff, and render in UIs.
- Human workflows take one edge input and surface it as read-only `context` in their review artifact. Between input and output sits an internal state model (`state_type`, a pydantic model): editable, prefilled from the context, validated on submission. Conditional edges out of a human are declared in `build()`, their routers reading an enum/literal verdict field of the submitted state (like `"approve"` / `"reject"` / `"revise"`, generalizing control's pass/fail), so routing reads what the human submitted without a mandatory downstream control node. There is no separate branch-label vocabulary: the branch-map keys *are* the possible state values. The artifact therefore has two sections:

```yaml
context:  {...}     # edge input, validated against input_type, never edited
response: {...}     # empty editable slots generated from state_type leaves
```

Response slots cover leaf primitive fields of `state_type` (`str`/`int`/`bool`/enum/literal); fields with defaults may be left empty; required-without-default blocks completion. Completing a review validates with plain `state_type.model_validate(response)`; out-edge branch labels must then match the submitted state values, resolved the way control branch labels are. State and output are distinct models: by default the engine passes the validated state through as the node's output; a subclass may override with a programmatic `(context, state) -> output` transformation, whose result is validated against `output_type` before it travels over an edge.

A per-node `prefill` map seeds response slot values from the context: path strings into the edge input (`"gate.notes"`). Prefill fills the artifact, never completes it: even fully prefilled required fields wait for human submission, since submitting the reviewed artifact is the act that resumes the run.
- Node types: Worker (model call via LiteLLM), Control (programmatic predicate or model-filled boolean `pass`, routing on pass/fail targets), Human (interrupt plus review artifact plus state-driven enum routing). All four are Workflows.
- Recursion native from day one: a workflow appears anywhere a node does. Even if tests exercise one level of nesting deeply and two levels lightly, checkpoint trees, per-level cost attribution, interrupt propagation, and `(run_id, node_path)` addressing exist now.
- Supervision metadata: every activation records the frozen six-field metadata object (iterations, tokens_in_context, tokens_total, cost_usd, elapsed_ms, last_output_valid) into provenance, computed by the engine per scope. No author-facing observers in v0.1; they arrive in v0.2 built into the scheduler (see that release doc).
- Provenance records emitted on every activation without opt-in: kind-typed payloads (node_activation, model_call, artifact_write) in a versioned envelope.
- AgentNode seam declared with mocked executor and PermissionSet shape, so budgets and boxes have something real to constrain later.

## Registration and configuration

- A workflow is an ordinary `Workflow` subclass carrying `description` as a class attribute; nothing registers by existing. Identity is the fully-qualified class path (`module.__qualname__`) — no author-chosen name attribute — so plugins may ship same-named classes without collision; UIs tidy the path for display, never for identity.
- Discovery is explicit listing, never scanning: distributions declare workflow modules under the `ngen-weave.workflows` entry-point group (pip resolves them from the same wheel as the code, so the pointer cannot go stale); projects list modules in their manifest; importing a listed module auto-registers every `Workflow` subclass found there. Duplicate class paths fail loudly.
- Author-facing YAML config references registered workflows by class path with kwargs (JSON accepted as equivalent dialect), and assigns models through a top-level `models:` section: keys are fully-qualified class paths matching concrete classes only (inheritance plays no role) — naming a composite assigns every model-calling leaf in its subtree however deep, naming a leaf binds it directly and overrides enclosing scopes — values are variant names from `models.json`. Code declares structure; config assigns models; workflow classes carry no model attributes. Thin by design: wiring, parameters, run settings. One standing constraint recorded here so early configs never paint us into a corner: the v0.4 editor serialization widens this same format to cover every serializable field, never a new syntax. Everything valid in v0.1 configs stays valid forever.

## Engine and state

Thin wrapper over LangGraph's StateGraph: nodes are node functions, control booleans are conditional edges, human interrupts map to `interrupt()`, composites are subgraphs.

Sequential execution only. Input assembly follows the child's declared fan-in form: single parent passes its validated output through unchanged; named slots assemble `{field: source_output}` from their `into` edges; collected fan-in appends parent outputs to the declared list field. The assembled model then validates against `child.input_type` as usual. Any multi-parent situation not matching a declared form failed at import time already, so assembly cannot fail on wiring at runtime. SQLite checkpointer by default, memory for tests. One JSON file per run under `.ngen-weave/runs/<run-id>/` holding metadata plus the event/provenance stream, written atomically per transition, always valid, sufficient to re-run.

Error taxonomy: data failures (schema-invalid output, failed control logic) flow through the graph and never retry; infra failures retry per policy (default 3 attempts, exponential backoff from 1000ms); config errors kill the run with a report. `ngen-weave resume <run-id>` continues from any stop.

## Model layer

LiteLLM via `init_chat_model`, resolved through project-root `models.json` shared across workflows. Variants are data; the run config's `models:` bindings override `defaultVariant` per class or subtree (see Configuration). Auth is provider environment variables. One `CompletionProvider` protocol; adapters translate, never extend.

## Artifacts (minimal)

A workflow may declare outputs worth persisting; validated writes land content-addressed under `.ngen-weave/projects/<project>/` with provenance linking artifact to producing activation and input hashes. Diff tracking, display, export formats come later; the record shape is fixed now.

## CLI

```
ngen-weave validate <config-or-module>
ngen-weave run <workflow> [-i input.json]
ngen-weave resume <run-id>
ngen-weave status <run-id>
```

Every command also ships under the short alias `ngw` (`ngw run`, `ngw resume`, ...), registered as a second console script entry point in the same package. Both names are official; docs use the long form, examples may use either.

Validation catches (all at import time via dry-run compile plus static checks): schemas resolve, class paths unique across sources, exactly one START edge, END reachable, no unreachable nodes, fan-in legality (multi-parent targets fit a declared form; slots covered exactly once with type-matching sources; collected arities within list bounds; humans single-parent), control schemas require boolean `pass`, human verdict field exists and is enum/literal-typed, prompt placeholders reference real `input_type` fields, artifact names exist on `output_type`, boundary agreement where trivially decidable, duplicate class paths across sources, `models:` binding keys resolvable to Workflow classes with variant values known to `models.json`.

## Repo and toolchain

uv workspace monorepo, packages `ngen-weave-core` and `ngen-weave-cli` shipping inside one `ngen-weave` distribution. Python ≥3.12, pytest, ruff, Apache-2.0, Forgejo CI, conventional commits.

## Canonical examples

Two shipped, both exercised end to end by tests:

1. **Code review** (canonical): worker drafts a review, control gates it, human approves or rejects, reviewed diff lands as an artifact with provenance.
2. **Document drafting**: draft, model-mode quality-gate, human review, finalize. Kept visible so agnosticism stays honest (the model-filled control already exercises the second node mode).

## Non-goals for v0.1

- Parallel execution, scheduling, queues.
- MCP exposure, serving, web UI, run management API.
- Artifact diffing, display, export.
- Plugins beyond in-process subclassing.
- Real AgentNode execution (mocked only).
- Postgres or auth (files and SQLite only).

## Success criteria

1. Both canonical examples run end to end from the CLI and pass e2e tests, configured through YAML without touching their source.
2. Killing the process mid-run and calling `ngen-weave resume` completes the run correctly.
3. A two-level nested workflow runs with correct per-level cost attribution in provenance and a resumable interrupt at depth 2.
4. Every activation produces provenance addressable by `(run_id, node_path)` with zero logging code written by the workflow author.
5. Registering two workflows resolving to the same class path across discovery sources makes `ngen-weave validate` fail naming both.
