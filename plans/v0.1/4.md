# Step 4 — workflow loader and static validator

PRD reference: "Graph configuration", "Fan-out and fan-in", "Canonical examples", and the `loom validate` bullet list.

## Goals

- Load a workflow directory (graph.yaml + node .md files + schema files + models registry) into one resolved, fully validated `Workflow` object. This is the object the engine consumes; nothing downstream re-reads YAML.
- Implement all checks `loom validate` promises, as a pure function the CLI calls in step 11.

## Detailed steps

1. `src/schema/load.ts`:
   - `loadNodeDef(path): NodeDefinition` — read `.md`, split frontmatter from body, parse frontmatter with the `yaml` package against `node-def.ts` schema. Body becomes the prompt if no `prompt:` key exists; if both exist the key wins; if neither exists throw `ConfigError`. Apply name default from filename.
2. `src/schema/workflow.ts` — the resolved runtime shape:
   - `name`, `inputSchema`, `outputSchema` (parsed JSON Schema objects), `maxSteps`, `retries`,
   - `nodes`: record of name → `{ def: resolved NodeDefinition, inputsMap?: Record<string,string>, observers: resolved Observer[] }`,
   - `edges`: normalized list,
   - `models`: parsed registry,
   - `hash`: sha256 over the concatenation of all loaded file contents (for state.json's workflow hash).
3. `src/engine/validate.ts` exporting `validateWorkflow(dir: string): { ok: true, workflow } | { ok: false, errors: string[] }` plus a throwing variant `loadWorkflow(dir)`. Checks, each producing a clear error message with file path:
   - graph.yaml parses and passes its Zod schema; every referenced node def file exists and parses.
   - All `input`/`output` paths resolve (relative to the declaring file); JSON Schema files parse as JSON/YAML and are draft 2020-12 compatible enough to use with Ajv (add `ajv` dependency here).
   - Node names unique across the graph.
   - Edges reference existing node names; control nodes' outgoing edges use only the compact pass/fail form; non-control nodes never have pass/fail edges.
   - Control node output schemas contain a required boolean property named `pass`.
   - Human node routes reference existing nodes; observer reroute targets reference existing nodes.
   - Fan-in: any node with multiple incoming edges must declare an `inputs` map covering all fields required by its input schema. Single-parent nodes may omit it (pass-through). Mapping keys must exist in the child input schema's required properties or properties.
   - Workflow-level invariant: entry nodes (no incoming edges) accept the workflow input schema; exit candidates (nodes whose outgoing routes all leave the graph — i.e. control fail/pass targets that are absent are not allowed since targets must exist; so exit candidates are simply nodes with no outgoing edge) produce the workflow output schema. Validate via JSON Schema composition: workflow input must validate whenever entry input validates (use `ajv` compile + a few probe documents is too clever; instead require structural compatibility check: the workflow schema and the union of entry schemas are mutually satisfiable — implement as: workflow input schema must be a subset constraint of each entry node's input schema, checked with ajv by validating synthetic minimal instances is unreliable, so simply require that each entry node's input schema equals or is looser than the workflow input schema using `$dataMeta` free comparison of required lists). Keep this simple and documented: compare `required` field sets — workflow input's required set must be contained in each entry node's required set, and vice versa for outputs at exits. Document the limitation in code comments.
   - Expressions compile: human route `when`s and observer `when`s go through step 3's compiler with allowed identifiers = metadata six fields + observer params (observers), or artifact output-schema properties (human routes).
4. Unit-test fixture workflows under `test/fixtures/`: one valid full example (draft → quality_gate → finalize/human_review mirroring the PRD), plus broken variants matching each validation rule.

## Success criteria

- `validateWorkflow` on the good fixture returns ok with a fully resolved Workflow.
- Every broken fixture fails with exactly one targeted, readable error.

## Tests

- Good fixture loads; names resolved; relative paths absolutized; hash stable across two loads of same dir.
- Duplicate node names rejected. Edge to nonexistent node rejected. Long-form edge on a control node rejected. Control output schema without required boolean `pass` rejected. Incomplete fan-in map rejected. Non-compiling expression rejected. Reroute target pointing at a nonexistent node rejected. Worker with neither prompt key nor body rejected.

## Commits

- `feat(schema): markdown node definition loader`
- `feat(engine): static workflow validator with fan-in, contract, and expression checks`

## Out of scope

- Executing anything (step 5+)
- The CLI command surface itself (step 11)
- Subworkflow resolution when a `def` points at another `graph.yaml` — detect it and reject with "not supported in v0.1"
- Deep JSON Schema semantic diffing beyond the required-fields subset check
