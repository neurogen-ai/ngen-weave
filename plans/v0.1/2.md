# Step 2 — Zod schemas and error types

PRD reference: every YAML/frontmatter block in the PRD. These schemas are the single source of truth; later steps parse with them.

## Goals

- One `src/schema` module per PRD concept, plus the shared error hierarchy.

## Detailed steps

1. `src/schema/errors.ts`:
   - `abstract class LoomError extends Error` with a `kind` field.
   - `ConfigError` (static, malformed workflow), `DataError` (invalid node output / failed control logic / unmet human requirements), `InfraError` (transport/API). Each takes a message and an optional `details` object.
2. `src/schema/node-def.ts` — schema for a node definition file's frontmatter (the `---` header of `.md` files):
   - `type`: enum `worker | control | human`.
   - `name`: optional string (defaults to filename at load time).
   - `input`, `output`: required strings (schema file paths).
   - worker/control-model fields: `model` (string), `variant` (optional string), `temperature` (optional number 0–2).
   - control-only: `mode`: enum `programmatic | model`. For `mode: model`, model/variant/temperature apply. For programmatic, they must be absent.
   - human-only: `routes`: array of `{ when?: string, to: string }`; at most one entry without `when`, and it must be last if present.
   - `observers`: optional array; each entry is either `{ ref: string }` plus arbitrary extra keys, or an inline map with `when: string`, `action`, and parameter keys. Model as a union; validate `action` against the action schema below.
   - `prompt`: optional string (inline prompt).
3. `src/schema/graph.ts` — schema for `graph.yaml`:
   - `name`: string.
   - `input`, `output`: strings (workflow-level schema paths).
   - `retries`: optional `{ attempts?: number (default 3), backoff_ms?: number (default 1000) }`.
   - `max_steps`: positive int, required.
   - `nodes`: record of name → `{ def: string, inputs?: record<string, string> }` (`inputs` is the fan-in map).
   - `edges`: array of edge variants: `{ from, to }` OR `{ from, pass, fail }`. Reject any edge mixing the two shapes (Zod strict objects in a discriminated attempt make this automatic).
4. `src/schema/models.ts` — schema for `models.yaml`: record of alias → `{ provider: string, id: string, variants?: record<string, unknown> }`.
5. `src/schema/observer.ts`:
   - action: discriminated union on `type`: `{ type: "pause" }`, `{ type: "stop" }`, `{ type: "reroute", target: string }`.
   - resolved observer shape used by the engine later: `{ when: string, params: Record<string, unknown>, action }`.
6. `src/schema/state.ts` — run state file (`state.json`) shape:
   - `run_id`, `workflow_dir`, `workflow_hash`, `status` (enum `running | waiting_human | paused | done | failed | stopped`), `steps_used`, `current_node` (nullable),
   - `node_status`: record name → enum `pending | blocked | waiting_human | done | failed | skipped`,
   - `outputs`: record name → unknown (validated JSON values),
   - `observer_events`: array of `{ node, observer_when, fired_at, metadata }`.
7. Unit tests per schema: valid examples from the PRD parse; each malformed case listed under Tests throws with a readable message.

## Success criteria

- Every structure in the PRD has a named exported Zod schema and an inferred TS type.
- All tests green.

## Tests

- Worker frontmatter example from the PRD parses, including inline + ref observers.
- Edge long-form-with-control-keys mixtures are rejected (`{from,to,pass}` fails).
- Control `mode: programmatic` with a `temperature` field is rejected.
- Human routes: two entries missing `when` rejected; `when` entry after default route rejected.
- `max_steps: 0` and negative rejected.
- Observer action with unknown `type` rejected.

## Commits

- `feat(schema): zod schemas for node defs, graph, models, observers, state`
- `feat(schema): typed loom error hierarchy`

## Out of scope

- Reading files or parsing markdown frontmatter (that is the loader, step 4)
- Compiling or evaluating expressions (step 3); here `when` is just a string
- Any resolution of relative paths, defaults application, or cross-field checks beyond what one schema can express (step 4 owns semantic validation)
