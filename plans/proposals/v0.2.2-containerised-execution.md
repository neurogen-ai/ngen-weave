# ngen-weave v0.2.2 proposal: containerised execution

Status: draft, pre-ratify.

## Context

v0.2.1 realigned the engine and shipped. The containerisation brief (`../research/brief-containerised-permission-gate.md`, status: open question) asks whether the security boundary should move from our in-process `PermissionGate` to the container runtime. The SWE_tools example already runs agent activations as trusted subprocesses with a documented "container it yourself" caveat (`pi_rpc.py` SAFETY note), so the gap between "gate we wrote" and "boundary the OS enforces" is live in the examples today. This proposal claims the v0.2.2 patch slot for that work. If a reviewer reads "can" as something else, this doc's interpretation is containers and nothing else.

The PRD places container volume mounting at 1.0. That is artifact-store configuration for deployed servers, not execution isolation. Nothing here moves that entry.

## Proposed features

1. Whole-graph containerised execution, opt-in: one container holds the engine and its workers; the run API tunnels out so callers cannot tell the difference.
2. The in-process `PermissionGate` stays, inside the container, as the soft gate for allowlists, call caps, budgets, and return-to-review.
3. Canonical run state stays external: workflow code in the container reaches `runs.db` only through the tunnelled API. The langgraph checkpoint database stays on a container-internal volume.
4. A container process that dies before the API responds writes one fully serialised JSON crash report to the mounted volume, strings only.
5. Ship the already-merged headless RPC hardening (dialog auto-answer, `--no-extensions` workers, infra retry cap) as the v0.2.2 fix batch, and pin langgraph to the exact `uv.lock` versions instead of `>=0.2`.

## Architecture decisions

Each decision names the rejected alternative and why.

**One container for the whole graph, not one per activation.** Per-activation isolation is the brief's richer Option B shape and it loses on evidence, not taste: cold-start cost per activation, `PermissionSet` fields (`max_calls`, `budget_usd`, `denied_policy`) have no faithful container-policy equivalent, and the brief's own deliverable list (cold-start measurements, `PermissionSet`-to-container mapping table) has not been executed. Granularity arrives when that research exists, not before.

**Backend owns the container; callers get a tunnelled API.** Rejected: letting the user containerise the deployment themselves. The brief says why: it presents friction to getting the UI to run, and half-configured isolation reads as worse than none.

**Run store external, checkpoint store internal.** The brief's secondary question, decided as a split. Rejected mounting both databases: code inside the container could rewrite run history and provenance directly, which voids the provenance guarantee the PRD makes ("provenance is emitted unconditionally"). Rejected putting the checkpoint store outside too: in-flight state would cross the tunnel on every transition, re-creating the write amplification the v0.2.0 SQLite move just removed. The checkpoint database is engine-internal state by definition; the canonical run history is the product's memory and stays where the API can police it.

**Opt-in flag with in-process fallback, not container-by-default.** Rejected default-on: dev machines and CI without a container runtime (the brief lists Windows/macOS portability) would fail at startup. The fallback must behave identically, which is testable (exports byte-identical).

**Keep the in-process gate alongside the container.** Rejected container-as-the-only-gate: "scout cannot write" is a tool-allowlist judgement, not a network policy, and `denied_policy: return_to_review` is engine semantics. The container bounds blast radius; the gate still counts calls and money.

**Crash reports are serialised strings on a mount.** Rejected structured artifacts or direct store writes from the crashed process: anything richer than a JSON file of strings crossing the boundary is an execution risk precisely when the process state is least trustworthy.

## Risk assessment

Severity per the risk-assess skill: BLOCKING invalidates until it resolves into descope or redesign; MAJOR must carry a trigger; MINOR is recorded and absorbed.

### Friction points

**F1. The engine currently owns both stores in one process. MAJOR.** `engine/runner.py` wires the checkpointer and the `RunStore` into the engine; `engine/store.py:45` derives `runs.db` as a sibling of the runs dir; `local_service.py` and the server package both assemble this by hand. Splitting durable execution (internal) from canonical history (external) means one SQLite writer becomes a process plus an HTTP client, and two databases that were transactionally adjacent are now separated by a socket. This was BLOCKING until decision 3 resolved the placement; it stays MAJOR because the split must actually hold under failure.
Trigger: probe script in the implementation branch kills the container mid-run and resumes from the internal checkpoint volume; if the resumed run's exported bytes differ from an uninterrupted control run, cut the tunnel and the external-store decision (feature ships with `.ngen-weave` volume-mounted, which is v0.1 semantics and a recorded downgrade).

**F2. Every provenance append crosses the tunnel. MAJOR.** The engine appends records at every transition (`engine/store.py` append path, observer emissions). Each becomes a local HTTP call. Model latency dominates wall time, so the average case is safe; the risk is the concurrent-drive path v0.2.1 just hardened (`test_drive_isolation.py`).
Trigger: the 3-repeat concurrency test from the v0.2.1 plan, run containerised against in-process; if run wall time doubles or a drive-isolation invariant trips, batch appends; if batching is not enough, cut the tunnel (see F1 trigger).

**F3. Image build and pinning. MAJOR.** The container must build deterministically in Forgejo CI with pinned Python and langgraph versions; unpinned images repeat the failure-attribution ambiguity `refactor-lang.md` already complains about.
Trigger: if the image build cannot be made deterministic in CI, cut published images; the Dockerfile ships in-repo, built locally, documented in the release notes.

**F4. Runtime detection and portability. MINOR.** Opt-in flag plus in-process fallback absorbs dev machines without docker. Recorded because the fallback identity claim (byte-identical export) is the one thing that must not drift.

**F5. MCP dispatch spawns host-side processes today. MINOR.** `ngen_weave_mcp/stdio.py` and `http.py` chdir to the project root and spawn the CLI with `--models`/`--db` overrides. The server stays host-side in containerised mode and launch/run tunnel in through `LocalRunService`, which is already the seam. No rework expected; the conformance suite is where it would show if wrong.

### Cost to build

- Container wrapper plus API tunnel: medium, as large as the `LocalRunService` extraction in v0.2.1.
- Store split (decision 3): medium, same budget.
- Crash report path: small, as small as the tolerant store startup fix in v0.2.1.
- Fix batch and pins (feature 5): small, already merged except the version bump.

Reference point for "too big": v0.2.0 absorbed the SQLite store move, FastAPI serving, and the MCP server in one release. Nothing here exceeds that. If the total grows past it, feature 1 waits for v0.3 (the least entangled later slot per `../research/drop-langgraph-earliest-point.md`).

### Descope triggers

Each trigger names what gets cut and where it is checked. Scope shrinks here or nowhere.

1. If the kill-and-resume probe (F1) shows the store split cannot produce identical exports, cut the API tunnel and decision 3; the release ships containerised execution with `.ngen-weave` mounted, and the external-store idea returns to the brief as an unanswered question. Checked by the probe script before any tunnel code merges.
2. If containerised launch overhead exceeds 5 seconds over in-process on the reference example, cut crash reports and tunnel batching; keep containerised execution with the checkpoint volume only. Checked by the overhead probe in the implementation branch.
3. If the image build is not deterministic in CI, cut published images, keep the in-repo Dockerfile. Checked in the first CI run of the release branch.
4. If the in-process fallback cannot be kept byte-identical in exports, cut containerised execution from v0.2.2 entirely and reschedule against v0.3. Checked by the export-identity acceptance command before the container work merges. This trigger is the whole scope contract: the fallback is not a degradation, it is the release.

## Non-goals

Per-activation containers, Windows containers, a published registry, remote dispatch. The brief's unmapped `PermissionSet`-to-container research stays open; this proposal builds the whole-graph slice that needs no new research.
