## Conventions every step follows

- TypeScript workspace monorepo (npm workspaces). Packages: `packages/core`, `packages/cli`, `packages/mcp`, `packages/export-langgraph`. Generated Python lives in `langgraph/` and is committed, built by CI, never hand-edited.
- Zod schemas in `packages/core/src/schema` remain the single source of truth for all YAML/frontmatter structures. Types are `z.infer`.
- Every structure crossing the TS→Python boundary is defined once as a JSON Schema derived from the Zod schema; the generated Python validates against it at runtime. No second hand-written definition of the same shape.
- Paths inside a workflow resolve relative to the declaring file, resolved once at load time.
- Error hierarchy unchanged from v0.1: `ConfigError` (static), `DataError` (flows through graph), `InfraError` (retryable).
- Commit style: conventional commits, one commit per "Commit" bullet.
- Test runner: vitest. Python side uses pytest, run only where a step says so.

## Rules for the implementing agent

- Do exactly what the current step says. Anything the PRD needs but the step doesn't ask for belongs to another step or to "Out of scope". Leave it alone.
- If the LangGraph API can't map something the way the step describes, stop and report back with evidence before cutting scope. There is no documented-subset mode.
- Adapters translate; they never extend. If you find yourself adding methods to `CompletionProvider` or `NodeExecutor` beyond what the PRD shows, you are extending, not translating.
- The smoke runner is non-authoritative. Never add behavior to it "to match" the backend; if they diverge, the backend wins and the divergence gets documented, not patched around.

## Global out of scope (applies to all steps)

From the v0.2 PRD non-goals, plus constraints inherited from v1.0:

- Parallel execution within a workflow
- Subworkflow nesting
- Any REST API owned by loom beyond what langgraph-server provides
- Templating in artifact paths or content (plain JSON dumps only)
- Any pi-specific code path; pi appears only in docs as an MCP consumer
- Argo export, remote container dispatch, multi-tenant serving (v1.0)
- Web UI, read API, polling (v0.3)
- Loom-managed credential store; auth on the MCP HTTP transport beyond what the deployment doc mentions
