# Step 10 — MCP server

PRD reference: "Workflow-as-tool: the MCP server".

## Goals

- `packages/mcp` serves workflows as MCP tools. Any MCP client can call them; pi is just the first documented consumer.

## Detailed steps

1. Manifest: `loom.json` at project root, Zod schema in core:
   ```ts
   loomManifest = z.object({ workflows: z.array(z.string()) })  // workflow dir paths
   ```
   Add `loadManifest(projectRoot)` to core. Absent manifest → error listing the expected path.
2. Server (`packages/mcp/src/server.ts`), built on the official MCP TypeScript SDK:
   - At startup: load manifest, load + validate every listed workflow via core. Any validation failure → exit non-zero with all errors printed (fail loudly, not mid-conversation).
   - One tool per workflow. Tool name = workflow `name:`. Tool description = graph.yaml `description:`. Input schema = workflow's top-level input JSON Schema converted to MCP tool-input format via the step 2 serializer.
   - Tool handler: dispatch to the backend client from step 9 (configured endpoint; start local server if missing, same logic as CLI). Synchronous and blocking: await final output. Result content = validated output object as JSON text block. Intermediate node traffic never crosses the seam.
3. Transports: stdio (default) and HTTP streamable (`--http --port N`). One `startServer(transport)` function, two thin entry wrappers.
4. CLI integration: `loom mcp` command starts the server (delegates into `@agent-loom/mcp`). Keep the package importable so clients can also embed it programmatically.
5. Docs: `docs/mcp.md` with a pi configuration snippet showing pi consuming loom's server — pi appears only here and in README prose, no code dependency anywhere.

## Success criteria

- A generic MCP client (use the SDK's InMemory client in tests) lists one tool per workflow with correct name/description/schema, calls it, and receives the validated final output of a full run including a human interrupt resolved by pre-seeding an auto-resume test double (test-only resume hook, not shipped behavior).

## Tests

- Startup failure: broken workflow → non-zero exit, error list.
- Tool listing matches workflows for a two-workflow fixture project.
- Blocking call returns final output; max_steps exhaustion surfaces as a tool error result, not a hang.
- stdio transport smoke test over child process.

## Commits
- `feat(core): loom.json manifest loader`
- `feat(mcp): expose validated workflows as blocking MCP tools`
- `feat(cli): loom mcp command with stdio and http transports`

## Out of scope
- Streaming/progress notifications during runs
- Auth on HTTP transport beyond deployment-doc mention
- Per-call workflow overrides or parameters beyond the input schema
- Any pi-specific handling; pi is documentation only
- Multi-project serving (one process, one manifest)
