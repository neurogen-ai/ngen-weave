# v0.1 implementation plan

## Context

Nothing is implemented yet. The repository holds only `plans/`; this is the first code. What exists before this feature is the product PRD (`../product/PRD.md`, authoritative, carries the decision log) and the v0.1 release requirements (`../releases/v0.1.md`). No design docs exist under `../design/` yet beyond its README; where this plan makes a technical choice the release doc left open (exact file formats), the choice is recorded here and should be lifted into a design doc when that doc gets written.

Files touched: everything. This plan creates the repo's entire source tree:

- `packages/ngen-weave-core/src/ngen_weave/` — core library
- `packages/ngen-weave-cli/src/ngen_weave_cli/` — CLI
- `examples/` — two canonical example packages
- root `pyproject.toml`, `ruff.toml`, `.forgejo/workflows/ci.yaml`

Depends on: `releases/v0.1.md` and `product/PRD.md` only.

Conventions all steps follow:

- Comments on classes and fields describe what they are and how they behave, never what was rejected or what they deliberately omit. Rejection rationale belongs in the PRD decision log, which future generations read; code sketches should read like finished code.
- Every source file opens with a semantic module docstring per ../README.md's conventions (≤20 lines: module purpose, then name plus achievement per public class/function); each step that creates a file writes it from the file's listed purpose, and steps that change a public surface update it.

- Python ≥3.12, uv workspace, pytest, ruff. Conventional commits, one commit per step unless stated.
- Tests live next to the code (`src/ngen_weave/**/test_*.py`) except end-to-end tests, which live in `packages/ngen-weave-core/tests/e2e/`.
- Every run of the full suite must pass before committing. Command: `uv run pytest`.
- Global out of scope for every step (v0.1 non-goals): parallel execution, scheduling, queues, HTTP serving, MCP, web UI, plugins beyond subclassing, Postgres, auth, artifact diffing/display/export, real AgentNode execution.

---

## Goals

1. Define workflows in Python with strict pydantic boundaries; composites wire their children through a LangGraph-style builder (`build()` over a narrow `GraphBuilder`), validated at import by a dry-run compile.
2. Execute them sequentially on LangGraph with SQLite checkpointing, human interrupts, and resumability from disk.
3. Emit provenance on every activation with no logging code in workflow authorship.
4. Discover workflows by explicit listing — package entry points plus the project manifest — with duplicate names failing loudly; configure runs through YAML.
5. Ship both canonical examples (code review, document drafting) passing end-to-end tests driven purely by YAML config.

## Success criteria

From `releases/v0.1.md`, verbatim in intent:

1. Both canonical examples run end to end from the CLI and pass e2e tests, configured through YAML without touching their source.
2. Killing the process mid-run and calling `ngen-weave resume <run-id>` completes the run correctly.
3. A two-level nested workflow runs with correct per-level cost attribution in provenance metadata and a resumable interrupt at depth 2.
4. Every activation produces provenance addressable by `(run_id, node_path)` with zero logging code written by the workflow author.
5. Declaring two workflows with the same name across any discovery sources makes `ngen-weave validate` fail, naming both sources.

## Abstractions and what they absorb

One sentence each; these are the load-bearing choices.

- **`Workflow` base class with class attributes** absorbs new node types: Worker/Control/Human/Agent are subclasses, and a future node kind touches only its own module. Identity is the fully-qualified class path, so plugin classes never collide with core or each other.
- **Compile-time model binding from the config's `models:` section** absorbs new model-routing policies (path patterns, per-run overrides) as refinements of the matching rule, never new propagation machinery.
- **Import-time dry-run compile as the validator** absorbs editor/UI needs later: the editor reads compiled topology (`get_graph()`) from the same dry-run pass the import check uses, without executing any node.
- **`RunStore` as the sole writer of `run.json`** absorbs format changes (Postgres at v0.6, PROV-JSON export at v0.4): every read and write goes through one class.
- **`CompletionProvider` protocol** absorbs new model backends; adapters translate, nothing else imports LiteLLM.
- **`Engine.compile(wf) -> CompiledGraph` separated from `Engine.run/resume`** absorbs the v0.2 RunService and eventual Argo compilation, which consume compiled graphs rather than re-walking definitions.
- **Supervision metadata computed by the engine per scope** absorbs v0.2 observers and budgets: they evaluate predicates over records the engine already emits, so adding them touches only the scheduler's transition boundary, never nodes or workflow authorship.
- **Slot generation from `state_type` leaves** absorbs schema evolution in review artifacts; changing a human's state model changes the artifact automatically, while `output_type` stays free to diverge via the programmatic transformation.

### Step 3 — Workflow base classes, GraphBuilder, dry-run validation

`packages/ngen-weave-core/src/ngen_weave/workflow.py`. This is the central module; get the shapes exactly as below.

Node kind is a property of the subclass, never a stored tag. A workflow whose `build()` wires no nodes is a leaf and must define `run()`; one that wires children is a composite and must not override `run()`. Worker/Human/Control/Agent are leaf specializations shipped here (thin bodies; full behavior in later steps).

```python
class Workflow:
    # Identity is the fully-qualified class path (module + __qualname__), e.g.
    # "examples.code_review.workflows.CodeReview". Module paths disambiguate
    # same-named classes across plugins; UIs tidy the path into display labels
    # without round-tripping it back.
    description: ClassVar[str] = ""             # machine-facing: the MCP tool description (mandatory for MCP exposure at v0.2)
    human_description: ClassVar[str] = ""        # person-facing: shown by `ngen-weave workflows` list output and in the web UI
    input_type: ClassVar[type[BaseModel]]    # required
    output_type: ClassVar[type[BaseModel]]   # required
    prompt: ClassVar[str | None] = None      # worker template; override prompt(self, input) method instead for logic
    artifacts: ClassVar[Sequence[str]] = ()  # names of output_type fields persisted as artifacts
    # Supervision (observers) arrives in v0.2, built into the scheduler; no
    # author-facing observer surface exists in v0.1.
    # Model assignment lives in the run config's `models:` section (see Step 5):
    # every model-calling node runs on defaultVariant until configured there.

    def run(self, input: BaseModel, ctx: RunContext) -> BaseModel:
        raise NotImplementedError            # leaves only

    def build(self, g: "GraphBuilder") -> None:
        ...                                  # composites only; leaf default wires self as a single node
```

`RunContext` (same module, minimal):

```python
@dataclass
class RunContext:
    run_id: str
    node_path: str
    emit: Callable[[str, dict], None]   # (kind, payload); engine supplies provenance sink
    provider: CompletionProvider        # defined in Step 6; Step 3 declares the attribute, importing lazily is acceptable until then
```

To avoid a circular import, declare `provider`'s type via `TYPE_CHECKING`; the protocol lands in Step 6 unchanged.

**GraphBuilder** is the only thing `build()` receives. It accepts Workflow objects and resolves their identity — the fully-qualified class path (`cls.__module__ + "." + cls.__qualname__`) — itself; authors never type an identifier string:

```python
START = "__start__"   # maps to langgraph START
END = "__end__"       # maps to langgraph END

class GraphBuilder(Protocol):
    def add_node(self, node: Workflow) -> None
    def add_edge(self, src: Workflow | Literal[START], dst: Workflow | Literal[END], *,
                 into: str | None = None) -> None
    def add_conditional_edges(self, src: Workflow, router: Callable[[dict], str],
                              branches: Mapping[str, Workflow | Literal[END]]) -> None
```

`into` names the destination field for named-slot fan-in (Step 7's input assembly); it is the protocol's only fan-in surface.

Underneath it delegates to an ordinary LangGraph `StateGraph`, so everything LangGraph supports for wiring is available as-is. The engine implements the protocol twice per validation pass: once against a recording sink, once against the real StateGraph. Production compiles through the real one only.

Contract: **build() wires, it does not compute.** It must be deterministic and side-effect-free apart from builder calls, and must never execute nodes. Useful errors, not policing of bodies — but two mechanical checks fire at import time (`__init_subclass__`), so a broken definition raises before any run:

1. **Dry-run compile**: `build()` runs against a recording sink, then against a throwaway StateGraph. Structural problems raise `ConfigError` naming the class path: no edge from START or more than one (entry must be unique), unreachable node, unknown child reference, conditional branch target missing from the branch map. Nodes never execute during a dry run.
2. **Determinism check**: the recorded op sequences from both builds must be identical; divergence means `build()` is nondeterministic or stateful → `ConfigError`.

Validation beyond wiring (`ConfigError`, same import-time pass; the whole pass is exported as `validate_structure(cls) -> None` so later versions and tooling have one entry point to call):

1. `input_type`/`output_type` present and are `BaseModel` subclasses; the class path's last segment matches `[A-Za-z_][A-Za-z0-9_]*` (an ordinary Python class name already does).
1b. Model bindings are not a workflow concern — nothing to validate here beyond what Step 5's config loader owns (`models:` keys resolve to Workflow classes; values are variant names known to `models.json`).
2. Leaf (no nodes wired) must define `run` concretely; composite (nodes wired) must not.
3. Exactly one child receives the START edge; END is reachable.
3b. Fan-in legality: a target with multiple incoming parents must fit exactly one declared form. Named slots — every required `input_type` field covered by exactly one `into` edge, no duplicate slots, each source `output_type` validating against the targeted field's type; a plain untargeted edge into a multi-parent node is an error. Collected — `input_type` contains exactly one `list[<model>]` field (zero or two is an error naming the fields) and the static parent count lies within that field's `min_length`/`max_length`. Human nodes accept at most one parent regardless of form.
4. Boundary agreement between composite and entry/terminal children is checked only when trivially decidable (exact model match); deeper checks happen at runtime as ordinary port validation.
5. Control nodes: `output_type` contains a required `bool` field named `pass` (Step 7 covers how routers read it).
6. `prompt` placeholders on a worker reference fields existing on `input_type` (dotted paths allowed).
7. `artifacts` names exist on `output_type`.

(Observer-declaration validation is gone with observers themselves; supervision validation gets specified when the v0.2 scheduler work is planned.)

Subclasses shipped now (thin):

```python
class Worker(Workflow):    # requires prompt
class Control(Workflow):   # decide() override or model-mode boolean in output_type.pass
class Human(Workflow):     # state_type, verdict_field; Step 9
class AgentNode(Workflow): # declared seam, mocked executor (Step 11)
```

Routing out of control and human nodes is declared inside `build()` with `add_conditional_edges`, the router reading the node's validated verdict field from state. There is no separate branch-label vocabulary; the branch map keys *are* the possible values. A router returning a value absent from its map is a runtime `DataError` naming the node's class path and value.

**Model binding (resolved at compile time, frozen per node).** Model assignments live entirely in the run config's `models:` section — never in class attributes, and only canonical fully-qualified class paths as keys (no shorthands; validity must never depend on which plugins are installed). Keys match concrete class paths exactly; inheritance plays no role. Keying a composite assigns every model-calling leaf in its subtree however deep; keying a leaf binds it directly and overrides enclosing scopes:

```yaml
models:
  "examples.doc_draft.workflows.DocDraft": haiku                 # every model call in this workflow
  "examples.doc_draft.workflows.InnerReview": sonnet              # ...except this subtree's, however deep
  "examples.code_review.workflows.Gate": sonnet                   # one specific leaf anywhere
```

Every model-calling leaf resolves its variant before any run starts by one flat lookup:

1. its own exact class path if bound,
2. otherwise the innermost enclosing composite with a binding,
3. `defaultVariant` from `models.json`.

No MRO walk, no specificity tie-breaks: two classes related by inheritance never compete for a binding. Having the same function run on a different model means binding that leaf directly or shipping an explicit class copy with its own path. The engine resolves during `Engine.compile(wf, models)`, stores the chosen variant on the compiled node, and records it in every `model_call` provenance payload — so resumed runs resolve identically (the checkpointed record, not a re-walk, is authoritative after resume) and supervision sees which variant actually ran.

Two descriptions, two audiences: `description` is what machines read (MCP tool registration chooses tools by it), `human_description` is what people read (CLI workflow listing and the web UI). Neither is validated for prose quality; only MCP exposure makes `description` mandatory.

Tests: every validation rule exercised with failing definitions; determinism violation via a module-level counter mutated in `build()`; two same-short-named classes in different modules coexisting while identical class paths fail registration; binding resolution (own-key beats innermost scope beats default) against a three-level tree; the canonical `code_review` shape from `releases/v0.1.md` compiling cleanly through `build()`.

Absorbs: future node types (subclass); the v0.4 editor, which reads compiled topology via `get_graph()` after the same dry-run compile instead of class attributes.

Out of scope: any execution, LangGraph import at definition time beyond the dry run's throwaway graph, checkpointing, prompt rendering.

Verify: `uv run pytest src/ngen_weave/test_workflow.py`.

Commit: `feat(core): workflow base classes, GraphBuilder protocol, import-time dry-run validation`

### Step 4 — Discovery and registration

`packages/ngen-weave-core/src/ngen_weave/registry.py`, `discovery.py`.

The registry is populated only by discovery; no class registers itself by existing.

In-process registry (`registry.py`): a module-level dict keyed by fully-qualified class path — `f"{cls.__module__}.{cls.__qualname__}"` — with `register(cls)` (duplicate path → `ConfigError` naming both sources), `get(path) -> type[Workflow]` raising `ConfigError(f"unknown workflow: {path}")`, `all() -> dict`. Because the key derives mechanically from the class, plugins shipping same-named classes coexist; genuine duplicates mean the same class registered twice through overlapping discovery sources.

```python
# discovery.py
def discover(modules: Sequence[str], *, strict: bool = True) -> dict[str, type[Workflow]]
    # imports each module in order; after each import, every Workflow subclass
    # whose __module__ == that module registers under its fully-qualified class
    # path. An import that raises is collected and re-raised as ConfigError when
    # strict=True. Duplicate paths raise in both modes (overlapping sources).
```

Two source kinds feed `discover`:

1. **Package entry points**: distributions list workflow modules under the `ngen-weave.workflows` entry-point group, one module path string per entry, declared in `pyproject.toml`. Read via `importlib.metadata`; because pip resolves entry points from the same wheel as the code, the pointer cannot go stale relative to the classes. No build-time manifest exists.

2. **Project manifest** (formalized in v0.2 as `ngen-weave.json`, consumed here as a plain module list): explicitly named modules for local development.

Consumers merge results into one map; the merged map is the only namespace anything reads (config, CLI, server, MCP). Nothing touches the registry dict directly except through it.

Tests: entry-point-declared modules register their subclasses; a project module list does too; duplicate class paths raise naming both sources; unknown-path lookup error; a broken module raises in strict mode; two classes sharing a short name but differing modules both register.

Absorbs: tolerant discovery at v0.3 (`DiscoveryResult` wraps this function), plugin packs at v0.5 (more entry points, same group).

Out of scope: directory globbing or runtime scanning of unlisted code; watching files; caching.

Verify: `uv run pytest src/ngen_weave/test_registry.py src/ngen_weave/test_discovery.py`.

Commit: `feat(core): explicit-listing discovery with auto-registration`

### Step 5 — Configuration layer

`packages/ngen-weave-core/src/ngen_weave/config.py`.

YAML is primary, JSON accepted identically (detect by extension; both parse to the same dict).

```python
@dataclass(frozen=True)
class RunSettings:
    checkpointer: Literal["sqlite", "memory"] = "sqlite"
    db_path: Path = Path(".ngen-weave/checkpoints.db")
    max_retries: int = 3
    retry_backoff_ms: int = 1000

@dataclass(frozen=True)
class ResolvedConfig:
    workflow: type[Workflow]
    params: dict            # kwargs passed to the workflow factory (data-only tunables)
    models: dict            # class-path -> variant-name bindings; source for Engine.compile
    models_file: Path       # resolved against config file dir, default ./models.json
    run: RunSettings

def load_config(path: Path, registry: dict[str, type[Workflow]]) -> ResolvedConfig
```

Schema:

```yaml
workflow: examples.code_review.workflows.CodeReview   # registered class path; unknown path is ConfigError
params: {}                   # passed to the workflow factory (data-only tunables)
models:                      # class-path -> variant bindings; composite keys scope to their subtree
  "ngen_weave.workflow.Control": haiku
models_file: models.json
run:
  checkpointer: sqlite
  max_retries: 3
```

Validation errors are `ConfigError` listing the offending key. Unknown keys rejected (typo protection). `models:` validation: each key imports to a registered-or-importable Workflow subclass, each value is a variant name known to `models.json`; no shorthand forms are accepted — canonical class paths only, so config validity never depends on installed plugins. Params are data-only tunables passed to the workflow factory (numeric thresholds and similar); they never carry code-bearing members, and the factory validates them against the class's declared tunables rather than silently ignoring unknown names.

This is deliberately thin. The standing constraint from the release doc: v0.4 widens this same format to cover every serializable field (data only); nothing valid today may ever become invalid. Keep the parsed shape a plain dataclass so widening adds fields, never renames them.

Tests: yaml and json equivalence, unknown workflow, unknown key, defaults, path resolution relative to the config file.

Out of scope: per-run CLI overrides of the `models:` section, multi-workflow configs, environment interpolation.

Verify: `uv run pytest src/ngen_weave/test_config.py`.

Commit: `feat(core): thin YAML/JSON run configuration`

class ModelRegistry:

### Step 7 — Engine part 1: compile, run flat graphs, run files, retries

Two modules under `packages/ngen-weave-core/src/ngen_weave/engine/`.

`state.py`:

```python
RunStatus = Literal["running", "waiting_human", "paused", "completed", "failed"]

@dataclass
class RunFile:
    format: int                    # 1
    run_id: str
    workflow: str
    status: RunStatus
    input: dict
    output: dict | None
    error: {"type": str, "message": str} | None
    records: list[ProvenanceRecord]   # full stream, oldest first

@dataclass
class RunResult:
    run_id: str
    status: RunStatus
    output: BaseModel | None
    waiting: dict | None           # {"node_path", "artifact"} when waiting_human
```

`store.py`:

```python
class RunStore:
    def __init__(self, runs_dir: Path)   # .ngen-weave/runs
    def create(self, workflow_name: str, input_dump: dict) -> str      # uuid4 run id, writes initial file
    def load(self, run_id: str) -> RunFile
    def save(self, run_file: RunFile) -> None                          # atomic: temp file + os.replace
    def append(self, run_id: str, record: ProvenanceRecord) -> None    # load-modify-save
    def list(self) -> list[RunFile]
```

Every mutation goes through `RunStore`; the file is always valid JSON and always sufficient to re-run, per the release doc. `RunStore` is the single writer, so the v0.6 Postgres swap and the v0.4 export both touch one class.

`runner.py`:

```python
class Engine:
    def __init__(self, provider: CompletionProvider, store: RunStore,
                 checkpointer: Literal["sqlite", "memory"], db_path: Path,
                 max_retries: int = 3, retry_backoff_ms: int = 1000)

    def compile(self, wf: type[Workflow], models: dict) -> CompiledGraph   # langgraph.StateGraph, cached per (class, models)
    async def run(self, wf: type[Workflow], input: BaseModel) -> RunResult
    async def resume(self, run_id: str, payload: dict | None = None) -> RunResult
```

Compilation rules (LangGraph `StateGraph`, state is a dict keyed by child name holding that child's validated-output dump; composites produce their topology by running their `build()` against the real `GraphBuilder`, which delegates to this StateGraph):

- Child workflow -> node function. Node function: build `RunContext(run_id, node_path=join(root_class_path, child_class_path), emit, provider)`; assemble the child's input per its declared fan-in form — single parent: the parent's validated-output dump as-is; named slots: `{field: source_dump}` for each `into` edge (coverage was proven at compile time); collected: all parent dumps appended to the declared list field — validate against `child.input_type` (`DataError` on failure); call `child.run(validated_input, ctx)` for leaves or delegate to the child's compiled subgraph; validate results against `child.output_type` (`DataError` with pydantic errors on failure), store dump in state, emit `node_activation` provenance with `{"status": "ok"|"invalid"}`.
- Routing between nodes is whatever the author declared in `build()` — plain `add_edge` plus `add_conditional_edges` whose routers read validated output fields from state. A control whose programmatic `decide(self, input) -> bool` is overridden uses that; otherwise its `prompt` is rendered and sent to the provider, the model reply parsed as the boolean (non-parseable reply is `DataError`). Either way the boolean lands in the validated `pass` field, so routers, provenance, and the per-scope metadata record read the same value. Every model call uses the variant resolved at compile time from the run config's `models:` bindings (Steps 3/5); the resolved variant lands in the `model_call` provenance payload. Failed control logic is a `DataError` and flows through the graph, never retried, per the error taxonomy. A router returning a value absent from its branch map is a `DataError` naming the node and value.
- Worker prompts: render `cls.prompt` against validated input fields (dotted paths via `input.model_dump()` traversal), send as one user message through `provider.complete(variant=resolved_variant)`, parse reply text into `output_type.model_validate_json` when the schema looks object-shaped, else `model_validate(text)`. Emit a `model_call` provenance record with `{"variant", "tokens_total", "cost_usd"}`.
- Retry policy: only `InfraError` retries, `max_retries` attempts, exponential backoff from `retry_backoff_ms` (1000, 2000, 4000...). Each retry emits `node_activation` with `{"status": "retry", "attempt": n}`. Exhausted retries fail the run with status `failed` and the error recorded in the run file. `ConfigError` and `DataError` never retry.
- Checkpointing: LangGraph `SqliteSaver` (or `MemorySaver`) threaded through `compile` and `run`; the thread id is the run id. Composites are subgraphs; this step compiles only single-level graphs, nesting lands in Step 8, human interrupts in Step 9.

Provenance emission is unconditional and lives entirely in the engine's `emit`; workflow authors write zero logging code, satisfying success criterion 4 mechanically.

Tests: three-node linear worker chain with `FakeProvider`; control pass and fail routing; model-mode control; invalid worker output produces `DataError`, failed status, no retry; infra failure retries three times with observed backoff then fails; run file after each transition parses as JSON and contains the full record stream; `resume` on a completed run is a no-op returning the stored output; named-slot fan-in (two workers into a synthesizer via `into=`) and collected fan-in (three parents into a reducer with `min_length=2`) assembling inputs correctly.

Out of scope: nesting/subgraphs (Step 8), interrupts and Human execution (Step 9), artifact writes (Step 11).

Verify: `uv run pytest src/ngen_weave/engine/test_engine.py`.

Commits: `feat(engine): langgraph compilation and sequential execution`, `feat(engine): run store with atomic run files`, `feat(engine): infra retry policy` (may be one combined commit if cleaner; keep the three concerns separable in history if split).

### Step 8 — Engine part 2: recursive composition and cost attribution

Extend `compile` in `runner.py`: a composite child compiles to a subgraph whose state is scoped under the child's name, so parent state remains `{child_name: dump}` uniformly at every level. Nothing about the parent's compilation changes when a leaf becomes a composite; that is the point of the recursion.

Rules:

- `node_path` accumulates: activations inside `Inner` of root `CodeReview` emit paths like `"...CodeReview.Inner.Draft"` (Step 2's convention).
- Cost attribution: when a composite finishes, the engine computes a `RunMetadata` for the subgraph (summing token/cost/iteration fields from the child's own records plus its descendants') and emits a `node_activation` record on the composite's path with `payload["metadata"]` as that six-field object. v0.2 supervision reads exactly this; in v0.1 it is provenance like any other record. Attribution is therefore correct at any depth without special-casing levels.
- Interrupts and failures propagate upward untouched; the engine catches at the top level only.

Fan-in compiles to ordinary state plumbing: named-slot targets read their sources' state keys directly; collected fan-in appends the parents' state entries to the list field before validation. Both forms were validated structurally at import time, so nothing here can fail on wiring at runtime — a runtime failure means data, not structure. There are no merge-overwrite semantics anywhere in the engine; if two edges could deliver the same data to the same place, that is a compile error, never a precedence rule.

Tests (`test_nesting.py`, matching success criterion 3): a two-level nested workflow where the inner composite contains workers with known fake token counts; assert the parent-visible `node_activation.metadata.cost_usd` equals the sum; kill simulation: drop the process state by constructing a fresh `Engine` from the same sqlite db and run file and completing via `resume`; assert final output and record stream integrity.

Absorbs: deeper nesting (rules are level-independent), Argo compilation later (compiles from the same definitions recursively).

Out of scope: parallel branches within a composite, cross-composite state sharing beyond what a node's incoming edges deliver, depth limits.

Verify: `uv run pytest src/ngen_weave/engine/test_nesting.py`.

Commit: `feat(engine): recursive composition, fan-in, cost attribution`
