# v0.8 implementation plan

## Context

v0.6 (per `implementation/v0.6.md`) put Postgres behind the async store seams and left file mode untouched; v0.7 retired the langgraph-server adapter. Identity does not exist yet: the server implicitly trusts whoever can reach it, and the collaboration features that need principals are untestable without one.

v0.8 adds the collaboration slice pulled from the pre-split v0.6 (requirements in `releases/v0.8.md`): token auth, project roles, multi-reviewer human nodes, run-level roles, tickets, and `import-project`. Per the release doc these ship plugin-first where the v0.5 seams carry them; token auth itself stays core (infrastructure every consumer shares). Each step below notes its in/out-of-tree decision point; anything requiring a core change beyond the named amendments is a bug report on the extension seams, per the PRD.

Files touched:

- `packages/ngen-weave-core/src/ngen_weave/auth.py` (**new**): principals, token hashing, role matrix
- `packages/ngen-weave-core/src/ngen_weave/db/importer.py` (**new**), plus migrations for `users`/`project_roles`/`tickets`
- `packages/ngen-weave-core/src/ngen_weave/human.py`, `tickets.py`: multi-review accumulation, ticket spec
- `packages/ngen-weave-server/src/ngen_weave_server/app.py`, `api.py`, `service.py`, `client.py`: auth dependency, principal plumbing
- `packages/ngen-weave-cli/src/ngen_weave_cli/context.py`, `main.py`: backend selection, `import-project`, `user add/list`
- `packages/ngen-weave-mcp/src/ngen_weave_mcp/`: bearer-token support on the HTTP transport
- `../ngen-weave-web/`: login/token entry, 401/403 handling (small)

Depends on: `releases/v0.8.md`, `product/PRD.md` (wins on conflict), and module shapes from `implementation/v0.1.md` through `implementation/v0.7.md`.

Conventions inherited from `implementation/v0.1.md`: Python ≥3.12, uv workspace, pytest, ruff, conventional commits, full suite green before committing, tests next to code except e2e under `tests/e2e/`, no network (live-marked exceptions only). Web repo conventions per `implementation/v0.3.md` Step 7.

Global out of scope for every step: multi-tenancy beyond projects-per-user, SSO/OIDC federation, live collaborative editing, distributed execution, API semver (that is 1.0).

## Goals

1. Every mutating API and MCP request requires a bearer token issued per user; unauthenticated requests get 401 before any handler logic runs.
2. Project-level roles (owner, reviewer, observer) gate the service boundary: owners launch, cancel, edit workflows, install plugins, and manage roles; reviewers additionally answer reviews; observers read.
3. A HumanNode may require N distinct reviewers before resuming; submissions accumulate and are attributed per reviewer.
4. Workflow-declared tickets attach to runs on human-wait and close under role checks through the API.
5. `ngen-weave import-project <dir>` loads a pre-v0.6 project directory into Postgres so its runs, provenance, and artifacts are fully addressable afterward.

## Success criteria

From `releases/v0.8.md`, verbatim in intent:

1. An unauthenticated request to any mutating endpoint is rejected; a reviewer-role token can answer reviews but cannot launch workflows.
2. Two reviewers must both approve before a multi-review HumanNode releases; roles prevent a non-reviewer from submitting.
3. Tickets create on human-wait via workflow declaration, close through the API under role checks, and land in provenance like any other record.
4. A pre-v0.6 project directory imports cleanly into Postgres: runs, provenance, artifacts all addressable after import, and export back to JSON matches the original file's semantics.

## Abstractions and what they absorb

One sentence each:

- **`Principal(name, role)` resolved at the HTTP boundary and passed as one value** absorbs SSO/OIDC later: federation swaps the resolver, not the enforcement points, which see only `Principal`.
- **One `require_role(principal, action)` matrix in `auth.py`, called nowhere else** absorbs new gated actions and role tweaks: the matrix is one function, extending v0.5's run-level pattern upward to projects.
- **Tokens stored only as sha256 hashes** absorbs rotation and revocation cheaply: issuance and verification are the only two functions that touch token material.
- **Reviewer accumulation in the run file's existing `waiting` dict** absorbs future participation rules (delegation, quorums by weight) without moving the resume path.
- **The importer reading only through public parsers and writing only through `Pg*` stores** absorbs future import sources (a reader function per source) and store-backend changes without stranding the command.

## Commit sequence

### Step 1: Token auth: principals, issuance, and the 401 wall

`packages/ngen-weave-core/src/ngen_weave/auth.py` (new), server `app.py`/`api.py`, MCP HTTP transport, CLI user commands. Roles arrive in Step 2; this step is identity and rejection only. Core (not plugin) per the release doc.

```python
# auth.py
Role = Literal["owner", "reviewer", "observer"]

@dataclass(frozen=True)
class Principal:
    name: str
    role: Role          # resolved from project_roles; Step 2 enforces it

def hash_token(token: str) -> str        # sha256 hex of the raw token
def new_token() -> str                   # "ngw_" + secrets.token_urlsafe(24)

class DbAuthResolver:
    """Resolves a bearer token to a Principal via the users + project_roles tables."""
    def __init__(self, sessionmaker: async_sessionmaker[AsyncSession]) -> None
    async def resolve(self, token: str | None) -> Principal | None   # None when missing/unknown
```

Issuance and storage rules: `ngen-weave user add <name> [--role owner|reviewer|observer]` (default `observer`) inserts the user and prints the raw token exactly once, writing only `hash_token(token)`; `ngen-weave user list` shows names and roles, never tokens. Both operate directly against the resolved database (management commands, not API calls). Duplicate name → `ConfigError`. Tables `users` (`name` PK, `token_hash` unique, `created_at`) and `project_roles` (`user_name` FK, `role`; one role per user in v0.8) arrive in migration `0002_auth`.

Server enforcement (`app.py`): one FastAPI dependency `current_principal` extracting `Authorization: Bearer <token>`, calling the resolver, raising `HTTPException(401)` on `None`. Applied to **every** route in `api.py`, reads included. Escape hatch, explicit and narrow: `create_app(..., auth_disabled: bool = False)`, also enabled by env `NGW_AUTH_DISABLED=1`, intended for tests, the local file-mode dev loop, and stdio MCP. When disabled the dependency returns `Principal(name="local", role="owner")`, which makes Step 2's matrix total instead of nullable.

Actor plumbing: the `X-Ngw-Actor` header (superseded mechanism) is still parsed only when auth is disabled; with auth on, a client-supplied actor header is ignored (forging identity was the hole being closed); mutating handlers receive `principal.name`.

MCP: the HTTP transport forwards its own `Authorization` configuration (`--token` flag or `NGW_TOKEN` env) and sits behind the same dependency; stdio mode keeps in-process `auth_disabled` semantics since it constructs its own `LocalRunService` locally.

Client: `HttpRunService` gains `token: str | None`, sent as the bearer header; CLI grows a global `--token` option (env `NGW_TOKEN` fallback) used whenever `--url` targets a remote server.

Tests: hashing determinism, `new_token` uniqueness/format, resolver hit/miss; `test_auth_api.py` drives `create_app`: no header → 401 on every route (parametrized over the route table, reads included), garbage token → 401, valid token → 200 with actor recorded as principal name, `auth_disabled` restores open access with actor `"local"`; `test_http_auth.py` covers the MCP HTTP transport.

Absorbs: OIDC/SSO later (replace `DbAuthResolver`; enforcement points keep consuming `Principal`), token rotation (issue new, rewrite hash; verification stateless).

Out of scope: role enforcement (Step 2), token expiry/TTL, rate limiting, HTTPS termination, password logins.

Verify: `uv run pytest src/ngen_weave/test_auth.py packages/ngen-weave-server/src/ngen_weave_server/ packages/ngen-weave-mcp/src/ngen_weave_mcp/ -m 'not live'`.

Commit: `feat(server,mcp,cli): bearer-token authentication on every request`

### Step 2: Project roles enforced at the boundary

`auth.py` (matrix), `service.py` (signature growth), local service, `api.py`, conformance suite. Plugin-first checkpoint: if v0.5's entry points allow mounting this enforcement without core edits, do that; the expected core touch is limited to the `RunService` signature change below, which is recorded here as an accepted amendment rather than discovered later.

The matrix, one function, called nowhere else:

```python
def require_role(principal: Principal, action: str, *, also: Sequence[str] = ()) -> None
    # raises PermissionError(NgWeaveError) naming principal/action unless:
    #   action == "read"                        -> any authenticated principal
    #   action in {"launch", "cancel", "note", "budget",
    #              "assign_role", "edit_workflow", "install_plugin"} -> owner
    #   action == "resume"                      -> owner or reviewer
    #   action in also                          -> those roles admitted additionally
```

Mapping onto surfaces, decided here:

- `RunService` protocol: every method's actor keyword becomes required `principal: Principal` (after Step 1 there is always a principal, real or `local`). Implementations updated together; `HttpRunService` sends nothing extra (identity travels by token). This is a core amendment, accepted here rather than discovered later.
- Enforcement points: launch/resume/cancel/note/budget/assign_role each call `require_role` before touching the store; workflow PUT (`edit_workflow`) and plugin/pack install routes (`install_plugin`) check in `api.py` before delegating. Reads call with `"read"`.
- Interaction with run-level grants: `resume` succeeds when the principal holds project-level owner/reviewer **or** appears in the run's `roles.reviewers` list (per-run grants from Step 4).
- Role management API: `PUT /api/users/{name}/role` (caller must be owner); `GET /api/users` lists names and roles. CLI wrappers: `ngen-weave role set/list`.
- Error mapping: `PermissionError` → `403 {"error": {"type": "forbidden", ...}}`; the auth-disabled `local` owner principal means local development flows never trip it.

Conformance suite extension: owner launches and cancels; reviewer resumes a waiting run and answers a review but launch/cancel/edit raise; observer reads everything and mutates nothing.

Web: api client sends the stored token on every request, treats 401 as session-invalid (clear token, show prompt), 403 as inline message; `/api/me` (`{"name", "role"}`) drives hiding non-owner controls.

Tests: exhaustive `require_role` truth table; conformance scenarios above; 403 shapes and role-management routes; CLI role smoke.

Absorbs: new gated actions (one row), richer role models post-1.2 (rows + the `Role` literal), workspaces (the key grows a dimension; signature unchanged).

Out of scope: multiple roles per user, per-workflow permissions, invitation flows, audit log beyond provenance.

Verify: `uv run pytest packages/ngen-weave-server/ src/ngen_weave/test_auth.py -m 'not live'`.

Commit: `feat(server,cli): project-level roles with one enforcement matrix`

### Step 3: Multi-human review

`human.py` plus engine resume-path edits. Plugin-first checkpoint: reviewers-required is expressible as a Human subclass registration if the engine exposes the waiting-transition hook; if the accumulation loop must live in core anyway, land it there and record the seam gap in the amendments section of this plan.

Contract:

```python
class Human(Workflow):
    reviewers_required: ClassVar[int] = 1     # new; >= 1 validated in validate_structure
```

Resume payload shape widens to `{"reviewer": str, "response": dict}`. Decisions:

- Each reviewer submits a complete `response`; the run resumes using the **last** submission's response. Requiring N distinct reviewers is a participation gate, not a merge algorithm.
- Submissions accumulate in the run file's `waiting` dict: `waiting["reviewers"]: {reviewer_name: response_dict}` in arrival order. When `len(waiting["reviewers"]) >= reviewers_required`, the engine validates the latest response with the existing completion validation, emits the usual `artifact_write` record (payload gains `"reviewers": [names...]` as an additive key), clears `waiting`, and continues the graph. Below the threshold the engine stays interrupted, emitting `node_activation {"status": "waiting_human", "awaiting_reviewers": remaining}` per submission.
- Duplicate submissions from the same reviewer replace their prior entry and do not advance the count.
- Back-compatibility: a payload lacking `"reviewer"` is accepted as reviewer `"local"`; with `reviewers_required == 1` every pre-v0.8 flow behaves identically, proven by the untouched review-parity tests passing unchanged. Bare-dict payloads (old shape) are detected by absence of both keys and treated as `{"reviewer": "local", "response": <dict>}`.
- The artifact YAML on disk gains a `reviewers:` section mirroring the run file; slot generation/prefill are untouched.
- The engine trusts its caller on identity; whether the claimed reviewer may submit is the Step 2 boundary check. The engine validates only distinctness and completeness.

Tests: `reviewers_required=2` holds the interrupt after one submission and releases after a second distinct reviewer; same-reviewer resubmission does not release; invalid second response rejects with field errors and keeps waiting; legacy payloads pass existing suites; artifact YAML shows both submissions; crash between submissions resumes correctly.

Out of scope: response merging/delegation, timeouts/escalation, reviewer-specific prompts.

Verify: `uv run pytest src/ngen_weave/test_human.py src/ngen_weave/engine/ packages/ngen-weave-server/tests/conformance/`.

Commit: `feat(core): multi-reviewer human nodes with accumulated submissions`

### Step 4: Run roles enforced at the RunService boundary

Roles extend the Step 2 project matrix down to individual runs. Plugin-first checkpoint: same test as Step 2 — if this mounts through published interfaces without core edits, prefer that.

Protocol: every mutating method carries `principal: Principal` (Step 2). Run file gains `roles: {"owner", "reviewers": [], "observers": []}`, written at launch; new protocol method on both implementations:

```python
async def assign_role(self, run_id: str, role: Literal["reviewer", "observer"], who: str, *, principal: Principal) -> RunFile
```

Rules fixed here: launch assigns the launching principal as owner; `cancel`, `attach_note`, budget override, and `assign_role` require the run owner; `resume` (including answering reviews) requires owner or listed reviewer **in addition to** passing the Step 2 project check; reads require nobody. One helper extends `require_role` with the run-level dimension; called nowhere else.

Definition of done detail: conformance suite gains role scenarios run against both implementations — non-reviewer resume raises, reviewer resume succeeds, owner cancel succeeds, double-assign idempotent.

Absorbs: new gated actions (rows), workspace-level roles post-1.2.

Out of scope: authentication beyond Step 1, audit log beyond provenance.

Verify: `uv run pytest packages/ngen-weave-server/ src/ngen_weave/test_service_types.py`.

### Step 5: Tickets

`tickets.py`, one engine hook, three routes. Plugin-first checkpoint: ticket creation on human-wait is exactly the kind of thing the notification framework proved (event consumption plus side effects); if a plugin can register a waiting-transition hook through published interfaces, the reference implementation ships out of tree like email/text did.

```python
TicketStatus = Literal["open", "closed"]

@dataclass(frozen=True)
class Ticket:
    id: str             # "t-1", "t-2", ... incrementing per run
    title: str
    role: str           # "owner" | "reviewer" | "observer"
    status: TicketStatus
    created_by: str     # node_path that created it, or "api"
    closed_by: str | None = None
    # backing table `tickets` (migration 0003_tickets): run_id FK, ticket_id, title,
    # role, status, created_by, closed_by; PK (run_id, ticket_id); Pg* store variant,
    # file-mode JSON sidecar kept for local parity

@dataclass(frozen=True)
class TicketSpec:
    title: str          # template; "{field}" placeholders render over the human node's context dump
    role: str = "reviewer"
```

Creation trigger: `Workflow` gains `ticket_on_wait: ClassVar[TicketSpec | None] = None`; on a human-wait transition the engine (or the plugin hook) appends a ticket and emits `ticket_created` provenance. Routes:

```
GET  /api/runs/{run_id}/tickets                                  -> {"tickets": [...]}
POST /api/runs/{run_id}/tickets        body {"title": str, "role": str}   -> Ticket; owner only
POST /api/runs/{run_id}/tickets/{tid}/close                          -> Ticket; owner or holder of the ticket's role
```

Role checks call the Step 4 helper with `also=(ticket.role,)`; violations map to 403. Unknown run/ticket → 404, bad role → 400. Web UI out of scope; the API and provenance are the deliverable.

Tests: append increments ids and persists; close idempotent; human node with a spec produces exactly one ticket plus `ticket_created` record, rerun of the same node path does not duplicate; routes cover 200/403/404/400; template rendering with a missing placeholder leaves it verbatim.

Out of scope: assignment to individuals, priorities, due dates, web screens, external trackers.

Verify: `uv run pytest src/ngen_weave/test_tickets.py packages/ngen-weave-server/src/ngen_weave_server/test_run_api.py src/ngen_weave/engine/test_engine.py`.

Commit: `feat(core,server): run-attached tickets with role-gated lifecycle`

### Step 6: `ngen-weave import-project`

`db/importer.py` (new), one CLI command.

```
ngen-weave import-project <dir> [--database URL] [--projects-root PATH]
```

Behavior, fixed here:

- `<dir>` is a pre-v0.6 (or current file-mode) project root containing `.ngen-weave/runs/*/run.json`, `.ngen-weave/definitions/`, and `projects/` artifact trees. Target is the resolved database (`--database` overrides env/config; refusing to guess, the command errors when no URL resolves).
- Runs: each `run.json` parsed with `load_run_json` (v0.6 Step 5), inserted preserving the original `run_id` (colliding id → `ConfigError("run already imported: {id}")`, making re-runs safe and idempotent-by-abort).
- Records: inserted with their original ordinals from stream order.
- Definitions: loaded through the standard parser and saved into the `definitions` table (validation applies unchanged; a broken file aborts with the validator's message listing the file).
- Artifact manifests: each project's version manifests read and inserted into `artifact_versions`; blobs copied (or left in place when `--projects-root` points at the existing tree) so hashes continue to address content on disk.
- Tickets/notify sidecars: imported when present, silently skipped otherwise.
- Output: counts per category printed; exit 0 only if everything landed.

The importer reads only through `load_run_json` and standard parsers, writes only through the `Pg*` stores, no direct SQL, so a future backend change cannot strand it.

Tests: checked-in fixture pre-v0.6 directory imports fully; every imported run loads equal from `PgRunStore`; export equals original bytes (criterion 4, byte-exact); re-import aborts naming the colliding run; broken definition aborts before partial commit (runs last so definitions validate first); artifact sha256 resolves to readable bytes after import.

Absorbs: future import sources (a reader function per source feeding the same writes) and v0.5→current upgrades of existing file-mode projects (same command).

Out of scope: live dual-writing during transitions, importing *from* Postgres to files (use `export-run`), merging partially-imported directories beyond the abort rule.

Verify: `uv run pytest src/ngen_weave/db/test_import.py packages/ngen-weave-cli/tests/test_cli_import.py && uv run ngen-weave import-project --help`.

Commit: `feat(cli): import-project migrates pre-v0.6 directories into postgres`

## Definition of done

All four success criteria demonstrably pass: 1 → parametrized 401 wall over the whole route table plus a reviewer token answering a review while a launch attempt draws 403; 2 → two-distinct-principal release on a multi-review HumanNode with a non-reviewer submit rejected at the boundary; 3 → declared ticket fires, closes under role checks, lands in provenance; 4 → checked-in pre-v0.6 fixture imports with run equality, byte-identical re-export, and hash-addressable artifacts. Backend `uv run ruff check .` clean, full non-live suite green. Web lint/unit/build green. File mode remains functional locally: the pre-v0.6 suites passing without a database or tokens is the standing proof.
