# v0.2 implementation plan

## Context

v0.1 (per `implementation/v0.1.md`) ships the `ngen-weave` distribution with two workspace packages, `ngen-weave-core` and `ngen-weave-cli`: `Workflow` classes with structural validation, entry-point manifest registration, thin YAML config, a LangGraph-backed `Engine` with `compile/run/resume`, an atomic-file `RunStore` writing `.ngen-weave/runs/<run-id>/run.json`, human review artifacts resumable via `Engine.resume(run_id, payload)`, per-scope supervision metadata in provenance (no author-facing observers yet), content-addressed artifacts, and a mocked `AgentNode` seam. Two canonical examples pass e2e.

v0.2 makes runs reachable and observable: workflows exposed as MCP tools, runs managed over a long-lived process behind a `RunService` protocol with one owned FastAPI implementation, budget enforcement, and a stub-real AgentNode harness. No UI, no new node vocabulary.

Files touched:

- `packages/ngen-weave-core/src/ngen_weave/` — service protocol types, budget enforcement in the engine, agent harness modules
- `packages/ngen-weave-cli/` — `runs` and `cancel` commands
- `packages/ngen-weave-server/` — **new** package: FastAPI `RunService` implementation
- `packages/ngen-weave-mcp/` — **new** package: MCP server exposing workflows as tools

Depends on: `releases/v0.2.md` (requirements), `product/PRD.md` (decision log, wins on conflict), and the module shapes defined in `implementation/v0.1.md` (this plan references those signatures without restating them). The former open design questions tagged v0.2 in `../design/README.md` (langgraph-server identity mapping, packaging friction) dissolved when the dual-implementation serving plan was dropped for a single owned FastAPI service; see the PRD decision log.

Conventions inherited from `implementation/v0.1.md` and applied to every step below: Python ≥3.12, uv workspace, pytest, ruff, conventional commits, one commit per step unless stated, full suite green before committing (`uv run pytest`), tests next to code except e2e under `tests/e2e/`, no network in tests (`FakeProvider`, extended with `FakeTools` in Step 10).

Global out of scope for every step (v0.2 non-goals per `releases/v0.2.md`): web UI of any kind, parallel execution within a workflow, plugins or third-party node registration, artifact diffing/display/export, collaboration and notifications, any REST API beyond what the serving path itself provides, MCP loopback (ngen-weave exposing itself as the agent's tool source), claims of good agentic behavior.

---

## Goals

1. Every caller reaches runs through one `RunService` protocol with one implementation: our FastAPI service. Nothing outside it imports LangGraph's serving layer.
2. Workflows become MCP tools driven by a project-root `ngen-weave.json`, callable from any MCP client over stdio or HTTP, validated loudly at startup.
3. Runs carry enforced budgets that pause instead of kill, and `list_runs`/`cancel` surface run state to the CLI.
4. A real model drives AgentNode through `CompletionProvider` and a tool registry while `PermissionSet` constraints are enforced engine-side, not by prompting.
5. Remote JSON review submission resumes a paused run identically to the local YAML path, proven by one shared test.

## Success criteria

From `releases/v0.2.md`, verbatim in intent:

1. A workflow called through MCP from an external client runs to completion or human pause, with correct blocking semantics.
2. Remote JSON review submission resumes a paused run identically to the local file path (same e2e test, both transports).
3. `run.json` replays a completed run faithfully: every transition, supervision firing, and usage record present exactly once, ordered.
4. An AgentNode with a deny-listed tool attempts the denied call mid-run; the engine blocks it, records it, and routes per its configured policy.
5. A run exceeding its cost budget pauses instead of dying; resuming after raising the cap completes it.
6. The conformance suite passes green against the FastAPI implementation; nothing outside the protocol imports LangGraph's serving layer.

## Abstractions and what they absorb

One sentence each; these are the load-bearing choices.

- **`RunService` protocol living in core** absorbs new callers (v0.4 UI, future plugins): they program against the protocol, and swapping or adding backends touches only the backend's own package.
- **A shared conformance suite parametrized over implementation factories** absorbs backend changes: any behavioral change to run semantics is asserted once and every implementation must satisfy it.
- **Budget checking inside the engine's transition hook** absorbs new cap dimensions (steps today, tokens or wall-clock later): the check reads accumulated provenance, so a new dimension is one more sum in one function.
- **`ToolRegistry` of `ToolSpec` entries plus an engine-side `PermissionGate` wrapper** absorbs new agent tool sources (MCP loopback at v0.5) and new permission policies: tools register themselves, the gate wraps whatever registry it is given.
- **The MCP project manifest naming importable modules** absorbs new example packs: adding a workflow to the tool surface is one line in `ngen-weave.json`, no server code changes.
- **`RunStore.list()` extended with filter projection** absorbs richer queries (v0.4 screens) without changing storage; filters stay plain dataclasses, never query strings.

### Step 2 — RunService protocol and run-summary types

`packages/ngen-weave-core/src/ngen_weave/service.py`. This module defines the seam both backends implement; the exact shapes below are the contract for Steps 3–6.

```python
@dataclass(frozen=True)
class RunHandle:
    run_id: str
    status: RunStatus            # from engine/state.py

@dataclass(frozen=True)
class RunSummary:
    run_id: str
    workflow: str
    status: RunStatus
    started_at: str              # UTC ISO-8601, from the run file's first record ts
    cost_usd: float              # sum of model_call payloads
    waiting_on_human: bool       # status == "waiting_human"

@dataclass(frozen=True)
class RunFilters:
    workflow: str | None = None
    status: RunStatus | None = None

class RunService(Protocol):
    async def launch(self, workflow: str, input: BaseModel) -> RunHandle
    async def resume(self, run_id: str, payload: dict | None = None) -> RunHandle
    async def status(self, run_id: str) -> RunFile            # full run file, from engine/store.py
    async def cancel(self, run_id: str) -> None               # terminal status "cancelled"; see below
    async def list_runs(self, filters: RunFilters | None = None) -> list[RunSummary]
    async def attach_note(self, run_id: str, note: str) -> None
```

Decisions made here so no later step weighs them:

- `launch` takes the registered workflow *name* (str), not the class, because remote callers cannot hold class objects. Implementations resolve names through the same registry the CLI uses.
- `status` returns the whole `RunFile` rather than a trimmed view: the release doc requires the event stream to be the single thing any future UI reads, so the API returns it whole. Summaries exist only for listing.
- Cancellation is cooperative: `cancel` sets a flag the engine checks between transitions and writes terminal status `"cancelled"` into the run file. Add `"cancelled"` to the `RunStatus` Literal in `engine/state.py` in this step. A running node finishes; the next boundary stops.
- Notes append to a `notes: list[str]` field on `RunFile` (default empty). This widens the run file format; bump nothing — the envelope `format: int` stays 1 until the shape changes incompatibly, which it does not.
- Add `started_at: str` to `RunFile`, set once at creation.

Also in this module: `summaries(files: Iterable[RunFile]) -> list[RunSummary]`, a pure projection used by the service, the CLI listing path, and any future second implementation.

Tests (`test_service_types.py`): summary projection numbers (cost summed from fake `model_call` records, waiting flag), filter behavior, unknown-run error type. Define `UnknownRunError(KeyError)` here; both backends raise it for missing run ids.

Absorbs: the v0.4 UI, which consumes exactly these six methods; new run states, which widen `RunStatus` in one place.

Out of scope: HTTP serialization (Step 3), cancellation mid-node (cooperative check lands with budgets in Step 4; until then `cancel` on a running run takes effect at the next await point naturally).

Verify: `uv run pytest src/ngen_weave/test_service_types.py`.

Commit: `feat(core): RunService protocol, run summaries, cancelled status`

### Step 3 — FastAPI-owned RunService implementation

`packages/ngen-weave-server/src/ngen_weave_server/local.py` plus `app.py`.

`local.py` — the in-process implementation, the reference for the protocol:

```python
class LocalRunService:
    def __init__(self, engine: Engine, store: RunStore)   # constructed like the CLI's _build_engine
    # implements all six RunService methods directly over Engine + RunStore
```

Behavior per method:

- `launch`: resolve the name via `registry.get(workflow)` (raises `UnknownRunError` wrapped as `ConfigError` text if unregistered), call `engine.run(wf, input)`, return `RunHandle(run_id, result.status)`.
- `resume`: delegate to `engine.resume(run_id, payload)`; unknown id raises `UnknownRunError`.
- `status`: `store.load(run_id)`.
- `cancel`: set the cooperative flag (Step 4 wires the engine side; here write terminal `"cancelled"` if the run is not mid-transition, else mark pending).
- `list_runs`: `summaries(store.list())` filtered by `RunFilters` fields.
- `attach_note`: load, append, save through `RunStore` only.

`app.py` — the HTTP translation layer. Per the PRD the web API holds no business logic; these routes translate HTTP to `LocalRunService` calls and nothing else:

```
POST /runs                      body {"workflow": str, "input": dict}   -> RunHandle json
POST /runs/{run_id}/resume      body {"payload": dict | null}           -> RunHandle json
GET  /runs/{run_id}                                                     -> RunFile json
POST /runs/{run_id}/cancel                                              -> 204
GET  /runs?workflow=&status=                                            -> [RunSummary] json
POST /runs/{run_id}/notes       body {"note": str}                      -> 204
```

Errors map to HTTP: `UnknownRunError` → 404, `ConfigError` → 400, `NgWeaveError` → 500 with `{"error": {"type", "message"}}`. Pydantic validation failures on launch input surface as 400 with pydantic's error list.

An application factory ties it together:

```python
def create_app(config_path: Path | None = None,
               runs_dir: Path = Path(".ngen-weave/runs"),
               db_path: Path = Path(".ngen-weave/checkpoints.db"),
               models_file: Path = Path("models.json")) -> FastAPI
```

Defaults match the v0.1 `RunSettings`; `config_path` given means load `ResolvedConfig` first and derive everything from it.

Tests (`test_local_service.py`): drive the FastAPI app with `httpx.AsyncClient(transport=ASGITransport(app))` and a `FakeProvider`-built engine — launch a linear worker chain to completion; resume after a human interrupt with a JSON payload; 404 on unknown run; list filtering; note append visible in `status`. All against tmp directories.

Absorbs: the eventual standalone deployment at 1.0, which is this same app run under uvicorn with Postgres behind `RunStore`; nothing above this layer changes.

Out of scope: auth (v0.8), streaming/SSE, websocket anything, CORS, multiple workflows per process beyond what the registry loads, background task queues.

Verify: `uv run pytest packages/ngen-weave-server/src/ngen_weave_server/test_local_service.py`.

Commit: `feat(server): local FastAPI RunService with HTTP translation layer`

### Step 4 — Budget enforcement in the engine

Two edits in `packages/ngen-weave-core/src/ngen_weave/`.

`config.py`: extend `RunSettings` with `budget: Budget | None = None`, parsed from YAML/JSON:

```yaml
run:
  budget:
    cost_usd: 5.00     # optional
    steps: 100         # optional
```

```python
@dataclass(frozen=True)
class Budget:
    cost_usd: float | None = None
    steps: int | None = None
```

Both fields optional; at least one required when the key is present (else `ConfigError`). Unknown budget keys rejected like all config keys.

`provenance.py`: widen `Kind` with `"budget_exhausted"` and `"permission_denied"` (the latter used by Step 10; declare it now so the Literal changes once). Payload contracts, written here and nowhere else:
- `budget_exhausted`: `{"dimension": "cost_usd" | "steps", "limit": float | int, "observed": float | int}`
- `permission_denied`: `{"tool": str, "node_path": str, "policy": str}`

`engine/runner.py`: after each node activation completes and *before* any supervision predicate evaluates at the same boundary, the engine calls a single private hook `_check_budget(run_id, node_path) -> bool` (True means breached):

- `cost_usd`: compare against running totals maintained on the `RunFile` metadata (each `model_call` updates them; no record rescanning at check time).
- `steps`: same, via a transition counter in the run file metadata.
- On breach: emit `budget_exhausted` provenance, set run status `paused`, `interrupt()` the graph, and make `RunResult.status == "paused"` with `waiting` carrying `{"node_path", "reason": "budget_exhausted"}`. The run does not fail, per the release doc.
- Resumption: `Engine.resume(run_id, payload=None)` re-reads the current budget from... nowhere — the engine holds limits in memory. So persist the breach context instead: the run file's `waiting` dict is already checkpointed via the interrupt, and resume re-evaluates `_check_budget` at the next boundary. Raising the cap therefore works by launching resume with a new `Engine` built from updated settings, exactly how the CLI already rebuilds engines per invocation. Document this in the hook's docstring in one sentence; no special resume path.

The evaluation order is deliberate: budget breach short-circuits any author-declared supervision predicate at the same boundary, so a cost pause cannot be overridden. One sentence in `runner.py` noting this; do not build a priority system.

Tests (`engine/test_budget.py`): cost breach pauses mid-chain with a `budget_exhausted` record present exactly once; steps breach likewise; under-budget runs never emit the record; resume after constructing a fresh `Engine` with a raised cap completes the run (criterion 5 at unit level); budget breach suppresses a would-fire supervision predicate at the same transition once supervision lands.

Out of scope: per-node budgets (PermissionSet keeps its own `budget_usd` for agents, checked per call in Step 10), live cost dashboards, refunding or re-measuring spent cost.

Verify: `uv run pytest src/ngen_weave/engine/test_budget.py src/ngen_weave/test_config.py`.

Commit: `feat(engine): run-level budget enforcement pauses on breach`

Note: author-declared supervision (observers) also lands in v0.2, per `releases/v0.2.md`'s "Supervision: observers in the scheduler". Its step is deliberately not written yet: predicates as structured builders (`gt`, `lt`, `and_`, `or_`, self-rendering descriptions), pause-only actions, evaluated at this same activation boundary. The step gets specified when the scheduling work around it is planned, since budget enforcement here defines the boundary mechanics it will reuse.

### Step 6 — MCP project manifest

`packages/ngen-weave-mcp/src/ngen_weave_mcp/manifest.py`.

Project-root `ngen-weave.json` (the project-side complement to packages' `ngen-weave.workflows` entry-point group from v0.1 Step 4):

```json
{
  "format": 1,
  "project": "my-project",
  "workflows": ["examples.code_review.workflows", "more.workflows"]
}
```

Each entry is an importable module whose import triggers `__init_subclass__` validation and discovery registration. Loader:

```python
@dataclass(frozen=True)
class ProjectManifest:
    project: str
    modules: tuple[str, ...]

def load_project_manifest(root: Path) -> ProjectManifest
    # parses ngen-weave.json; missing file, bad format int, non-list workflows,
    # or unimportable module raise ConfigError naming the file and the offending entry
def discover_workflows(manifest: ProjectManifest) -> dict[str, type[Workflow]]
    # imports each module, returns registry.all() restricted to what loaded;
    # duplicate workflow names across modules are ConfigError
```

Startup validation happens in `discover_workflows` by construction: importing a module runs v0.1's import-time structural validation, so a broken workflow fails server startup loudly, per the release doc. Additionally require `description != ""` for every exposed workflow here — v0.2 makes description mandatory for MCP exposure because agents choose tools by description; an empty description is `ConfigError` naming the workflow. This requirement applies only to MCP exposure; bare `Workflow.description` stays optional in core.

Tests (`test_manifest.py`): happy path, missing file, malformed JSON, unimportable module, duplicate names, empty description rejected, valid description accepted.

Out of scope: glob patterns or directory scanning in the manifest, per-workflow exposure toggles, remote manifests, watching the file for changes.

Verify: `uv run pytest packages/ngen-weave-mcp/src/ngen_weave_mcp/test_manifest.py`.

### Step 7 — MCP tool registration and stdio dispatch

`packages/ngen-weave-mcp/src/ngen_weave_mcp/tools.py` and `stdio.py`.

`tools.py` builds the tool surface once, at startup, from discovered workflows plus a `RunService`:

```python
def register_workflow_tools(server: mcp.server.Server,
                            workflows: dict[str, type[Workflow]],
                            service: RunService) -> None
```

Per the release doc, for each workflow:

- Tool name = `workflow.name`; description = `workflow.description` (required non-empty per Step 7).
- Input schema = `workflow.input_type.model_json_schema()`, passed through unchanged.
- Handler semantics: **blocking with an explicit timeout, and honest about pauses.** The handler calls `await service.launch(name, input_type.model_validate(arguments))`, then polls `status(run_id)` at 250 ms until a terminal status (`completed`, `failed`, `cancelled`), a pause (`paused` / `waiting_human`), or the caller-supplied timeout. On completed: return the validated output object as the tool result. On failed: return an MCP error result carrying the run file's `error`. On `paused`/`waiting_human`: return immediately (no further polling) with the run id and waiting node path; humans take unbounded time by design, and resumption happens through the runs API or CLI, not by holding the tool call open. On timeout: return an MCP error result naming the run id, which stays resumable. MCP is documented as the machine-speed calling path; human review enters through runs surfaces.

`stdio.py`:

```python
def main() -> None:
    # argparse: --root PATH (default cwd), optional --models/--db overrides mirroring create_app defaults
    # loads manifest from root, discovers workflows, builds LocalRunService via create_app's engine wiring,
    # registers tools, serves over the mcp SDK's stdio transport
```

Console script `ngen-weave-mcp = "ngen_weave_mcp.stdio:main"` in the package's pyproject.

Tests (`test_tools.py`): drive `register_workflow_tools` against the mcp SDK's in-memory session pair with a FakeProvider-backed `LocalRunService` — list tools shows one entry per workflow with correct name/description/schema; calling a completing workflow returns its validated output; calling one that hits a Human returns the paused structure with a run id; calling with schema-invalid arguments returns a validation error result, and no run file was created. E2E (`tests/e2e/test_stdio.py`): spawn the actual console script as a subprocess pointed at a copy of `examples/code_review`, speak real MCP-over-stdio through the SDK client, run to completion with a monkeypatched provider via an env var the subprocess reads (`NGEN_WEAVE_FAKE_PROVIDER=1` makes the engine wiring use `FakeProvider`; this env hook is test-only and documented as such).

Absorbs: new workflows (manifest line only), a remote-service backend (pass any other `RunService` to the same registrar), future result shaping (one return-mapping function).

Out of scope: streaming/progress notifications, tool-level permissions or auth, HTTP transport (Step 8), resource/prompts primitives, ngen-weave-as-agent-tools loopback.

Verify: `uv run pytest packages/ngen-weave-mcp/ && uv run ngen-weave-mcp --help`.

Commits: `feat(mcp): workflow-as-tool registration with blocking dispatch`, `test(mcp): stdio e2e against canonical example`.

### Step 9 — Runs CLI commands

`packages/ngen-weave-cli/src/ngen_weave_cli/main.py` grows:

```
ngen-weave workflows [--url URL]
gen-weave runs [--workflow NAME] [--status STATUS] [--url URL]
ngen-weave cancel <run-id> [--url URL]
ngen-weave note <run-id> <text> [--url URL]
```

Decision: the CLI talks to a `RunService`, never to the engine directly. Without `--url` it constructs `LocalRunService` in-process from the usual config resolution (reusing `context._build_engine`, extended to also return the store); with `--url` it uses an `HttpRunService` — a thin client in `packages/ngen-weave-server/src/ngen_weave_server/client.py` speaking the Step 3 routes back into the six protocol methods. This keeps one command surface working against either backend and gives the conformance idea a third consumer for free.

Output formatting: `workflows` prints one line per registered workflow — `name  human_description` (resolved through the same merged discovery map); it is the person-facing inventory, deliberately showing `human_description`, never the MCP-facing `description`. `runs` prints one line per summary — `run_id  workflow  status  cost_usd  started_at  waiting_flag`; `cancel` prints the resulting status; exit codes follow v0.1 conventions (0 success, 1 `NgWeaveError`).

Tests (`test_cli_runs.py`): seed tmp run files, exercise filtering and printing through Typer's runner; cancel on unknown id exits 1 with the message; `--url` mode tested against the Step 3 ASGI app via httpx transport monkeypatched into the client factory.

Absorbs: v0.4 management screens, which sit on these same protocol calls per the release doc.

Out of scope: `pause`/`resume` as separate CLI verbs (`ngw resume` exists from v0.1 and pausing is always system-initiated), watch/stream modes, JSON output flags.

Verify: `uv run pytest packages/ngen-weave-cli/tests/ && uv run ngen-weave runs --help`.

Commit: `feat(cli): runs, cancel, and note commands over RunService`

### Step 10 — AgentNode harness: tools, gate, real-model executor

Three modules replacing the mock as the default executor. The mock stays for tests.

`packages/ngen-weave-core/src/ngen_weave/agent/tools.py`:

```python
@dataclass(frozen=True)
class ToolSpec:
    name: str                       # [a-z][a-z0-9_-]*, unique in registry
    description: str
    parameters_schema: dict         # JSON Schema for the tool's arguments
    fn: Callable[[dict], Awaitable[dict]]   # args validated against parameters_schema before calling

class ToolRegistry:
    def register(self, spec: ToolSpec) -> None          # duplicate name raises ConfigError
    def specs(self) -> tuple[ToolSpec, ...]
    async def call(self, name: str, args: dict) -> dict # validates args, UnknownToolError otherwise
```

`packages/ngen-weave-core/src/ngen_weave/agent/gate.py` — permission enforcement, engine-side:
