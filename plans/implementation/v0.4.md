## Goals

1. Every `Workflow` serializes to YAML (JSON accepted) in the v0.1 config format widened to cover every serializable field; `load(dump(x))` re-serializes the data subset identically, byte for byte, for every shipped workflow, and code-bearing members serialize as registry-name references.
2. Definitions live as files under `.ngen-weave/definitions/`; saving goes API → validation gate → `DefinitionStore` → disk → standard loader, never around it. Invalid saves return the full error list, identical to `ngen-weave validate`.
3. The UI creates and edits workflows on the v0.3 canvas with mutation handlers attached; unknown node types remain generically editable.
4. The UI launches runs, lists/filters them, shows status/cost/steps/budget, cancels, resumes, submits human reviews from rendered artifacts, and adjusts budgets mid-run (pause at next transition, per v0.2 breach behavior).
5. Every artifact write versions content in a small JSON manifest; the core diff engine produces typed diff records (text line hunks, binary size/hash indicators) that the UI renders best-effort per type.
6. A run exports as W3C PROV-JSON (activity = activation, entity = input/output/artifact, agent = model call) plus the single-file run JSON, from the run file alone, with no new instrumentation.

## Success criteria

From `releases/v0.4.md`, verbatim in intent:

1. A user creates a two-node workflow entirely in the UI, launches it, answers a human review in the browser, and gets the final output. Zero source files touched.
2. Every saved workflow round-trips its data subset exactly through the storage layer, with code-bearing members as registry-name references (property-style test over all example workflows).
3. An artifact written across three runs shows three versions with inspectable diffs and a provenance export tracing each version to its producing activation.
4. A PROV-JSON export validates against the W3C schema and contains no reference to entities absent from the run JSON.
5. Mid-run budget reduction pauses a running workflow at the next transition.

## Abstractions and what they absorb

One sentence each; these are the load-bearing choices.

- **The definition format as one pure pair (`definition_to_dict` / `definition_from_dict`) in `storage.py`** absorbs new node fields and future schema features: both grow inside these two functions, callers never see the wire dict.
- **JSON Schema as the only model representation** absorbs new serializable types (dates, unions, plugin types at v0.5) with zero grammar to extend: models serialize as canonicalized `model_json_schema()` documents and rebuild through one `schema_to_model` constructor; there is no second type language to keep in sync with pydantic. Constructs outside the supported subset (unions of models, custom validators) are by definition code-bearing and must be a Python registry reference, matching the data-only rule.
- **`DefinitionStore` as the only writer of `.ngen-weave/definitions/`** absorbs storage backends (Postgres at v0.6) and multi-project trees: consumers see `list/load/save/delete`, nothing else knows files exist.
- **Discovery-by-source (v0.3's `DiscoveryResult`) gaining a definitions-directory source** absorbs plugins (v0.5): a third source joins the same result shape; the read API and editor never learn where classes came from.
- **`VersionLog.append` as the sole versioner, called from the engine's existing artifact-write hook** absorbs retention policies and renames: version numbering lives in one class, the blob store stays untouched.
- **`diff_bytes` returning typed `FileDiff` records** absorbs new media types: the classifier maps bytes to a kind in one function; the UI renders kinds it knows and falls back otherwise.
- **Effective budget = `budget_override ?? budget` resolved inside the engine's existing `_check_budget`** absorbs per-node budgets and policy changes: the resolution rule exists in one hook, mid-run edits are a `RunService.set_budget` call — file mode implements it as a run-file write, so the v0.6 Postgres backend swaps underneath without touching the mechanism.
- **The PROV exporter as a pure function over `RunFile`** absorbs new record kinds: the kind-to-PROV mapping is one dispatch table; missing mappings fail loudly rather than silently dropping entities.

## Commit sequence

### Step 1 — Storage format: serializer and parser

`packages/ngen-weave-core/src/ngen_weave/storage.py`. Pure functions over `Workflow` classes and dicts; no filesystem, no imports of engine or server modules. This module defines the format; Steps 2–4 consume it.

```python
FORMAT_VERSION = 1

def definition_to_dict(wf: type[Workflow]) -> dict
def definition_from_dict(data: dict, *, name: str | None = None) -> type[Workflow]
def to_yaml(data: dict) -> str            # canonical: sort_keys=False, explicit start, width=120
def to_json(data: dict) -> str            # indent=2, sort_keys=True
def parse_text(text: str) -> dict         # YAML or JSON by sniffing first non-blank char ('{' -> json)
def canonical_yaml(wf: type[Workflow]) -> str   # to_yaml(definition_to_dict(wf)); the fidelity unit
```

Document shape (widened v0.1 config syntax; everything valid in a v0.1 config remains valid input):

```yaml
format: 1
workflow: reviewed_draft          # definition name, [a-z][a-z0-9_-]* (rule 2 of validate_structure)
description: "Drafts then gates"
kind: worker                      # worker | control | human | agent | composite
input:                            # JSON Schema document (canonicalized model_json_schema()), see below
  title: DraftInput
  type: object
  required: [diff]
  properties:
    diff: {type: string}
output:                            # same; nested models via $ref into $defs
  title: DraftOutput
  type: object
  properties:
    text: {type: string}
    score: {type: integer, default: 0}
prompt: "Review this diff:\n{diff}"
variant: sonnet                   # null when unset
artifacts: []                     # output field names
observers:                        # composite/any level
  - name: cost_watch
    predicate: "lambda md: md.cost_usd > 1.0"   # source string
# composite-only keys, mirroring the class attributes verbatim:
children: [<full nested definition>, ...]
edges: [["draft", "gate"], ["gate", "human_review", "fail"]]
inputs: {finalize: {review: "human_review.notes"}}
prefill: {}                       # human nodes; callables serialized as {"__callable__": "<source>"}
```

Model representation, decided here so no later step weighs it: input/output/state schemas are stored as **canonicalized JSON Schema** — exactly what `model_json_schema()` already produces for config, UI, and MCP. There is no field-type grammar and no parallel type language.

```python
def schema_canonical(model: type[BaseModel]) -> dict   # sort_keys canonical dump of model_json_schema()
def schema_to_model(schema: dict) -> type[BaseModel]   # the one reconstruction path
```

- `schema_to_model` supports the subset pydantic emits for plain data models: object schemas, primitive types, enums/literals, arrays, defaults, `$ref`/`$defs` for named nested models (two-plus levels). Anything outside the subset fails parsing with a `ConfigError` naming the construct — such models are code-bearing by rule and must come from a registered Python workflow.
- The read API already serves these documents verbatim (`GET .../schemas/:file`, v0.3), so the stored form and served form are identical artifacts; structural fidelity loses its translation step.

Parser behavior, decided here so no later step weighs it:

- `definition_from_dict` builds pydantic models with `pydantic.create_model` and the class with `type(name, (Worker/Control/Human/AgentNode,), attrs)` chosen by `kind`, then runs `validate_structure` — invalid definitions raise `ConfigError` with the same messages the decorator path produces. Composites recurse into `children` before assembling `edges`/`inputs`.
- Observers serialize as their description string plus action and target; the editor edits those fields, never the predicate function. Prefill callables serialize as registry-name references like all code-bearing members.
- Unknown `format` value, unknown `kind`, an out-of-subset or malformed schema document, or unknown top-level key raises `ConfigError` naming the offending key — typo protection identical to `config.load_config`.
- `definition_to_dict` emits `null` for absent optionals rather than omitting keys, so dumps are stable under re-serialization (this is what makes exact round-trip achievable).
- Fidelity contract: for any workflow passing today's validation, `canonical_yaml(definition_from_dict(parse_text(canonical_yaml(wf)))) == canonical_yaml(wf)`. Semantic equality additionally asserted: parsed class passes `validate_structure`; `schema_document` output of its input/output models equals the original's (compare `model_json_schema()` with sort_keys dumps). Function identity of observer predicates is *not* asserted; their source text is.

Tests (`test_storage.py`): parametrized over every workflow in `examples/` plus constructed fixtures covering each node kind, fan-in maps, observers, prefills (path and callable), defaults, literals, nested models two levels deep — full fidelity assertion on each; each `ConfigError` branch with message match; yaml/json dialect equivalence (`parse_text(to_json(d))` parses to the same dict).

Absorbs: v0.5 plugin node types (a `kind` registry entry; their schemas ride the same JSON Schema representation) and Postgres-era storage (the dict is already the record).

Out of scope: file locations (Step 2), HTTP exposure (Step 3), editing flows, migration tooling for hand-written configs (none needed — subset stays valid).

Verify: `uv run pytest src/ngen_weave/test_storage.py src/ngen_weave/test_workflow.py`.

Commit: `feat(core): workflow definition format`

### Step 2 — DefinitionStore and validate-on-definition-files

Two pieces in core, one in CLI.

`packages/ngen-weave-core/src/ngen_weave/definitions.py`:

```python
@dataclass(frozen=True)
class DefinitionRecord:
    name: str
    path: Path
    text: str                      # exact file bytes (decoded)

class DefinitionStore:
    def __init__(self, directory: Path)   # typically <root>/.ngen-weave/definitions
    def list(self) -> list[DefinitionRecord]           # sorted by name; missing dir -> []
    def load(self, name: str) -> type[Workflow]        # KeyError-naming ConfigError when absent
    def save(self, data: dict) -> type[Workflow]       # parse -> validate_structure -> atomic write;
                                                       # filename <name>.yaml; returns the loaded class
    def delete(self, name: str) -> None                # missing -> KeyError
    def raw(self, name: str) -> str                    # exact stored text
```

Rules: `save` rejects a name collision with a *registered Python* workflow (the objects remain canonical; file definitions may extend, not shadow, the registry) with `ConfigError`; overwriting its own file is fine. Extension is always `.yaml` even when the content is JSON dialect — one file per definition, extension is not the dialect. Writes are atomic (temp + `os.replace`, same pattern as `RunStore.save`).

CLI (`packages/ngen-weave-cli/src/ngen_weave_cli/main.py`): `ngen-weave validate <path>` gains detection — if the parsed document has top-level keys `format` and `workflow`, treat it as a definition file: `definition_from_dict` + `validate_structure` statically, print errors, exit 1 on failure, exactly mirroring existing validate output style. Registry-based validation unchanged otherwise.

Tests: save/list/load/delete round trip; atomicity observable via leftover-temp absence; collision with registered name rejected; overwrite own file fine; CLI validate accepts a good definition file and rejects a broken one with named-field errors and exit 1.

Absorbs: v0.6 Postgres store (swap inside `DefinitionStore`) and v0.5 packs shipping pre-built definition files (they land in the same directory).

Out of scope: serving over HTTP (Steps 3–4), discovery integration (Step 3), deleting or renaming workflows via UI (delete exists in the store; no route exposes it in v0.4), git operations (git is the user's history mechanism; ngen-weave never shells out to git).

Verify: `uv run pytest src/ngen_weave/test_definitions.py packages/ngen-weave-cli/tests/test_cli_validate.py && uv run ngen-weave validate examples/code_review/.ngen-weave/definitions/nonexistent.yaml` (prints unknown-file error cleanly).

Commit: `feat(core): definition store with static validation of definition files`

### Step 3 — Byte-fidelity read model and the definition endpoint

`packages/ngen-weave-server/src/ngen_weave_server/readmodel.py` and `api.py`. This fulfills the v0.3 promise: the structural-fidelity contract tightens to data-subset round-trip, inside the module designed to absorb it.

Changes, all internal to `readmodel.workflow_detail` plus one new pure function:

```python
def definition_view(store_or_class) -> dict
# {"text": "<exact definition text>", "hash": sha256(text), "origin": "file" | "derived"}
```

- `ReadState` (v0.3 Step 4) gains `definitions: DefinitionStore` rooted at `project_root/.ngen-weave/definitions`, and discovery merges a second source: every `DefinitionStore.list()` name loads through `definition_from_dict` and contributes a `DiscoveredWorkflow`. Name collisions between file definitions and manifest-imported classes were already rejected in Step 2; collisions among file names raise at startup (duplicate = definition bug, matching v0.3 duplicate policy).
- `workflow_detail` for a file-origin workflow includes `"source": null` (no Python module exists) and `"definition": <definition_view>`; for a Python-origin workflow, `definition.text` is `canonical_yaml(cls)` with `"origin": "derived"` and `hash` computed over that derived text. The detail-level `hash` continues to cover the whole detail dict minus itself, so it changes when either form changes.
- New route in `api.py`: `GET /api/workflows/{name}/definition` → `definition_view`; unknown name → 404 envelope as established. This is the endpoint the editor loads before editing.

Tests (extend `test_api.py`): file-defined workflow appears in the list with correct hash; its detail carries `source: null` plus definition text equal to the file bytes; a Python workflow's derived text re-parses (`definition_from_dict` succeeds) and re-canonicalizes identically; the definition endpoint serves both origins; collision case fails startup with both names in the message.

Absorbs: the editor (loads and saves through this one view) and future alternate origins (plugin-shipped definitions are still files).

Out of scope: any mutation (Step 4), diffing of definitions (git's job), serving `.json` dialect back verbatim (files saved by hand as JSON keep their bytes in `raw`/`text`; only derived Python workflows canonicalize to YAML).

### Step 4 — Mutation API: create and update definitions

`packages/ngen-weave-server/src/ngen_weave_server/api.py`. One route, one write path, per the release doc's architecture notes: the API never writes a file it hasn't validated, and the browser never writes YAML itself.

```
PUT /api/workflows/{name}     body: the definition document as JSON (Content-Type application/json)
                              or text/yaml text
```

Behavior, fully specified:

- The handler injects/overrides `"workflow": name` into the document (path is authoritative), then calls `DefinitionStore.save`. All failure modes surface as one error shape: `400 {"error": {"type": "invalid_definition", "message": ..., "errors": ["<line>", ...]}}` where `errors` is the collected `ConfigError` list from parsing + `validate_structure` — the same list `ngen-weave validate` prints. Collision-with-registry and unknown-name-mismatch cases are ordinary entries in that list.
- On success: `201` when the name is new, `200` when replacing; response body is the updated `workflow_detail` (Step 3 shape), so the editor can re-render immediately without a refetch.
- After a successful save, the API layer rebuilds its `ReadState` discovery/details (extract the eager-build block from `create_app` into a `ReadState.rebuild()` method; `save` triggers it). Concurrent-request policy: last write wins; no locking, no etags before 1.0.
- **Launch resolution shares the same discovery chain.** `POST /runs` resolves workflow names through exactly what `ReadState.rebuild()` discovered — registry ∪ definition files, one merged map held by the API layer — never a separate lookup path. Without this, a just-saved definition passes validation and appears in the UI but fails at launch (split-brain). The v0.2 route's name-resolution step is amended to consume this shared chain.
- Request bodies larger than 256 KiB → 413. Malformed YAML/JSON → 400 `invalid_definition` with parser error text, not a 500.

Amendment to `packages/ngen-weave-server/tests/e2e/test_read_only.py` (v0.3 Step 5): the blanket "all routes are GET/HEAD" assertion becomes an explicit allow-list assertion — the set of (path, method) pairs not in `{"GET", "HEAD"}` must equal exactly `{("/api/workflows/{name}", "PUT")}` plus the v0.2 run routes. The import-scan assertion drops `DefinitionStore.save` from its forbidden-names list. Both changes carry comments pointing at this plan.

Tests (extend `test_api.py`): create-new returns 201 and the file exists on disk with canonical text; replace returns 200; invalid graph (edge to nonexistent child) returns 400 with the offending node named in `errors[]`; path/body name mismatch resolves to path; registry-collision rejected; after save, `GET /api/workflows` reflects the new workflow without restart.

Absorbs: v0.5 plugin-authored definitions (same route) and any future bulk import (loops over this route's handler).

Out of scope: DELETE route, rename (rename = new save + manual delete; UI offers neither), optimistic concurrency/etags, draft/autosave semantics, permission checks.

Verify: `uv run pytest packages/ngen-weave-server/src/ngen_weave_server/test_api.py packages/ngen-weave-server/tests/e2e/test_read_only.py`.

Commit: `feat(server): validated definition mutation endpoint`

### Step 5 — Artifact version log

`packages/ngen-weave-core/src/ngen_weave/artifacts.py` (extend) and `provenance.py` (one-line widen). Blobs stay exactly as v0.1 left them; versioning is a sidecar index per logical artifact name.

```python
@dataclass(frozen=True)
class VersionEntry:
    n: int                 # 1-based, monotonic per artifact name
    sha256: str
    ts: str                # UTC ISO-8601
    run_id: str
    node_path: str

class VersionLog:
    def __init__(self, projects_dir: Path, project: str)
    def append(self, name: str, sha256: str, ts: str, run_id: str, node_path: str) -> VersionEntry
        # manifest file: projects/<project>/<name>.versions.json
        # {"format": 1, "name": ..., "versions": [...]} — atomic write, append-only by contract
    def entries(self, name: str) -> list[VersionEntry]   # unknown name -> []
```

Engine hook (`engine/runner.py`): the existing post-activation artifact-write block, after emitting `artifact_write` provenance, additionally calls `VersionLog.append(field_name, record.sha256, ts, run_id, node_path)`. One extra provenance kind is deliberately *not* emitted — version facts are recoverable from the manifest, and the release doc forbids new instrumentation beyond the record stream; instead `Kind` gains `"version_write"` declared now but unused until evidence demands it (comment says exactly that).

Same-run idempotence: if the engine retries a node and rewrites identical bytes, `append` still adds an entry (distinct activations are distinct versions); identical bytes within one activation append once (guard on `(activation-order)` is unnecessary — the retry path emits separate `node_activation` records and each counts). Decision made here: versions count writes, not distinct contents.

Tests (`test_versions.py`): three appends across three fake runs yield versions 1..3 with ordered ts; manifest survives a crash-between-append-and-write (atomic-write simulation: inject `os.replace` failure, assert old manifest intact); entries for unknown name empty; engine integration — a two-run fixture writes two versions of one artifact name and the manifest links both `run_id`s and `node_path`s (this is criterion 3's tracking half).

Absorbs: retention/pruning policies (inside `VersionLog`) and v0.6 database move (same class, new backing).

Out of scope: diff computation (Step 6), version-aware tree listing changes (the v0.3 projects reader hides sidecars and keeps working untouched), restoring old versions, cross-project moves.

Verify: `uv run pytest src/ngen_weave/test_versions.py src/ngen_weave/engine/test_engine.py`.

Commit: `feat(core): per-artifact version log written from the engine hook`

### Step 6 — Diff engine

### Step 7 — Versions and diff API routes

`packages/ngen-weave-server/src/ngen_weave_server/projects.py` (extend) and `api.py`. Routes translate to Step 5–6 calls; zero logic here.

```
GET /api/projects/{project}/{path:path}/versions
    # path is the artifact name (blob path relative to project root);
    # -> {"name": ..., "versions": [{"n", "sha256", "ts", "run_id", "node_path"}, ...]}
GET /api/projects/{project}/{path:path}/diff?v1=1&v2=2
    # -> <FileDiff as JSON>
```

Error mapping follows the v0.3 envelope: unknown project/prefix/name or missing version → 404; traversal `ValueError` → 400; missing query params → 422 (FastAPI default). ### Step 8 — PROV-JSON export

`packages/ngen-weave-core/src/ngen_weave/prov.py` (new), CLI, and one API route. Reads `RunFile` only — no checkpoints, no engine, per the release doc's fix-direction rule (if the export lacks something, the record stream grows, not this module).

```python
PROV_NAMESPACE = "https://w3c.github.io/prov/"
def to_prov_json(run: RunFile) -> dict
```

Mapping, fixed here (prefix `ngw:` throughout):

- **activity** per `node_activation` record: id `ngw:<run_id>:<node_path>#<ordinal>` (ordinal = index in the record stream, making retries distinct activities); attributes `prov:type="ngw:node_activation"`, `ngw:status` from payload, `prov:startTime`/`prov:endTime` from adjacent record timestamps when derivable, else `prov:startTime` only.
- **entity** per distinct input field hash, per validated output, and per `artifact_write` payload `artifact_sha256`: ids `ngw:<run_id>:in:<field>:<hash8>`, `ngw:<run_id>:out:<node_path>`, `ngw:<run_id>:artifact:<name>:<hash8>`; `prov:type` = `ngw:input` / `ngw:output` / `ngw:artifact`.
- **agent** per distinct `model_call` variant: id `ngw:variant:<variant>`; `prov:type="prov:SoftwareAgent"`, attribute `ngw:variant`.
- **relations**: `used(activity, entity)` from each activation's input hashes; `wasGeneratedBy(entity, activity)` from outputs and artifact writes; `wasAssociatedWith(activity, agent)` from model calls on the same `node_path`; `wasDerivedFrom(output_entity, input_entities)` per activation.

Completeness rule, tested mechanically: every entity id referenced by any relation must exist in the document's `entity` map, and every entity must trace to a run-file fact (criterion 4's second half). Unknown record kinds raise `ConfigError("cannot map provenance kind: ...")` loudly rather than dropping.

CLI: `ngen-weave export-prov <run-id> [--out PATH]` — loads via `RunStore`, prints or writes PROV-JSON. `--out` omitted prints to stdout.

API route in `api.py`: `GET /api/runs/{run_id}/provenance` → `to_prov_json(store.load(run_id))` with `Content-Type: application/json`; unknown run → 404 envelope. The plain run JSON is already served whole by `GET /runs/{run_id}` (v0.2); link, don't duplicate.

W3C validation: check in the official PROV-JSON schema (`prov-json-schema.json`) under `packages/ngen-weave-core/tests/e2e/data/` and validate exports with `jsonschema` (added as a dev dependency of core). No runtime dependency.

Tests (`test_prov.py` + e2e): export of a completed code-review run validates against the checked-in schema; referential closure assertion (every referenced id exists); artifact versions appear as entities generated by the right activities (criterion 3's provenance half); unknown-kind raises; CLI smoke via Typer runner.

Absorbs: new record kinds (one dispatch-table row) and Argo-era export targets (pure function, reusable anywhere).

Out of scope: importing PROV-JSON, cross-run graphs, PROV-N serialization, streaming exports.

Verify: `uv run pytest src/ngen_weave/test_prov.py && uv run ngen-weave export-prov --help`.

Commit: `feat(core): w3c prov-json exporter over the run file`

### Step 13 — Web: editor

`src/lib/editor/` + `src/routes/workflows/new/+page.svelte` + mutation handlers wired into the v0.3 canvas component. Biggest frontend step; split into three commits, each green.

**13a — Editing state machine** (`src/lib/editor/state.ts`). A pure Svelte store holding the working definition document (the Step 1 dict shape, typed as `DefinitionDoc` in `types.ts`):

```typescript
export function createEditor(doc: DefinitionDoc): {
  doc: () => DefinitionDoc                       // current document
  setField(path: string[], value: unknown): void // dotted-path setter into the doc
  addNode(kind: string): string                  // returns generated node name "node_2"
  removeNode(name: string): void                 // also drops incident edges and inputs-map entries
  connect(src: string, dst: string, branch?: "pass" | "fail"): void
  disconnect(src: string, dst: string): void
  setFanIn(target: string, field: string, ref: string): void
  validate(): Promise<ValidationResult>          // client-side cheap checks only; truth is the server's
}
```

All operations mutate the document; nothing talks to the network except `validate`/save. Client-side checks limited to: edge endpoints exist, control nodes have both branches, names unique and kebab-case. Everything else waits for the server's error list.

**13b — Canvas mutation handlers.** The v0.3 canvas gains props `onConnect`, `onNodeDelete`, `onNodeSelect` (v0.3 reserved this seam). Node drag updates positions transiently for layout only — positions are *not* persisted (layout derives from topology, per v0.3); dragging is visual comfort. Edge creation drags from port to port; control nodes offer branch choice on drop. Unknown node types (generic fallback) expose the same ports and open the same field form, so v0.5 plugins are editable without frontend work.

**13c — Field forms and save flow.** Right-hand panel tabs per selected node: fields (name, kind select locked to known five, description, prompt textarea for workers, variant, artifacts multi-select of output fields, observers as raw predicate-source textareas with a "compiled server-side" hint), input/output schema editors as field tables (name, JSON-Schema type from a dropdown — string/integer/number/boolean/array/enumeration, options list when enumeration, required toggle, default input); the table compiles to the stored JSON Schema document on save, edges/fan-in table for composites. Save bar: **Validate** (`putDefinition` dry-run is not supported — instead Validate = client checks + render server errors from a previous failed save) and **Save** (`putDefinition`; 200/201 navigates to `/workflows/[name]`; 400 renders `errors[]` line-per-item above the canvas, each error clickable when it names a node). New workflow starts from `createEditor(blankWorker())` exporting the minimal valid document.

Playwright arrives here (first mutation flows): `tests/e2e/editor.spec.ts` covering create-two-node-connect-save-launch-review-complete — the automated skeleton of criterion 1, run against a backend started by the Playwright config from a copied example project.

Tests: state-machine unit tests for every operation including cascades (removeNode cleans edges/inputs); form binding tests; Playwright flow above.

Absorbs: v0.5 plugin node kinds (registry entry + form falls back to generic fields) and schema evolution (the dropdown emits standard JSON Schema fragments; richer constructs arrive as registry-referenced Python models, not UI work).

Out of scope: drag-persisted layouts, undo/redo, multi-user locks, YAML text-mode editing (the JSON PUT body is the editing surface; hand-editing files remains the power path), subgraph drill-down editing (composites edit as flat child lists, recursion renders as one node, per v0.3), copy/paste of subtrees.
