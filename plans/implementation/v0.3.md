# v0.3 implementation plan

## Context

After v0.2 (per `implementation/v0.2.md`) the `ngen-weave` distribution ships four workspace packages: core (`Workflow` classes with import-time structural validation, explicit-listing discovery registry, thin YAML config, LangGraph engine, `RunStore`, human review artifacts, observers, content-addressed `ArtifactStore`, budget enforcement, agent harness), cli, server (FastAPI `RunService` with two implementations behind a shared conformance suite), and mcp (project-root `ngen-weave.json` manifest + workflow-as-tool registration). Nothing visual exists; runs are reachable but not visible.

v0.3 adds the read-only web surface: a faithful-in-structure read API served from the same process, a `ngen-weave ui` command, the separate `ngen-weave-web` SvelteKit repository (graph canvas, detail views, projects browsing, light/dark), and the start of the MkDocs docs site. No write capability of any kind; run state stays invisible.

Files touched:

- `packages/ngen-weave-core/src/ngen_weave/manifest.py` — **moved** from `packages/ngen-weave-mcp/src/ngen_weave_mcp/manifest.py`, extended with tolerant discovery
- `packages/ngen-weave-server/src/ngen_weave_server/` — **new modules** `readmodel.py`, `projects.py`, `api.py`; `app.py` extended
- `packages/ngen-weave-cli/src/ngen_weave_cli/main.py` — `ui` command
- `../ngen-weave-web/` — **new repository**, sibling checkout (SvelteKit + TypeScript + Svelte Flow + Tailwind + shadcn-svelte)
- `docs/`, `mkdocs.yml` — docs site start

Depends on: `releases/v0.3.md` (requirements), `product/PRD.md` (decision log, wins on conflict), and the module shapes defined in `implementation/v0.1.md` and `implementation/v0.2.md` (referenced, never restated). No design docs exist under `design/`; choices this plan makes get lifted there when those docs are written.

Conventions inherited from `implementation/v0.1.md` and applied to every backend step: Python ≥3.12, uv workspace, pytest, ruff, conventional commits, one commit per step unless stated, full suite green before committing (`uv run pytest`), tests next to code except e2e under `tests/e2e/`, no network in tests (`FakeProvider`). Frontend steps follow their own conventions, stated in Step 7: pnpm, Vitest, Playwright excluded until v0.4, conventional commits in the web repo, `pnpm lint && pnpm test && pnpm build` green before committing.

Global out of scope for every step (v0.3 non-goals per `releases/v0.3.md`): any mutation endpoint, run inspection of any kind, auth/multi-user/remote deployment, LLM-generated summaries, websockets/push, parallel-execution visualization, artifact diff previews, mobile beyond usable, internationalization, publishing either distribution.

---

## Goals

1. One read API, served by the existing `ngen-weave-server` app, exposing every registered workflow structurally faithfully: nodes with all fields, compiled edges with their branch maps (from the dry-run compile's topology), schemas, prompts, raw source, and a content hash per workflow.
2. Only validator-passing structures are ever served; workflows that fail still appear in the list, marked invalid with their full error list, via tolerant discovery.
3. `.ngen-weave/projects` artifact trees are browsable over HTTP with producing-node provenance attached to every blob.
4. `ngen-weave ui` starts one process serving both the API and the built web app.
5. The web repo renders list, canvas, details, and projects against that API alone, knows nothing ngen-weave-specific, and handles unknown node types generically so v0.5 plugins need no frontend rewrites.
6. Docs begin: MkDocs Material in the backend repo with an install-to-first-run quickstart.

## Success criteria

From `releases/v0.3.md`, verbatim in intent:

1. All workflows in a repo visible within two clicks of opening the app.
2. A ≤15-node workflow fully legible at typical laptop size without scrolling.
3. Any validation error findable from the list view.
4. Artifact trees under `.ngen-weave/projects` browsable with producing-node provenance shown.
5. Zero write capability; verified mechanically by asserting the FastAPI route table contains no mutating method.

## Abstractions and what they absorb

One sentence each; these are the load-bearing choices.

- **Tolerant discovery in core (`DiscoveryResult`)** absorbs new workflow sources (plugins at v0.5): each source contributes a `discover()` function returning the same result shape, and consumers never see partial failure.
- **The read-model serializer as one pure module (`readmodel.py`)** absorbs the v0.4 storage-format change: data-subset round-trip tightens inside one function pair, no route or frontend changes.
- **Dot-path schema keys (`"input"`, `"draft.output"`)** absorb new schema documents (nested composites, plugin node types): a new document is a new key in the same index endpoint, not a new route.
- **Derived edge-kind classification in the serializer** absorbs new routing forms (new observer actions, v0.5 policies): the classifier maps engine facts to kinds in one function and the wire format never grows a second spelling.
- **The frontend node-type registry with generic fallback** absorbs v0.5 plugin node types: a plugin ships one registry entry (badge text, color token, icon); unregistered types render through the fallback and remain fully navigable.
- **`summarize.ts` as pure template functions over the detail payload** absorbs richer prose later (LLM or authored descriptions): the component keeps consuming a `string[]` regardless of who produced it.
- **A hand-written typed API client as the only fetch path in the web repo** absorbs contract drift: every wire shape exists once, in `src/lib/api/types.ts`.

### Step 2 — Read-model serializer

`packages/ngen-weave-server/src/ngen_weave_server/readmodel.py`. Pure functions over `Workflow` classes; no FastAPI imports. This module defines the wire format for everything the UI sees, so the shapes below are the contract for Steps 4 and 8.

```python
def content_hash(detail: dict) -> str          # sha256 hex of canonical json.dumps(detail, sort_keys=True)
def list_entry(wf: type[Workflow]) -> dict     # list-view card
def workflow_detail(wf: type[Workflow],
                   run_config: dict | None,
                   source_text: str,
                   source_file: str) -> dict   # full structure
def schema_index(wf: type[Workflow]) -> dict[str, str]   # key -> title
def schema_document(wf: type[Workflow], key: str) -> dict # JSON Schema; KeyError -> caller maps to 404
```

`list_entry` shape:

```json
{"name": "...", "description": "...", "human_description": "...", "valid": true, "errors": null, "hash": "<sha256>"}
```

For invalid entries (built by the API layer in Step 4, not by this function):

```json
{"name": "<module path>", "description": "", "valid": false, "errors": ["<line>", ...], "hash": null}
```

`workflow_detail` shape — recursive over composites:

```json
{
  "name": "...", "description": "...", "node_type": "composite",
  "run_config": {"max_retries": 3, "retry_backoff_ms": 1000, "budget": null} ,
  "hash": "<sha256 of the detail minus the hash field>",
  "source": {"file": "examples/code_review/workflows.py", "text": "<entire module source>"},
  "children": [ <same shape, node_type worker/control/human/agent/composite> ],
  "edges": [ {"src": "...", "dst": "...", "branch": "pass"| "fail"| null, "kind": "..."} ],
  "inputs": {"<target-name>": {"<field>": "<reference string>"}},
  "input_key": "input", "output_key": "output"
}
```

Per-node fields, present on every node: `name`, `description`, `node_type`, `prompt` (rendered template string or null), `variant` (string or null), `artifacts` (tuple as list), `observers` (list of `{"name", "targets": [...]}`), `input_key`, `output_key`.

Field decisions made here so no later step weighs them:

- **Schema keys are dot paths.** `"input"` and `"output"` at the root; `"<child>.input"`, `"<inner.gate>.output"` deeper, segments joined by `.` following the v0.1 `node_path` convention. `schema_index` returns every key with the pydantic model's title; `schema_document` resolves a key by walking `children` and returns `model_json_schema()`. Unknown key raises `KeyError`.
- **Edge kinds are classified, not declared.** `classify_edge(edge, dst_node) -> "normal" | "control_pass" | "control_fail" | "human_route"`: branch set → control kind; else dst `node_type == "human"` → `human_route`; else `normal`.
- **Observer reroute edges are synthetic and best-effort.** Each observer entry's `targets` comes from scanning the predicate source with `ast` for `Reroute("<literal>")` calls; undetectable targets yield an empty list silently. Synthetic edges `{"src": <observed node>, "dst": target, "branch": null, "kind": "observer_reroute"}` are appended to `edges` for every detected target. This is presentation metadata, clearly marked by its kind; the engine never reads it.
- **`run_config` is the flat run-settings subset** (`max_retries`, `retry_backoff_ms`, `budget`) extracted from the project config when one exists and names this workflow; passed in by the API layer (Step 4). Null otherwise. The serializer does not touch the filesystem.
- **Source text is the whole declaring module**, read by the API layer via `inspect.getsourcefile`/`inspect.getsource`, passed in as parameters so this module stays pure and testable.
- **`hash` excludes itself**: compute the detail dict without `hash`, hash it, insert.

Tests (`test_readmodel.py`): build the canonical code-review-shaped fixture (worker, control, human, multi-parent fan-in node, observer) and assert the full detail dict; classify all five edge kinds including a synthetic reroute; schema index/document round trip including a nested composite key; unknown schema key raises `KeyError`; hash stability (same input, same hash; changed prompt, different hash).

Absorbs: the v0.4 storage tightening (raw representation joins `source` in this one module) and new node fields (one place adds them to the detail dict).

Out of scope: tolerant-parsing of broken definitions (invalid workflows never reach this module), prompt rendering against inputs (prompts ship as templates), any HTTP concern.

Verify: `uv run pytest packages/ngen-weave-server/src/ngen_weave_server/test_readmodel.py`.

Commit: `feat(server): structural read-model serializer with content hashes`

```python
    # unknown project or prefix -> KeyError;
    # sidecar files (<sha256>.json next to blobs) are hidden from listings and
```

Sidecar contract per v0.1 Step 11: `ArtifactStore.link_meta` writes JSON beside each blob containing the `ArtifactMeta` fields; `producer_node_path` reads `meta.node_path`. A blob without a readable sidecar gets `producer_node_path: None` and still lists (hand-placed files are legal).

Verify: `uv run pytest packages/ngen-weave-server/src/ngen_weave_server/test_projects.py`.

Commit: `feat(server): projects tree reader with producer provenance`

### Step 4 — Read API routes

`packages/ngen-weave-server/src/ngen_weave_server/api.py` plus a small `app.py` extension. Per the PRD, routes translate HTTP to the Step 2–3 modules and hold zero business logic.

`create_app` gains one parameter, `project_root: Path | None = None` (default cwd, after the existing v0.2 parameters). At startup the API builds its state once:

```python
@dataclass
class ReadState:
    project_root: Path
    projects_dir: Path          # project_root / ".ngen-weave" / "projects"
    discovery: DiscoveryResult  # from ngen_weave.manifest.discover_tolerant
    details: dict[str, dict]    # name -> workflow_detail(...), built eagerly
    run_configs: dict[str, dict | None]
```

Discovery source resolution, decided here: if `<project_root>/ngen-weave.json` exists, load it; otherwise synthesize `ProjectManifest(project=project_root.name, modules=())` and let the API additionally accept an explicit `modules: tuple[str, ...]` parameter on `create_app` (test and example convenience) merged into the manifest. Empty result is fine — the list is simply empty.

Run-config resolution: look for `ngw.yaml`, `ngw.yml`, `ngw.json` in `project_root` (first match); parse with `load_config`; if its workflow matches, pass the flat run-settings subset from Step 2. Parse failures leave `run_config` null; they are not surfaced as workflow errors.

Routes, all GET:

```
GET /api/workflows                         -> {"workflows": [<list_entry | invalid-entry>, ...]}
GET /api/workflows/{name}                  -> <workflow_detail>
GET /api/workflows/{name}/schemas          -> <schema_index>
GET /api/workflows/{name}/schemas/{key}    -> <JSON Schema document>
GET /api/projects                          -> {"projects": [str, ...]}
GET /api/projects/{project}                -> {"entries": [<TreeEntry>, ...]}
GET /api/projects/{project}/{path:path}    -> {"entries": [<TreeEntry>, ...]}   # prefix = path
```

Error mapping: unknown workflow name → 404 `{"error": {"type": "unknown_workflow", "message"}}`; unknown schema key or project/prefix → 404 same envelope; traversal `ValueError` → 400; everything else → 500. Invalid entries appear only in the list; requesting detail for one is a 404 whose message carries its collected errors (criterion 3's "one click away" resolves through the list payload's `errors` field).

Eager detail building at startup is deliberate: definitions are Python classes already in memory; recomputing per request buys nothing while polling makes responses hot. A restart picks up edited code.

Tests (`test_api.py`): drive the app with `httpx.AsyncClient(transport=ASGITransport(app))` over tmp examples — list contains valid and invalid entries with correct hashes and error texts; detail matches the Step 2 fixture; schema index and one document; projects listing with provenance; all four error cases; `modules=` fallback when no manifest file exists.

Absorbs: v0.4's editor, which inverts these exact shapes; new schema documents and node fields land in Step 2's module, never here.

Out of scope: CORS (localhost same-origin via the `ui` command; revisit with deployment at 1.0), caching headers beyond what polling hashes provide, partial/tolerant graph rendering, authentication.

Verify: `uv run pytest packages/ngen-weave-server/src/ngen_weave_server/test_api.py`.

Commit: `feat(server): read-only workflow and projects API`

### Step 10 — Graph canvas

`src/lib/graph/layout.ts`, `registries.ts`, and `src/lib/components/canvas/`; routed at `workflows/[name]/+page.svelte`, fed by `client.getWorkflow(name)`.

`layout.ts`: `layoutNodes(detail: WorkflowDetail): {nodes: Node[], edges: Edge[]}` — left-to-right `@dagrejs/dagre` layout, rank separation fixed constants tuned once; cycles cannot occur (structural validation forbids them), so no back-edge handling; synthetic `observer_reroute` edges are laid out but drawn dashed.

`registries.ts` — the v0.5 plugin seam:

```typescript
const nodeTypeRegistry: Record<string, {label: string; colorVar: string}> = {
  worker: ..., control: ..., human: ..., agent: ..., composite: ...
}
export function nodeStyle(t: string) { return nodeTypeRegistry[t] ?? GENERIC }
const GENERIC = { label: t => t, colorVar: "--color-muted" }  // unknown types render labeled, dimmed, fully clickable
const edgeKindRegistry: Record<EdgeKind, {colorVar: string; dashed: boolean}>
```

## Amendments to earlier plans

Kept explicit, following the convention `implementation/v0.1.md` set, so nobody hunts for hidden coupling:

1. **`ngen_weave.manifest`** (v0.2 Step 7): the module moves from `ngen-weave-mcp` to core unchanged; `ngen_weave_mcp.manifest` becomes a re-export shim. `discover_workflows` is redefined as `discover_tolerant(strict=True)` restricted to its original return type; its behavior, including duplicate-name errors, is identical and proven by the untouched v0.2 tests.
2. **No other earlier module changes.** `RunService`/`RunFile`, `Engine`, `Workflow` classes, `Observer`, `ArtifactStore`, and the config layer are consumed read-only or not at all. If implementation of these steps appears to require editing any of them beyond the shim above, stop: that is a sign the read model is leaking into core, and the fix belongs in `readmodel.py`.
3. **Known limitation accepted**: observer reroute targets come from an AST scan of predicate source and are silently empty for lambdas/closures. Core's `Observer` abstraction is not changed to declare targets statically; revisit only if the canvas proves unreadable without them.
