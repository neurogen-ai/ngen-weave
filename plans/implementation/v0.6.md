# v0.6 implementation plan

## Context

After v0.5 (per `implementation/v0.5.md`) ngen-weave is extensible (plugins, notification reference plugins, boxed agent autonomy), but every byte of state lives in files under `.ngen-weave/`: `RunStore` writes one `run.json` per run, `DefinitionStore` writes definition files, and `VersionLog` writes sidecar manifests next to content-addressed blobs.

v0.6 adds the platform layer and nothing else: Postgres becomes the canonical store for run state, provenance records, artifact manifests, and workflow registrations (blobs stay content-addressed on disk, joined by hash), with SQLAlchemy 2.0 async and Alembic from day one while file mode remains the zero-config local default. Auth, roles, multi-reviewer human nodes, tickets, and `import-project` are v0.8; identity work never entangles with this migration.

Files touched:

- `packages/ngen-weave-core/src/ngen_weave/db/` (**new**): engine factory, ORM tables, Postgres store implementations, Alembic environment under `packages/ngen-weave-core/alembic/`
- `packages/ngen-weave-core/src/ngen_weave/engine/store.py`, `runner.py`: async store protocols, backend selection, Postgres checkpointer
- `packages/ngen-weave-core/src/ngen_weave/definitions.py`, `versions.py` (`artifacts.py`), `notify.py`: async conversion, DB-backed variants
- `packages/ngen-weave-core/src/ngen_weave/export.py` (**new**): the single-file run-JSON writer extracted to one function
- `packages/ngen-weave-server/src/ngen_weave_server/app.py`, `api.py`, `service.py`, `client.py`: backend selection
- `packages/ngen-weave-cli/src/ngen_weave_cli/context.py`, `main.py`: backend selection, `export-run`

Depends on: `releases/v0.6.md` (requirements), `product/PRD.md` (decision log, wins on conflict), and module shapes fixed by `implementation/v0.1.md` through `implementation/v0.5.md` (referenced, never restated). No design docs exist under `design/`; choices this plan makes get lifted there when those docs are written.

Conventions inherited from `implementation/v0.1.md` (backend) and `implementation/v0.3.md` Step 7 (web): Python ≥3.12, uv workspace, pytest, ruff, conventional commits, one commit per step unless stated, full suite green before committing, tests next to code except e2e under `tests/e2e/`, `FakeProvider`/fakes in tests, no network (live-marked exceptions only). Web repo: pnpm, Vitest, Playwright, `pnpm lint && pnpm test && pnpm build` green before committing.

Global out of scope for every step (per `releases/v0.6.md` non-goals): multi-tenancy beyond projects-per-user, SSO/OIDC federation, live collaborative editing, distributed execution, object-storage blob backends beyond the disk layout (hash-keyed paths already tolerate them), API semver (that is 1.0), dropping file mode.

---

## Goals

1. A server deployment pointed at an empty Postgres database reaches working state through `alembic upgrade head` alone: runs, records, definitions, and artifact versions all live in Postgres; artifact blobs stay on disk keyed by sha256.
2. File mode survives untouched as the default: `ngen-weave run` with no `database:` config behaves exactly as v0.5, still zero-config.
3. Any run in either backend exports to the pre-v0.6 single-file run-JSON shape through one shared writer.

## Success criteria

From `releases/v0.6.md`, verbatim in intent:

1. A fresh server deployment runs against empty Postgres with Alembic up-migrations only; no manual schema steps.
2. Run-JSON export parity across both backends through the single writer.
3. File mode unchanged: every pre-v0.6 suite green without a database or config change.

## Abstractions and what they absorb

One sentence each; these are the load-bearing choices.

- **One `database:` config key resolving to a store-construction site per store kind** absorbs future backends (object-storage manifests, a hosted Postgres): each store's factory lives in one place, callers keep taking the abstract store they already take.
- **Async method signatures on the store protocols, converted once in Step 2** absorbs the Postgres backend without a second ripple later: after Step 2 no caller cares whether IO is files or wire.
- **The record table storing payloads verbatim as JSONB keyed by ordinal** absorbs schema churn in provenance records through 1.0 (guaranteed by the PRD): record-shape changes touch nothing but the existing dataclasses, never a migration.
- **`dump_run_json(run: RunFile) -> bytes` as the single serializer** absorbs export-format questions forever: the file store's atomic writes and the DB export path emit byte-identical output because there is exactly one writer.

## Commit sequence

### Step 1: Database foundation: engine factory, tables, initial migration

`packages/ngen-weave-core/src/ngen_weave/db/` (new: `__init__.py`, `engine.py`, `tables.py`) and `packages/ngen-weave-core/alembic/` (new). No store implementations yet; this step is schema and connection machinery only.

Dependencies added to `ngen-weave-core`: `sqlalchemy[asyncio]>=2.0`, `asyncpg`, `alembic`, `psycopg[binary]` (sync driver used by Alembic), `greenlet` (comes with SQLAlchemy async). Dev deps: `aiosqlite` (portable unit-test backend).

```python

    # env["NGW_DATABASE_URL"] wins; else config.database.get("url"); else None (file mode)
```

Config (`config.py`): optional top-level key `database:` accepting exactly `{url: str}`; unknown keys rejected as usual; `ResolvedConfig` gains `database: dict = {}`.

Tables (`db/tables.py`, declarative `Base`), decided here and created by migration `0001_initial`. Auth/role/ticket tables do not exist yet — they arrive with v0.8's migrations; this release's schema holds only what v0.6 itself serves:

- `runs`: `run_id` str PK, `workflow` str, `status` str, `input` JSONB, `output` JSONB null, `error` JSONB null, `waiting` JSONB null, `roles` JSONB null, `budget` JSONB null, `budget_override` JSONB null, `notes` JSONB, `started_at` str null, `created_at` timestamptz server-default now, `updated_at` timestamptz onupdate. Columns mirror the `RunFile` field-for-field; anything not listed here rides inside the JSONB columns already carrying it.
- `records`: `seq` BigInteger identity PK, `run_id` FK runs.run_id on delete cascade, `ordinal` int (position in the stream, unique with run_id), `kind` str, `ts` str, `payload` JSONB, `source` str null. Payloads are stored verbatim; the dataclasses in `provenance.py` remain the only schema authority.
- `definitions`: `name` str PK, `definition_hash` str, `text` text, `origin` str, `updated_at`.
- `artifact_versions`: `project` str, `name` str, `version` int, `sha256` str, `ts` str, `run_id` str, `node_path` str; PK `(project, name, version)`. Blob bytes stay out of the database permanently (release-doc rule); hash is the join key to disk.
- `notify_state`: `rule_name` str, `run_id` str, `fired_at`; PK `(rule_name, run_id)`: the dispatcher's dedupe state when running against the DB.

Alembic layout: `alembic.ini` at `packages/ngen-weave-core/`, `alembic/env.py` reading `to_sync_url(os.environ["NGW_DATABASE_URL"])`, `alembic/versions/0001_initial.py` creating every table above. Async application code never runs Alembic; deployment runs the CLI (`Step 4` wires `ngen-weave db upgrade`).

Tests (`db/test_engine.py`, `db/test_migrations.py`): url resolution precedence (env over config over None); `to_sync_url` mapping; migration test runs `upgrade head` against an empty **Postgres** database when `NGW_TEST_DATABASE_URL` is set (marked `live`, skipped otherwise) and asserts every table exists; a parallel `sqlite+aiosqlite` variant runs `Base.metadata.create_all` so repo unit tests (Steps 3–4) have a no-network backend with identical DDL.

Out of scope: any store reading or writing these tables (Steps 3–4), seeding data, connection-pool tuning, downgrade paths beyond Alembic's generated stub.

Verify: `uv run pytest src/ngen_weave/db/ src/ngen_weave/test_config.py`; with docker available: `NGW_TEST_DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/ngw_test uv run pytest -m live src/ngen_weave/db/test_migrations.py`.

Commit: `feat(core): database foundation with sqlalchemy models and initial migration`

### Step 2: Store seam goes async: one mechanical conversion, no behavior change

`packages/ngen-weave-core/src/ngen_weave/engine/store.py`, `runner.py`, `definitions.py`, `artifacts.py` (VersionLog), `notify.py`, and every caller (`LocalRunService`, `NotificationDispatcher.scan_once`, CLI context, MCP wiring). This step exists so the Postgres backends land in Steps 3–4 with zero call-site ripple.

Contract changes, applied mechanically:

- `RunStore` renames to `FileRunStore` with `RunStore = FileRunStore` alias kept for one release; all seven methods become `async def` (`create`, `load`, `save`, `append`, `list`). Bodies keep the existing sync file logic inline (small atomic file ops; no threading needed).
- `DefinitionStore` (`load`, `save`, `list`) and `VersionLog` (`append`, `entries`): `async def`, same bodies.
- A formal protocol lands in `engine/store.py` so Steps 3–4 implement against it, not against the concrete class:

```python
class RunRepo(Protocol):
    async def create(self, workflow_name: str, input_dump: dict) -> str: ...
    async def load(self, run_id: str) -> RunFile: ...
    async def save(self, run_file: RunFile) -> None: ...
    async def append(self, run_id: str, record: ProvenanceRecord) -> None: ...
    async def list(self) -> list[RunFile]: ...
```

- Callers updated: `Engine`, `LocalRunService`, `HttpRunService` (unchanged signatures, just awaited internals), `NotificationDispatcher.scan_once` becomes `async def scan_once`, CLI commands awaiting the coroutine equivalents, `readmodel` loaders. No signature visible outside these modules changes except sync→async.
- Deliberately untouched: `RunFile` data shapes, atomic-write mechanics, provenance emission, error types, all file formats.

Tests: none new. The entire existing suite must pass unmodified except adding `await` where the fixtures drive stores directly; if any test needed a behavioral change, this step did something wrong; stop and revert the offending edit.

Absorbs: the whole Postgres rollout (no second conversion ever) and any future remote store.

Out of scope: any Postgres code (Step 3), renaming public aliases beyond the one kept, batching writes, write-behind caching.

Verify: `uv run pytest -m 'not live' && uv run ruff check .`, identical results to Step 1's baseline.

Commit: `refactor(core): store protocols go async ahead of the postgres backend`

### Step 3: PgRunStore: runs and provenance records in Postgres

`packages/ngen-weave-core/src/ngen_weave/db/stores.py` (new) plus backend selection at the two construction sites.

```python
class PgRunStore:
    """RunRepo over the runs + records tables. One session per method call."""
    def __init__(self, sessionmaker: async_sessionmaker[AsyncSession]) -> None
    # methods match RunRepo exactly; semantics identical to FileRunStore:
    # create -> uuid4 id, initial row + format envelope implied by schema, not stored
    # append -> INSERT with ordinal = max(existing)+1 in the same transaction
    # save  -> UPDATE row; load -> SELECT row + records ordered by ordinal, rehydrated into RunFile
    # list  -> SELECT all rows ordered by created_at, records NOT loaded (summaries only,
    #          matching FileRunStore.list's contract of headers without the stream)
```

Rehydration rule, fixed here: `RunFile.records` is rebuilt from the `records` table on `load`; `save` diffs nothing and simply rewrites non-record fields (records are insert-only through `append`, matching the file store's invariant that only `append` touches the stream).

Selection, in exactly two places:

- CLI: `ngen_weave_cli/context.py` `_build_engine` gains, after config resolution, `url = resolve_database_url(config, os.environ)`; when set, build the engine/sessionmaker and construct `PgRunStore`, PG `DefinitionStore`/`VersionLog` variants (Step 4 stubs them as falling through to file implementations until written), and the Postgres LangGraph checkpointer; when unset, current classes, current arguments, byte-identical behavior.
- Server: `create_app(..., database_url: str | None = None)`; resolution order `database_url` argument → env → config, then the same branch. The app exposes the resolved mode on `app.state.store_mode` ("file" | "postgres") for diagnostics and tests.

Checkpointer: when Postgres mode is active, the engine's LangGraph checkpointer becomes `AsyncPostgresSaver` (langgraph-checkpoint-postgres dev-added to core) using the same URL; thread id stays the run id (v0.2 identity-mapping decision, unchanged). SQLite/memory remain the file-mode checkpointers.

Startup guard: in Postgres mode, `_build_engine` and `create_app` verify the `runs` table exists (one `SELECT 1 FROM runs LIMIT 1` in startup) and raise `InfraError("database not migrated; run: ngen-weave db upgrade")` on failure: loud, actionable, per the PRD's fail-loudly tradition.

CLI plumbing for that message lands here minimally: `ngen-weave db upgrade` shell command invoking Alembic programmatically (`alembic.config.Config` + `command.upgrade(head)`) with the resolved sync URL.

Tests (`db/test_run_store_pg.py`): the v0.2 conformance idea applied to storage: one parametrized suite driving `create/load/save/append/list` round trips, crash-consistency (kill between append and save: last `save` state plus all appended records survive), record ordering, and `list` summary contract against both `FileRunStore` (tmp dir) and `PgRunStore` (sqlite+aiosqlite sessionmaker). A live-marked variant repeats the suite under real Postgres when `NGW_TEST_DATABASE_URL` is set.

Absorbs: future run-store backends (implement `RunRepo`, register in the two selection sites) and schema evolution within the JSONB payload policy (dataclass change only).

Out of scope: definitions/versions/notify-state tables being *written* (Step 4; selection sites may reference them only as pass-throughs to the file implementations until then), connection pooling configuration surface, read replicas, full-text search over records.

Verify: `uv run pytest src/ngen_weave/db/ packages/ngen-weave-server/ packages/ngen-weave-cli/tests/ -m 'not live'`; manual: point `NGW_DATABASE_URL` at an empty database, run `uv run ngen-weave db upgrade && uv run ngen-weave run code_review …`, confirm rows in `runs`/`records` and a completed status.

Commit: `feat(core,server): pg run store behind the async repo protocol`

### Step 4: Remaining repos in Postgres: definitions, artifact versions, notify state

Extends `db/stores.py` with three small classes and completes the selection branches from Step 3.

```python
class PgDefinitionStore:    # definitions table; methods match DefinitionStore
class PgVersionLog:         # artifact_versions table; methods match VersionLog;
                            # constructor takes (sessionmaker, project: str)
class PgNotifyState:        # notify_state table; replaces the dispatcher's JSON state file
```

Decisions:

- The dispatcher constructor parameter `state_path: Path` widens to `state: Path | PgNotifyState` via a tiny `NotifyState` protocol (`async def fired(rule, run_id) -> bool`, `async def mark_fired(rule, run_id)`); `FileNotifyState` is the JSON-file behavior extracted verbatim from today's inline code, `PgNotifyState` implements the same two methods over the table. The dispatcher learns nothing else about either.
- `ArtifactStore` itself does not move: blobs stay content-addressed on disk in Postgres mode too, exactly as in file mode, with the same configured root (release-doc rule). Only the manifests/versions join the database; the sha256 join key needs no path changes anywhere.
- Selection sites from Step 3 swap their pass-throughs for these classes when the URL is set. Nothing else in the codebase branches on backend, grep-enforced by a test asserting `db.stores` is the only module importing both `sqlalchemy` and any store protocol.
- Multi-project note: `PgVersionLog` carries `project` because the table is keyed by it; file-mode `VersionLog` derives the project from its directory layout as today. The `project` value comes from the same config field both modes already read.

Tests (`db/test_repos_pg.py`): each class against sqlite+aiosqlite, mirroring its file-mode suite's cases (definition round trip + collision, version ordering + crash safety, notify fire-once across restart); dispatcher test with `PgNotifyState` firing once and surviving a restart; live-marked repetition under real Postgres.

Absorbs: object-storage manifests later (another `VersionLog` implementation), additional dispatcher state (fields on the state protocol).

Out of scope: blob bytes in the database, serving definitions from both backends simultaneously, migrating live file-mode projects automatically (that is `import-project`, v0.8 Step 6; a v0.5 file-mode project upgrades by running it too), backup tooling.

Verify: `uv run pytest src/ngen_weave/ packages/ngen-weave-server/ packages/ngen-weave-cli/tests/ -m 'not live'`.

Commit: `feat(core): postgres repos for definitions, versions, notify state`

### Step 5: One run-JSON writer, export parity

`packages/ngen-weave-core/src/ngen_weave/export.py` (new), `FileRunStore` touched only to call it, one CLI verb.

Today the single-file run-JSON format exists implicitly inside `FileRunStore.save`'s serialization. This step makes it explicit so both backends and the importer share it:

```python
def dump_run_json(run: RunFile) -> bytes
    # the exact bytes FileRunSave wrote through v0.5: json.dumps of the RunFile
    # envelope (format, run_id, workflow, status, input, output, error, records, ...)
    # with the established key order and defaults handling moved here verbatim
def load_run_json(data: bytes) -> RunFile     # inverse; tolerant of missing defaulted keys
```

Changes:

- `FileRunStore.save` serializes through `dump_run_json` and writes those bytes atomically; no byte changes anywhere (the existing file-format tests prove it).
- `PgRunStore` gains `async def export(self, run_id: str) -> bytes` returning `dump_run_json(await self.load(run_id))`; add `export` to the `RunRepo` protocol with a `FileRunStore` implementation (load then dump).
- API: `GET /api/runs/{run_id}/export` in `api.py` serves those bytes as `application/json`, unknown run → 404. (`GET /runs/{run_id}` keeps returning the parsed dict as today; the export route guarantees the canonical serialized form.)
- CLI: `ngen-weave export-run <run-id> [--out PATH]` over the configured store; stdout when `--out` omitted.

Byte-compatibility statement, tested not promised: for every shipped example workflow, the bytes written by a v0.5-era fixture file equal `dump_run_json(load(v0.5_file))`; the fixture corpus copied into the test guards the "byte-compatible with the pre-DB writer where practical" clause, with any unavoidable divergence asserted explicitly and commented.

Tests (`test_export.py` + extensions): dump/load round trip on the fixture corpus; `FileRunStore.save` output unchanged against recorded bytes; `PgRunStore.export` equals `FileRunStore` export for an identical run constructed through each backend; export route 200/404; CLI smoke.

Absorbs: reproducibility handoffs (one writer), Argo-era exporters (pure functions over `RunFile`), format evolution through 1.0 (one place).

Out of scope: PROV-JSON (exists since v0.4, untouched), exporting definitions or artifacts alongside (a run export stays the single run file, matching the pre-v0.6 shape), streaming/chunked export.

Verify: `uv run pytest src/ngen_weave/test_export.py src/ngen_weave/engine/ packages/ngen-weave-server/src/ngen_weave_server/test_run_api.py && uv run ngen-weave export-run --help`.

Commit: `feat(core,cli): single run-json writer shared by both stores`

## Amendments to earlier plans

Kept explicit, per the convention earlier plans set:

1. **`RunStore`, `DefinitionStore`, `VersionLog`, notify state** (v0.1 Steps 7/11, v0.4, v0.5 Step 10): all go async in Step 2 with identical semantics; `RunStore` gains the `RunStore = FileRunStore` alias and an `export` method (Step 5). File formats unchanged.
2. **`NotificationDispatcher`** (v0.5 Step 6): `scan_once` becomes async; `state_path` generalizes to a `NotifyState` protocol (Step 4); rule/fingerprint logic untouched.
3. **`config.ResolvedConfig`** (v0.1 Step 5, widened since): gains `database: dict` (Step 1). Unknown-key rejection rules apply as always.
4. **`create_app`** (v0.2 Step 3, widened since): gains `database_url` keyword (Step 3); defaulted, file-mode open-local behavior preserved.
5. **LangGraph checkpointer choice** (v0.1 Step 7): Postgres mode selects `AsyncPostgresSaver`; thread-id-equals-run-id stands.
6. **No earlier-module semantic changes.** If a step appears to alter validation, provenance emission, artifact addressing, or the schema representation, stop: the JSONB payload policy exists precisely so record and envelope shapes evolve without touching this release's schema again.
