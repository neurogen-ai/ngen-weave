# v0.6 implementation plan

## Context

After v0.5 (per `implementation/v0.5.md`) ngen-weave is extensible and collaborative (plugins, notifications, multi-reviewer human nodes, run-scoped roles, tickets, boxed agent autonomy), but every byte of state lives in files under `.ngen-weave/`: `RunStore` writes one `run.json` per run, `DefinitionStore` writes definition files, `VersionLog` writes sidecar manifests next to content-addressed blobs, `TicketStore` writes a `tickets.json` sidecar, and the deployed server implicitly trusts whoever can reach it (identity is the unverified `X-Ngw-Actor` header from v0.5 Step 9).

v0.6 adds the platform layer: Postgres becomes the canonical store for run state, provenance records, artifact manifests, workflow registrations, and tickets/roles (blobs stay content-addressed on disk, joined by hash), with SQLAlchemy 2.0 async and Alembic from day one while file mode remains the zero-config local default; then token auth on every API and MCP request, then project-level owner/reviewer/observer roles replacing implicit localhost trust.

Files touched:

- `packages/ngen-weave-core/src/ngen_weave/db/` (**new**): engine factory, ORM tables, Postgres store implementations, Alembic environment under `packages/ngen-weave-core/alembic/`
- `packages/ngen-weave-core/src/ngen_weave/engine/store.py`, `runner.py`: async store protocols, backend selection, Postgres checkpointer
- `packages/ngen-weave-core/src/ngen_weave/definitions.py`, `versions.py` (`artifacts.py`), `tickets.py`, `notify.py`: async conversion, DB-backed variants
- `packages/ngen-weave-core/src/ngen_weave/export.py` (**new**): the single-file run-JSON writer extracted to one function
- `packages/ngen-weave-core/src/ngen_weave/auth.py` (**new**): principals, token hashing, role matrix
- `packages/ngen-weave-server/src/ngen_weave_server/app.py`, `api.py`, `service.py`, `client.py`: auth dependency, principal plumbing, backend selection
- `packages/ngen-weave-cli/src/ngen_weave_cli/context.py`, `main.py`: backend selection, `import-project`, `export-run`, `user add/list`
- `packages/ngen-weave-mcp/src/ngen_weave_mcp/`: bearer-token support on the HTTP transport
- `../ngen-weave-web/`: login/token entry, 401/403 handling (small)

Depends on: `releases/v0.6.md` (requirements), `product/PRD.md` (decision log, wins on conflict), and module shapes fixed by `implementation/v0.1.md` through `implementation/v0.5.md` (referenced, never restated). No design docs exist under `design/`; choices this plan makes get lifted there when those docs are written.

Conventions inherited from `implementation/v0.1.md` (backend) and `implementation/v0.3.md` Step 7 (web): Python ≥3.12, uv workspace, pytest, ruff, conventional commits, one commit per step unless stated, full suite green before committing, tests next to code except e2e under `tests/e2e/`, `FakeProvider`/fakes in tests, no network (live-marked exceptions only). Web repo: pnpm, Vitest, Playwright, `pnpm lint && pnpm test && pnpm build` green before committing.

Global out of scope for every step (per `releases/v0.6.md` non-goals): multi-tenancy beyond projects-per-user, SSO/OIDC federation, live collaborative editing, distributed execution, object-storage blob backends beyond the disk layout (hash-keyed paths already tolerate them), API semver (that is 1.0), dropping file mode.

## Goals

1. A server deployment pointed at an empty Postgres database reaches working state through `alembic upgrade head` alone: runs, records, definitions, artifact versions, tickets, users, and project roles all live in Postgres; artifact blobs stay on disk keyed by sha256.
2. File mode survives untouched as the default: `ngen-weave run` with no `database:` config behaves exactly as v0.5, still zero-config.
3. Any run in either backend exports to the pre-v0.6 single-file run-JSON shape through one shared writer, and `ngen-weave import-project <dir>` loads a pre-v0.6 project directory into Postgres so its runs, provenance, and artifacts are fully addressable afterward.
4. Every mutating API and MCP request requires a bearer token issued per user; unauthenticated requests get 401 before any handler logic runs.
5. Project-level roles (owner, reviewer, observer) gate the service boundary: owners launch, cancel, edit workflows, install plugins, and manage roles; reviewers additionally answer reviews; observers read.

## Success criteria

From `releases/v0.6.md`, verbatim in intent:

1. A fresh server deployment runs against empty Postgres with Alembic up-migrations only; no manual schema steps.
2. A pre-v0.6 project directory imports cleanly: runs, provenance, artifacts all addressable after import, and export back to JSON matches the original file's semantics.
3. An unauthenticated request to any mutating endpoint is rejected; a reviewer-role token can answer reviews but cannot launch workflows.

## Abstractions and what they absorb

One sentence each; these are the load-bearing choices.

- **One `database:` config key resolving to a store-construction site per store kind** absorbs future backends (object-storage manifests, a hosted Postgres): each store's factory lives in one place, callers keep taking the abstract store they already take.
- **Async method signatures on the store protocols, converted once in Step 2** absorbs the Postgres backend without a second ripple later: after Step 2 no caller cares whether IO is files or wire.
- **The record table storing payloads verbatim as JSONB keyed by ordinal** absorbs schema churn in provenance records through 1.0 (guaranteed by the PRD): record-shape changes touch nothing but the existing dataclasses, never a migration.
- **`dump_run_json(run: RunFile) -> bytes` as the single serializer** absorbs export-format questions forever: the file store's atomic writes and the DB export path emit byte-identical output because there is exactly one writer.
- **`Principal(name, role)` resolved at the HTTP boundary and passed as one value** absorbs SSO/OIDC later: federation swaps the resolver, not the enforcement points, which see only `Principal`.
- **One `require_role(principal, action)` matrix in `auth.py`, called nowhere else** absorbs new gated actions and role tweaks: the matrix is one function, extending v0.5's `require_actor` pattern upward from runs to projects.
- **Tokens stored only as sha256 hashes** absorbs rotation and revocation cheaply: issuance and verification are the only two functions that touch token material.

- `users`: `name` str PK, `token_hash` str unique, `created_at`.

### Step 2: Store seam goes async: one mechanical conversion, no behavior change

`packages/ngen-weave-core/src/ngen_weave/engine/store.py`, `runner.py`, `tickets.py`, `definitions.py`, `artifacts.py` (VersionLog), `notify.py`, and every caller (`LocalRunService`, `NotificationDispatcher.scan_once`, CLI context, MCP wiring). This step exists so the Postgres backends land in Steps 3–4 with zero call-site ripple.

Contract changes, applied mechanically:

- `RunStore` renames to `FileRunStore` with `RunStore = FileRunStore` alias kept for one release; all seven methods become `async def` (`create`, `load`, `save`, `append`, `list`). Bodies keep the existing sync file logic inline (small atomic file ops; no threading needed).
- `TicketStore`: `list`, `append`, `close` become `async def`; same bodies.
- `DefinitionStore` (`load`, `save`, `list`) and `VersionLog` (`append`, `entries`): `async def`, same bodies.
- A formal protocol lands in `engine/store.py` so Steps 3–4 implement against it, not against the concrete class:

```python
class RunRepo(Protocol):
    async def create(self, workflow_name: str, input_dump: dict) -> str: ...
    async def load(self, run_id: str) -> RunFile: ...
    async def save(self, run_file: RunFile) -> None: ...
    async def append(self, run_id: str, record: ProvenanceRecord) -> None: ...
    async def list(self) -> list[RunFile]: ...

class TicketRepo(Protocol):
    async def list(self, run_id: str) -> list[Ticket]: ...
    async def append(self, run_id: str, title: str, role: str, created_by: str) -> Ticket: ...
    async def close(self, run_id: str, ticket_id: str, actor: str) -> Ticket: ...
```

- Callers updated: `Engine`, `LocalRunService`, `HttpRunService` (unchanged signatures, just awaited internals), `NotificationDispatcher.scan_once` becomes `async def scan_once`, `assign_role`, ticket routes, CLI commands awaiting the coroutine equivalents, `readmodel` loaders. No signature visible outside these modules changes except sync→async.
- Deliberately untouched: `RunFile`/`Ticket` data shapes, atomic-write mechanics, provenance emission, error types, all file formats.

Tests: none new. The entire existing suite must pass unmodified except adding `await` where the fixtures drive stores directly; if any test needed a behavioral change, this step did something wrong; stop and revert the offending edit.

Absorbs: the whole Postgres rollout (no second conversion ever) and any future remote store.

Out of scope: any Postgres code (Step 3), renaming public aliases beyond the one kept, batching writes, write-behind caching.

Verify: `uv run pytest -m 'not live' && uv run ruff check .`, identical results to Step 1's baseline.

Commit: `refactor(core): store protocols go async ahead of the postgres backend`

### Step 3: PgRunStore: runs and provenance records in Postgres

`packages/ngen-weave-core/src/ngen_weave/db/stores.py` (new) plus backend selection at the two construction sites.

```python
class PgRunStore:
    """RunRepo over the runs + records tables. One session per method call."""
    def __init__(self, sessionmaker: async_sessionmaker[AsyncSession]) -> None
    # methods match RunRepo exactly; semantics identical to FileRunStore:
    # create -> uuid4 id, initial row + format envelope implied by schema, not stored
    # append -> INSERT with ordinal = max(existing)+1 in the same transaction
    # save  -> UPDATE row; load -> SELECT row + records ordered by ordinal, rehydrated into RunFile
    # list  -> SELECT all rows ordered by created_at, records NOT loaded (summaries only,
    #          matching FileRunStore.list's contract of headers without the stream)
```

Rehydration rule, fixed here: `RunFile.records` is rebuilt from the `records` table on `load`; `save` diffs nothing and simply rewrites non-record fields (records are insert-only through `append`, matching the file store's invariant that only `append` touches the stream).

Selection, in exactly two places:

- CLI: `ngen_weave_cli/context.py` `_build_engine` gains, after config resolution, `url = resolve_database_url(config, os.environ)`; when set, build the engine/sessionmaker and construct `PgRunStore`, PG `DefinitionStore`/`VersionLog`/`TicketStore` variants (Step 4 stubs them as falling through to file implementations until written), and the Postgres LangGraph checkpointer; when unset, current classes, current arguments, byte-identical behavior.
- Server: `create_app(..., database_url: str | None = None)`; resolution order `database_url` argument → env → config, then the same branch. The app exposes the resolved mode on `app.state.store_mode` ("file" | "postgres") for diagnostics and tests.

Checkpointer: when Postgres mode is active, the engine's LangGraph checkpointer becomes `AsyncPostgresSaver` (langgraph-checkpoint-postgres dev-added to core) using the same URL; thread id stays the run id (v0.2 identity-mapping decision, unchanged). SQLite/memory remain the file-mode checkpointers.

Startup guard: in Postgres mode, `_build_engine` and `create_app` verify the `runs` table exists (one `SELECT 1 FROM runs LIMIT 1` in startup) and raise `InfraError("database not migrated; run: ngen-weave db upgrade")` on failure: loud, actionable, per the PRD's fail-loudly tradition.

CLI plumbing for that message lands here minimally: `ngen-weave db upgrade` shell command invoking Alembic programmatically (`alembic.config.Config` + `command.upgrade(head)`) with the resolved sync URL.

Tests (`db/test_run_store_pg.py`): the v0.2 conformance idea applied to storage: one parametrized suite driving `create/load/save/append/list` round trips, crash-consistency (kill between append and save: last `save` state plus all appended records survive), record ordering, and `list` summary contract against both `FileRunStore` (tmp dir) and `PgRunStore` (sqlite+aiosqlite sessionmaker). A live-marked variant repeats the suite under real Postgres when `NGW_TEST_DATABASE_URL` is set.

Absorbs: future run-store backends (implement `RunRepo`, register in the two selection sites) and schema evolution within the JSONB payload policy (dataclass change only).

Out of scope: definitions/versions/tickets/notify-state tables being *written* (Step 4; selection sites may reference them only as pass-throughs to the file implementations until then), connection pooling configuration surface, read replicas, full-text search over records.

Verify: `uv run pytest src/ngen_weave/db/ packages/ngen-weave-server/ packages/ngen-weave-cli/tests/ -m 'not live'`; manual: point `NGW_DATABASE_URL` at an empty database, run `uv run ngen-weave db upgrade && uv run ngen-weave run code_review …`, confirm rows in `runs`/`records` and a completed status.

Commit: `feat(core,server): pg run store behind the async repo protocol`

### Step 4: Remaining repos in Postgres: definitions, artifact versions, tickets, notify state

Extends `db/stores.py` with four small classes and completes the selection branches from Step 3.

```python
class PgDefinitionStore:    # definitions table; methods match DefinitionStore
class PgVersionLog:         # artifact_versions table; methods match VersionLog;
                            # constructor takes (sessionmaker, project: str)
class PgTicketStore:        # tickets table; methods match TicketRepo
class PgNotifyState:        # notify_state table; replaces the dispatcher's JSON state file
```

Decisions:

- The dispatcher constructor parameter `state_path: Path` widens to `state: Path | PgNotifyState` via a tiny `NotifyState` protocol (`async def fired(rule, run_id) -> bool`, `async def mark_fired(rule, run_id)`); `FileNotifyState` is the JSON-file behavior extracted verbatim from today's inline code, `PgNotifyState` implements the same two methods over the table. The dispatcher learns nothing else about either.
- `ArtifactStore` itself does not move: blobs stay content-addressed on disk in Postgres mode too, exactly as in file mode, with the same configured root (release-doc rule). Only the manifests/versions join the database; the sha256 join key needs no path changes anywhere.
- Selection sites from Step 3 swap their pass-throughs for these classes when the URL is set. Nothing else in the codebase branches on backend, grep-enforced by a test asserting `db.stores` is the only module importing both `sqlalchemy` and any store protocol.
- Multi-project note: `PgVersionLog` carries `project` because the table is keyed by it; file-mode `VersionLog` derives the project from its directory layout as today. The `project` value comes from the same config field both modes already read.

Tests (`db/test_repos_pg.py`): each class against sqlite+aiosqlite, mirroring its file-mode suite's cases (definition round trip + collision, version ordering + crash safety, ticket idempotent close, notify fire-once across restart); dispatcher test with `PgNotifyState` firing once and surviving a restart; live-marked repetition under real Postgres.

Absorbs: object-storage manifests later (another `VersionLog` implementation), external tracker bridges (consume `TicketRepo`, unchanged), additional dispatcher state (fields on the state protocol).

Out of scope: blob bytes in the database, serving definitions from both backends simultaneously, migrating live file-mode projects automatically (that is `import-project`, Step 6, for pre-v0.6 directories; a v0.5 file-mode project upgrades by running `import-project` too), backup tooling.

Verify: `uv run pytest src/ngen_weave/ packages/ngen-weave-server/ packages/ngen-weave-cli/tests/ -m 'not live'`.

Commit: `feat(core): postgres repos for definitions, versions, tickets, notify state`

### Step 5: One run-JSON writer, export parity

`packages/ngen-weave-core/src/ngen_weave/export.py` (new), `FileRunStore` touched only to call it, one CLI verb.

Today the single-file run-JSON format exists implicitly inside `FileRunStore.save`'s serialization. This step makes it explicit so both backends and the importer share it:

```python
def dump_run_json(run: RunFile) -> bytes
    # the exact bytes FileRunSave wrote through v0.5: json.dumps of the RunFile
    # envelope (format, run_id, workflow, status, input, output, error, records, ...)
    # with the established key order and defaults handling moved here verbatim
def load_run_json(data: bytes) -> RunFile     # inverse; tolerant of missing defaulted keys
```

Changes:

- `FileRunStore.save` serializes through `dump_run_json` and writes those bytes atomically; no byte changes anywhere (the existing file-format tests prove it).
- `PgRunStore` gains `async def export(self, run_id: str) -> bytes` returning `dump_run_json(await self.load(run_id))`; add `export` to the `RunRepo` protocol with a `FileRunStore` implementation (load then dump).
- API: `GET /api/runs/{run_id}/export` in `api.py` serves those bytes as `application/json`, unknown run → 404. (`GET /runs/{run_id}` keeps returning the parsed dict as today; the export route guarantees the canonical serialized form.)
- CLI: `ngen-weave export-run <run-id> [--out PATH]` over the configured store; stdout when `--out` omitted.

Byte-compatibility statement, tested not promised: for every shipped example workflow, the bytes written by a v0.5-era fixture file equal `dump_run_json(load(v0.5_file))`; the fixture corpus copied into the test guards the "byte-compatible with the pre-DB writer where practical" clause, with any unavoidable divergence asserted explicitly and commented.

Tests (`test_export.py` + extensions): dump/load round trip on the fixture corpus; `FileRunStore.save` output unchanged against recorded bytes; `PgRunStore.export` equals `FileRunStore` export for an identical run constructed through each backend; export route 200/404; CLI smoke.

Absorbs: reproducibility handoffs (one writer), Argo-era exporters (pure functions over `RunFile`), format evolution through 1.0 (one place).

Out of scope: PROV-JSON (exists since v0.4, untouched), exporting definitions or artifacts alongside (a run export stays the single run file, matching the pre-v0.6 shape), streaming/chunked export.

Verify: `uv run pytest src/ngen_weave/test_export.py src/ngen_weave/engine/ packages/ngen-weave-server/src/ngen_weave_server/test_run_api.py && uv run ngen-weave export-run --help`.

Commit: `feat(core,cli): single run-json writer shared by both stores`

### Step 6: `ngen-weave import-project`

`packages/ngen-weave-core/src/ngen_weave/db/importer.py` (new), one CLI command.

```
ngen-weave import-project <dir> [--database URL] [--projects-root PATH]
```

Behavior, fixed here:

- `<dir>` is a pre-v0.6 (or current file-mode) project root containing `.ngen-weave/runs/*/run.json`, `.ngen-weave/definitions/`, and `projects/` artifact trees. The target is the resolved database (`--database` overrides env/config; refusing to guess, the command errors when no URL resolves).
- Runs: each `run.json` parsed with `load_run_json` (Step 5), inserted via `PgRunStore.create`-equivalent bulk path preserving the original `run_id` (colliding id → `ConfigError("run already imported: {id}")`, making re-runs safe and idempotent-by-abort rather than partially duplicated).
- Records: inserted with their original ordinals from the stream order.
- Definitions: files under `.ngen-weave/definitions/` loaded through the standard parser and saved into the `definitions` table via `PgDefinitionStore` (validation applies unchanged; a broken file aborts with the validator's message listing the file).
- Artifact manifests: each project's `*.versions.json` manifests read and inserted into `artifact_versions`; blobs themselves are copied (or left in place when `--projects-root` points at the existing tree; default: copy into the target root's layout) so hashes continue to address content on disk.
- Tickets and notify state: not present meaningfully in pre-v0.6 directories; if sidecar files exist they are imported too (same parsers), else silently skipped.
- Output: counts per category printed (`imported 42 runs, 12817 records, 9 definitions, 133 artifact versions`); exit 0 only if everything landed.

The importer reads only through `load_run_json` and the standard file parsers, writes only through the `Pg*` stores, no direct SQL, so a future backend change cannot strand it.

Tests (`db/test_import.py`, CLI test): a fixture pre-v0.6 directory (checked in, built from the example project) imports fully; every imported run loads from `PgRunStore` with identical `RunFile` equality; `export` of an imported run equals the original file's bytes (criterion 2's semantic-match half, byte-exact here); re-import aborts naming the colliding run; broken definition aborts before any partial commit (single transaction per category, runs last so definitions validate first); artifacts addressable: a version's sha256 resolves to bytes on disk after import with `--projects-root` pointing elsewhere.

Absorbs: future import sources (a reader function per source feeding the same store writes) and v0.5→v0.6 upgrades of existing file-mode projects (same command).

Out of scope: live dual-writing during a transition window, importing *from* Postgres back to files (use `export-run` per run), merging partially-imported directories beyond the abort rule, progress bars.

Verify: `uv run pytest src/ngen_weave/db/test_import.py packages/ngen-weave-cli/tests/test_cli_import.py && uv run ngen-weave import-project --help`.

Commit: `feat(cli): import-project migrates pre-v0.6 directories into postgres`

### Step 7: Token auth: principals, issuance, and the 401 wall

`packages/ngen-weave-core/src/ngen_weave/auth.py` (new), server `app.py`/`api.py`, MCP HTTP transport, CLI user commands. Roles arrive in Step 8; this step is identity and rejection only.

```python
# auth.py
Role = Literal["owner", "reviewer", "observer"]

@dataclass(frozen=True)
class Principal:
    name: str
    role: Role          # resolved from project_roles; Step 8 enforces it

class TokenHasher:      # module-level functions, not a class
def hash_token(token: str) -> str        # sha256 hex of the raw token
def new_token() -> str                   # "ngw_" + secrets.token_urlsafe(24)

class DbAuthResolver:
    """Resolves a bearer token to a Principal via the users + project_roles tables."""
    def __init__(self, sessionmaker: async_sessionmaker[AsyncSession]) -> None
    async def resolve(self, token: str | None) -> Principal | None   # None when missing/unknown
```

Issuance and storage rules: `ngen-weave user add <name> [--role owner|reviewer|observer]` (default `observer`) inserts the user and prints the raw token exactly once, writing only `hash_token(token)`; `ngen-weave user list` shows names and roles, never tokens. Both operate directly against the resolved database (they are management commands, not API calls). Duplicate name → `ConfigError`.

Server enforcement (`app.py`): one FastAPI dependency `current_principal` extracting `Authorization: Bearer <token>`, calling the resolver, raising `HTTPException(401, {"error": {"type": "unauthenticated", "message": ...}})` on `None`. Applied to **every** route in `api.py`, reads included; the release doc's "every API and MCP request authenticated" admits no read exemption. Escape hatch, explicit and narrow: `create_app(..., auth_disabled: bool = False)`; also enabled by env `NGW_AUTH_DISABLED=1`, intended for tests, the local file-mode dev loop, and stdio MCP. When disabled the dependency returns `Principal(name="local", role="owner")`, which is what makes Step 8's matrix total instead of nullable.

Actor plumbing: the `X-Ngw-Actor` header (v0.5 Step 9) is superseded: mutating handlers receive `principal.name` as the actor string. The header is still parsed for compatibility but only when auth is disabled; with auth on, a client-supplied actor header is ignored (forging identity was the hole being closed).

MCP: the HTTP transport (`ngen-weave-mcp-http`) forwards its own `Authorization` header configuration (`--token` flag or `NGW_TOKEN` env) and the server-side MCP mounting sits behind the same dependency; stdio mode keeps in-process `auth_disabled` semantics since it constructs its own `LocalRunService` locally.

Client: `HttpRunService` (`client.py`) gains `token: str | None`, sent as the bearer header; CLI grows a global `--token` option (env `NGW_TOKEN` consulted as fallback) used whenever `--url` targets a remote server.

Tests: `test_auth.py` covers hashing determinism, `new_token` uniqueness/format, resolver hit/miss/disabled-user; `test_auth_api.py` drives `create_app`: no header → 401 on every route (parametrized over the route table, including reads), garbage token → 401, valid token → 200 and actor recorded as the principal name on a launched run, `auth_disabled` restores open access with actor `"local"`; `test_http_auth.py` exercises the MCP HTTP transport denied without token and allowed with it.

Absorbs: OIDC/SSO later (replace `DbAuthResolver` with another resolver; the dependency and every enforcement point keep consuming `Principal`), token rotation (issue a new token, rewrite the hash; verification is stateless).

Out of scope: role enforcement (Step 8; this step authenticates, it does not authorize beyond identity), token expiry/TTL, rate limiting, HTTPS termination, password logins, the web UI's token-entry screen (Step 9).

Verify: `uv run pytest src/ngen_weave/test_auth.py packages/ngen-weave-server/src/ngen_weave_server/ packages/ngen-weave-mcp/src/ngen_weave_mcp/ -m 'not live'`.

Commit: `feat(server,mcp,cli): bearer-token authentication on every request`

### Step 8: Project roles enforced at the boundary

`packages/ngen-weave-core/src/ngen_weave/auth.py` (matrix), `service.py` (signature growth), `local.py`, `api.py`, conformance suite. This is the authorization half of the release, extending v0.5's run-level `require_actor` to project level.

The matrix, one function, called nowhere else:

```python
def require_role(principal: Principal, action: str, *, also: Sequence[str] = ()) -> None
    # raises PermissionError(NgWeaveError) naming principal/action unless:
    #   action == "read"                        -> any authenticated principal
    #   action in {"launch", "cancel", "note", "budget",
    #              "assign_role", "edit_workflow", "install_plugin"} -> owner
    #   action == "resume"                      -> owner or reviewer
    #   action in also                          -> those roles admitted additionally
```

Mapping onto surfaces, decided here:

- `RunService` protocol: every method's `actor: str | None` keyword becomes `principal: Principal` (required, no default; after Step 7 there is always a principal, real or `local`). Implementations updated together; `HttpRunService` sends nothing extra (identity travels by token; the server resolves it).
- Enforcement points: `LocalRunService.launch/resume/cancel/attach_note/budget/assign_role` each call `require_role` with their action before touching the store; workflow PUT (`edit_workflow`) and plugin/pack install routes (`install_plugin`) check in `api.py` before delegating. Reads call with `"read"`.
- Interaction with v0.5 run-level roles: `resume` succeeds when the principal holds project-level owner/reviewer **or** appears in the run's `roles.reviewers` list (grandfathered per-run grants keep working); every other action is governed purely by the project role. The `roles` dict on `RunFile` stays (it is data in Postgres now, and per-run reviewer grants remain meaningful).
- Role management API: `PUT /api/users/{name}/role` body `{"role": Role}`, caller must be owner (`require_role(principal, "assign_role")`); `GET /api/users` lists names and roles (any authenticated). CLI wrappers: `ngen-weave role set <name> <role>`, `ngen-weave role list`: thin translations over HTTP when `--url` given, direct DB when local.
- Error mapping: `PermissionError` → `403 {"error": {"type": "forbidden", ...}}` (existing mapping from v0.5, unchanged); the auth-disabled `local` owner principal means local development flows never trip it.

Conformance suite extension (both `RunService` implementations): owner launches and cancels; reviewer resumes a waiting run and answers a review but launch/cancel/edit raise; observer reads everything and mutates nothing; unknown-user scenarios impossible by construction (resolver returned no principal → 401 upstream). Criterion 3's second half (reviewer answers reviews, cannot launch) is asserted here at the service level and again end to end in Step 9.

Web (`../ngen-weave-web/`, may land with Step 9's web commit): api client sends the stored token on every request, treats 401 as "session invalid" (clear token, show token prompt), 403 as an inline permission message; UI hides launch/cancel/edit controls for non-owner resolved identities via a `/api/me` endpoint (`{"name", "role"}`) added in `api.py` here.

Tests: exhaustive `require_role` truth table in `test_auth.py`; conformance scenarios above; `test_auth_api.py` extended for 403 shapes, role-management routes, `X-Ngw-Actor` ignoring under auth; CLI role command smoke.

Absorbs: new gated actions (one row in the matrix), richer role models post-1.2 (rows and the `Role` literal, nothing else), team workspaces (the `project_roles` key grows a dimension; matrix signature unchanged).

Out of scope: multiple roles per user, per-workflow permissions, invitation flows, audit log beyond provenance, run-level role *writes* via API beyond what v0.5 shipped.

Verify: `uv run pytest packages/ngen-weave-server/ src/ngen_weave/test_auth.py -m 'not live'`.

Commit: `feat(server,cli): project-level roles with one enforcement matrix`
