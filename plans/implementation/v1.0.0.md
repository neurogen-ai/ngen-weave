# v1.0 implementation plan

## Context

After v0.8 (per `implementation/v0.8.md`) ngen-weave runs on Postgres as the canonical store (file mode still the zero-config default), every request carries a bearer token, and owner/reviewer/observer roles gate the service boundary. The editor loop, provenance export, budgets, notifications, plugins, tickets, and boxed agent autonomy all exist. What does not exist: a deployable product. The FastAPI service is the only serving path, projects are a config field rather than a managed entity, nothing ships as a container, the HTTP API has no version prefix or published contract, and no document walks a stranger from install to first run.

v1.0 closes that gap: our own FastAPI service becomes the only shipped serving path, projects become first-class isolated entities under authenticated users, budgets gain a project scope, everything deploys as a container image plus migration, exports work from the database store, notifications deliver in the deployed server, MCP is stable enough to drive pi end to end, docs cover every public surface, and both public surfaces (HTTP API, Python package) become semver-governed.

Files touched:

- `packages/ngen-weave-server/src/ngen_weave_server/`: versioned routing, project scoping, notification wiring, container entrypoint
- `packages/ngen-weave-core/src/ngen_weave/`: project registry, project budget enforcement, export seam, auth resolver widening
- `packages/ngen-weave-core/alembic/versions/0002_projects.py` (**new**): projects table and role-table widening
- `packages/ngen-weave-mcp/src/ngen_weave_mcp/`: project selection on the HTTP transport
- `packages/ngen-weave-cli/`: `--project` global option, `projects` commands
- `docker/` (**new**): Dockerfile, compose file, entrypoint script
- `docs/`: quickstart rewrite, API reference generation, semver policy, deployment guide update
- `design/api-contract.md`, `design/serving.md` (**new**, first design docs)
- `../ngen-weave-web/`: versioned client base URL, project switcher, budget display

Depends on: `releases/v1.0.md` (requirements), `product/PRD.md` (decision log, wins on conflict), `releases/post-1.0.md` (what stays out), and module shapes fixed by `implementation/v0.1.md` through `implementation/v0.8.md` (referenced, never restated). No design docs exist when this plan starts; Steps 1 and 5 write the first two, and later steps link to them rather than restating choices.

Conventions inherited from `implementation/v0.1.md` (backend) and `implementation/v0.3.md` Step 7 (web): Python ≥3.12, uv workspace, pytest, ruff, conventional commits, one commit per step unless stated, full suite green before committing, tests next to code except e2e under `tests/e2e/`, fakes instead of network (live-marked exceptions only). Web repo: pnpm, Vitest, Playwright, `pnpm lint && pnpm test && pnpm build` green before committing.

Global out of scope for every step (per `releases/v1.0.md` explicit-outs and `releases/post-1.0.md`): distributed execution, Argo export, remote node dispatch, simultaneous editing, team workspaces beyond the v0.8 role model, vertical workflow packs, cron scheduling, plugin marketplace infrastructure, multiple roles per user.

## Goals

1. The shipped serving path is our FastAPI service alone. Deployment is one container image with explicit volume-mount points for artifact blob stores, whose entrypoint runs `ngen-weave db upgrade` then starts the server.
2. Projects are first-class: created and listed through the API, isolated per artifacts and definitions, scoped by path parameter, with roles resolved per project and budgets enforceable at project level as well as run level.
3. Every HTTP route lives under `/api/v1/` with a frozen OpenAPI snapshot and a written contract (`design/api-contract.md`) stating the versioning and deprecation policy; the Python public surface is marked and tested the same way.
4. A stranger completes install → workflow built in UI → run with a real model → review answered from a second machine → budget observed → provenance exported, using only published interfaces and documentation.
5. pi calls a hosted workflow through MCP over HTTP end to end against the deployed server, and AgentNode actions during that call are auditable through provenance records fetched back through the API.

## Success criteria

From `releases/v1.0.md`, verbatim in intent:

1. A stranger who did not build ngen-weave completes the full loop unaided in under an hour, touching only published interfaces (the stranger test; assembled in Step 11).
2. Fresh deployment reaches working state from an empty Postgres through the container image alone: `docker compose up`, migrate, serve, launch a run.
3. Two projects on one server cannot see each other's runs, definitions, or artifacts; an observer in project A gets 403 launching in project B where they hold no role.
4. A project-level budget breach pauses new launches and running runs, recorded in provenance, without touching the run-level budget logic.
5. An email notification fires from the deployed server on human-review-waiting and arrives (fake SMTP in tests, live-marked variant documented).
6. PROV-JSON and single-file run JSON export identically from file mode and Postgres mode for an identical run.
7. pi drives a workflow to completion through the HTTP MCP transport with a bearer token, and every AgentNode action in the run appears in the run's provenance records.

## Abstractions and what they absorb

One sentence each; these are the load-bearing choices.

- **One versioned mount: every router collected under a single `APIRouter(prefix="/api/v1")` in `app.py`** absorbs a future `/api/v2` (new prefix, old one kept alive per the deprecation policy) without touching any handler, because handlers never know their own path.
- **The OpenAPI snapshot test as the contract freeze** absorbs drift between docs and code: any shape change fails CI until the snapshot and `design/api-contract.md` are deliberately updated together.
- **A `ProjectScope` resolved once by a FastAPI dependency from `{project}` path parameters** absorbs new per-project resources (each new route takes the dependency; isolation checks exist in one place) and future workspace/team grouping (the scope grows a field, callers unchanged).
- **Per-project role rows consumed through the same `AuthResolver.resolve(token, project)`** absorbs richer permission models post-1.2: the matrix in `auth.py` stays the only enforcement point; the resolver's query changes, nothing else.
- **`ProjectBudgetEnforcer` as one engine hook beside the existing `_check_budget`** absorbs budget-policy changes (per-user spend, rolling windows): aggregate-spend reading lives in one class; run-level logic is untouched.
- **Exporters as pure functions over `RunFile` fed by `RunRepo.load`** absorbs new backends and export targets: the DB/file question ends at `load`; a new export format is another pure function.
- **MCP tool tables keyed per project behind one `NGW_PROJECT` selector on the transport** absorbs multi-project MCP clients (one connection, project chosen per call) without a second server process per project.

### Step 1: Versioned API and the published contract

`packages/ngen-weave-server/src/ngen_weave_server/app.py`, `api.py`, web client, plus the first design doc. Nothing about any endpoint's behavior changes; only paths, snapshots, and paperwork.

Routing:

- In `app.py`, collect every existing router onto one parent `APIRouter(prefix="/api/v1")`. Exempt exactly two mounts from the prefix: `GET /healthz` (added here: returns `{"status": "ok", "store_mode": app.state.store_mode}`, no auth) and the MCP HTTP mount (its own transport, its own versioning story, Step 8).
- Old `/api/...` paths die without ceremony: the PRD declares the API unstable before 1.0, so there are no aliases, no redirects. The web client (`../ngen-weave-web/src/lib/api/client.ts`) changes its base path constant in the same commit; Playwright base URL updated to match.

Contract doc, `design/api-contract.md` (new; content fixed here so the implementing agent writes it verbatim in intent):

- Base URL rule: breaking changes ship under a new `/api/vN`, previous version supported for one minor release cycle with responses carrying `X-Ngw-Deprecation: true`.
- Additive changes (new optional request fields, new response fields, new routes within the current version) are non-breaking and may land anytime.
- The error envelope `{"error": {"type": str, "message": str}}` and the pagination-free list shapes are frozen for v1.
- Python surface: `ngen_weave` public modules listed explicitly (`workflow.py`, `engine/`, `storage.py`, `definitions.py`, `provenance.py`, `auth.py`, `export.py`, `notify.py` module-level names); everything else is private by declaration. Semver applies to those names' signatures from 1.0.

```python

def test_every_route_is_versioned(): ...  # iterates app.routes; asserts each HTTP path starts with /api/v1/, or is /healthz, or is the MCP mount
```

`export_openapi.py` (new, ~10 lines): writes `docs/api/openapi.json` from `create_app(auth_disabled=True).openapi()`; the docs site serves it (Step 9).

Out of scope: any behavior change behind existing routes, API docs prose (Step 9), MCP path versioning, client codegen.

### Step 3: Projects as first-class entities

`packages/ngen-weave-core/src/ngen_weave/projects.py` (new), `db/tables.py` + migration `0002_projects.py`, server `api.py` + a new `deps.py`, CLI. This is the largest step; it touches routes, storage layout assumptions, and role resolution together because splitting them would leave the tree red mid-sequence.

Data model:

- Migration `0002_projects` creates:
  - `projects`: `name` str PK (slug `[a-z][a-z0-9_-]*`), `created_at` timestamptz, `config` JSONB (the per-project config document: budgets, notifications, capability grants; validated by the existing config parser on write).
  - Alters `project_roles`: PK becomes `(project, user_name)`; existing rows back-filled with the project name from the single-project config value current deployments carry. This amends v0.8's `(user_name,)` keying from migration `0002_auth`; the amendment is listed at the foot of this plan.
- File mode: projects stay directory-per-project under the projects root exactly as today; the registry is the filesystem (a project exists iff its directory exists). `projects.py` hides this:

```python
# projects.py
@dataclass(frozen=True)
class ProjectInfo:
    name: str
    created_at: str | None      # None in file mode
    config: dict

class ProjectRegistry(Protocol):
    async def create(self, name: str, config: dict = {}) -> ProjectInfo   # ConfigError on bad name/duplicate
    async def get(self, name: str) -> ProjectInfo                          # KeyError -> 404 upstream
    async def list(self) -> list[ProjectInfo]

class FileProjectRegistry:  # over <projects-root>/
class PgProjectRegistry:    # over the projects table
```

Server scoping (`deps.py`, new):

```python
async def project_scope(project: str, principal: Principal = Depends(current_principal)) -> ProjectScope
    # 404 unknown project, 403 when principal has no row in project_roles for it;
    # ProjectScope = (name: str, principal: Principal) — everything downstream needs
```

Routes regroup (mechanical move, bodies unchanged except taking `scope: ProjectScope`):

- `GET/POST /api/v1/projects` (list needs any authenticated principal; create requires an authenticated principal, role assignment happens after creation by an owner)
- `GET/PUT /api/v1/projects/{project}/config`
- All existing run/definition/version/review/budget/ticket/user-role routes move under `/api/v1/projects/{project}/...`. `GET /api/v1/users/{name}/role` gains the project parameter; `PUT .../role` body unchanged.
- Artifact root per project: `<projects-root>/<project>/` (file mode already matches this layout; Postgres mode's `PgVersionLog(project=...)` already keys by name, so the change is passing the scope's name through instead of the config field).

Auth widening:

- `AuthResolver.resolve(self, token: str | None, project: str)` returns `Principal(name, role)` where role comes from `(project, user_name)`; `current_principal` can no longer resolve alone, so it yields an unresolved `Principal(name, role="observer")`-shaped `PendingPrincipal` and `project_scope` finishes the job (this keeps the 401 wall in one dependency and authorization in the other). `auth_disabled` mode short-circuits both to `Principal("local", "owner")`.
- `require_role` matrix untouched; it already takes a resolved `Principal`.

CLI: global `--project NAME` option on every remote command (default: the single configured project when exactly one exists, error listing projects otherwise); `ngen-weave projects list/create`.

Web: project switcher in the header backed by `GET /projects`; api client sends the selected project as the path segment everywhere; token prompt flow unchanged.

Isolation proof (`test_projects_api.py`): two registries seeded with disjoint runs/definitions/artifacts; project A's token sees none of B's listings, gets 404 on B's run ids, 403 writing to B; observer-of-A launching-in-B draws 403 (criterion 3 asserted at the API level).

Absorbs: team workspaces post-1.2 (the registry and scope grow membership concepts in one place) and per-project plugin grants (already config-borne, now stored per project).

Out of scope: renaming/moving existing directories automatically (single-project v0.6 deployments keep working because the default project name maps to the existing layout; a note goes in the upgrading docs, Step 9), project deletion/archival, quotas, cross-project artifact references, nested projects.

Verify: `uv run pytest src/ngen_weave/ packages/ngen-weave-server/ packages/ngen-weave-cli/tests/ -m 'not live'`; web `pnpm lint && pnpm test && pnpm build`; regenerate the OpenAPI snapshot (`uv run python -m ngen_weave_server.export_openapi`) and commit it with this step since route paths changed.

Commits: `feat(core): project registry over files and postgres`, `feat(server,cli,web)!: project-scoped api with per-project roles`

### Step 4: Project-level budgets

`packages/ngen-weave-core/src/ngen_weave/engine/budget.py` (extended), `engine/runner.py` hook, config parsing, one API surface, UI display.

Config: per-project `budget:` block in the project config document (Step 3's JSONB), parsed into:

```python
@dataclass(frozen=True)
class BudgetLimit:
    cost_usd: float | None = None
    steps: int | None = None  # existing run-level fields, reused verbatim


# project config: {"budget": {"cost_usd": 50.0}} — same grammar as the run-level block
```

Enforcement, one class beside the existing run-budget check:

```python
class ProjectBudgetEnforcer:
    """Aggregate spend across a project's runs, checked where _check_budget already runs."""
    def __init__(self, repo: RunRepo, limit: BudgetLimit, refresh_every_s: float = 30.0) -> None
    async def spent(self) -> tuple[float, int]     # sum of cost_usd and transition count over non-terminal runs; cached for refresh_every_s
    def breached(self, spent: tuple[float, int]) -> bool
```

Behavior, fixed here:

- Checked at the same two moments the engine already checks run budgets (between transitions, and at launch). Breach pauses: new launches raise `BudgetExceeded` (existing error type, message naming the project scope); running runs pause at next transition with a `budget_exhausted` provenance record whose payload gains `"scope": "project"` (run-level breaches record `"scope": "run"`, added to the existing emissions for symmetry).
- Raising the project cap mid-flight re-enables launches on the next check; paused runs resume through the normal resume path, matching the v0.2 pause-not-kill decision.
- Resolution precedence per run: run-level limits apply as always; project limits apply additionally (a run under its own cap still pauses if the project is over). Both checks run; neither subsumes the other.
- Server surface: `GET /api/v1/projects/{project}/budget` returns `{"limit": ..., "spent": ..., "breached": bool}` (any authenticated reader); `PUT` updates the limit (owner, via the config write path so validation applies once).

Tests (`engine/test_budget.py` extensions): enforcer sums only non-terminal runs; cache honors refresh window; launch raises while breached and succeeds after cap raise; mid-run breach pauses with the `scope: project` record; run-level and project-level caps combine correctly; config parse cases including rejection of unknown keys.

Web: budget display on the project view reads the new GET; owner edit control on the PUT.

Absorbs: future budget policies (rolling windows, per-user attribution) land inside the enforcer's `spent()`; the engine hook never learns how spend is computed.

Out of scope: per-node or per-workflow budgets (v0.4's override mechanism already covers per-run), notifications on project breach (Step 6 wires the existing `cost_crossed` rule; no new kind), spend forecasting, hard-kill semantics.

Verify: `uv run pytest src/ngen_weave/engine/test_budget.py packages/ngen-weave-server/src/ngen_weave_server/test_run_api.py -m 'not live'`.

Commit: `feat(core,server): project-level budget enforcement beside run budgets`

### Step 6: Notifications operational in the served deployment

`packages/ngen-weave-server/src/ngen_weave_server/lifespan.py` (extracted from `create_app`), `test_notifications_serving.py`. The dispatcher exists since v0.5 Step 6 and gained the async state protocol in v0.6 Step 4; what v1.0 adds is proof that it delivers from the deployed server, per project, against the Postgres store.

Wiring fixes, decided here:

- One dispatcher per project with notification rules in its config (Step 3's JSONB), started in the app lifespan task group; a project without rules starts nothing. Dispatcher construction moves to a factory `build_dispatcher(scope, registry_config, notifiers, repo, state) -> NotificationDispatcher | None` living in core (`notify.py`) so server and CLI construct identically.
- Rules now scope to their project: the fingerprint scan filters `store.list()` to the project's runs. `NotificationDispatcher.__init__` gains `project: str | None = None`; None preserves today's all-runs behavior (file mode, single project).
- Provider secrets: `target` dicts may reference env vars as `{"smtp_password_env": "SMTP_PASSWORD"}`; the email/text provider plugins resolve `_env`-suffixed keys at deliver time and refuse to start (loud `ConfigError` at dispatcher construction) when the variable is unset. No secrets in the database, ever.

Tests (`test_notifications_serving.py`): fake SMTP server (aiosmtpd fixture, localhost) receives mail when a run enters `waiting_human` in a served app with a configured email rule; a second occurrence does not refire; failing delivery leaves the run unaffected and lands the `notification_attempt` records (read back through `RunRepo.append` semantics in PG mode via sqlite backend); `NGW_AUTH_DISABLED` off, bearer token on, everything through real HTTP. Live-marked variant documented in `docs/notifications.md` (new, short: provider config reference, Twilio/env setup).

Criterion 5 is asserted here at the serving level; the stranger-test assembly (Step 11) repeats it end to end.

Absorbs: new delivery channels (provider registration, unchanged machinery) and post-1.0 digesting (the scan loop is one place).

Out of scope: webhook/push channels, per-user subscriptions, retry-policy configuration surface, HTML emails.

Verify: `uv run pytest packages/ngen-weave-server/src/ngen_weave_server/test_notifications_serving.py src/ngen_weave/test_notify.py -m 'not live'`.

### Step 7: Exports read through the repo seam

`packages/ngen-weave-core/src/ngen_weave/export_prov.py` (renamed/refactored from wherever v0.4 Step 8 landed it), routes, parity tests. Requirement 4: provenance export works from the database-backed store, identically in both modes.

Current shape: the PROV-JSON exporter reads runs through `SqliteRunStore.load`. Target shape, decided here:

```python
def prov_json(run: RunFile, *, definition_lookup: Callable[[str], dict | None] = lambda _: None) -> dict
    # pure function, W3C PROV-JSON dict out; unchanged mapping table from v0.4;
    # definition_lookup enriches activities with definition metadata when available
```

- The disk-reading wrapper becomes a thin caller: `load` via `RunRepo`, then `prov_json(run)`. Routes: `GET /api/v1/projects/{p}/runs/{id}/export/prov` and the existing run-JSON export route (serving since v0.2) move under the project prefix with everything else; both serve bytes produced solely from `RunRepo.load(run_id)`.
- Parity rule, tested not promised (`test_export_prov.py`): for the checked-in example corpus, constructing an identical run through `SqliteRunStore` and `PgRunStore` (sqlite backend) produces byte-identical PROV-JSON and byte-identical run JSON from the two export functions. Any divergence is a bug in a store's rehydration, and this test is where it surfaces.
- Definition enrichment uses `DefinitionStore.get` at the route layer, passed in as `definition_lookup`; missing definitions degrade to absent enrichment, never an error (exported runs must survive deleted workflows).

Out of scope: new export formats (Argo waits for 1.1), streaming export, exporting whole projects (per-run remains the unit, matching v0.4).

Verify: `uv run pytest src/ngen_weave/test_export_prov.py src/ngen_weave/test_export.py packages/ngen-weave-server/src/ngen_weave_server/test_run_api.py -m 'not live'`.

Commit: `refactor(core,server): prov-json export as pure function over runrepo loads`

### Step 8: MCP stability: project selection and the pi end-to-end

`packages/ngen-weave-mcp/src/ngen_weave_mcp/`, live-marked pi test. Requirements 6 and part of 5.

Project selection, decided here:

- The HTTP transport accepts `GET /mcp/{project}/mcp` (path segment) or the `X-Ngw-Project` header; path wins when both appear. Tool tables are built per project at request time from that project's registered workflows (the manifest mechanism from v0.2 Step 7, resolved against the project scope). stdio mode keeps its single-project local semantics unchanged.
- Auth rides the v0.8 bearer-token path; the resolved principal must hold at least observer on the selected project to list tools and reviewer-equivalent rights follow the same matrix as the HTTP API (launch via MCP is `launch`; enforced by calling the same `LocalRunService` methods, which already call `require_role`).
- Tool descriptions and input schemas come from the workflow's JSON Schema as before; result content remains the validated output object.

Auditability: AgentNode actions already emit provenance records (v0.5 boxing); the new piece is the round trip. Test asserts that after an MCP-driven run containing an AgentNode, `GET .../runs/{id}` includes the agent-action and blocked-action records with plugin/source tags intact.

pi test (`tests/e2e/test_pi_client.py`, live-marked, requires a real model key and the pi binary on PATH): boots the server in Postgres mode, registers the example workflow, invokes pi pointed at the HTTP MCP URL with a token, asserts the workflow completes and the output validates. Skipped when either prerequisite is missing; the skip message states exactly what to install. A non-live twin (`test_pi_client_shim.py`) drives the same flow with a scripted minimal MCP client so the server side is exercised in CI regardless.
