# v0.5 implementation plan

## Context

After v0.4 (per `implementation/v0.4.md`) the distribution ships five workspace packages: core (workflow classes with data-only YAML/JSON definition serialization, `DefinitionStore`, LangGraph engine with budgets and mid-run overrides, human review, observers, content-addressed artifacts with a `VersionLog`, PROV-JSON export, agent harness behind a `PermissionGate` over a `ToolRegistry`), cli, server (FastAPI `RunService`, read/mutation API, projects reader), mcp (workflow-as-tool over stdio and HTTP), plus the sibling `ngen-weave-web` repo (list, canvas, detail, projects, run screens, review screen, editor, diff viewer). Nothing extends ngen-weave yet except by writing Python inside the registry's reach.

v0.5 makes ngen-weave extensible, period: plugins via entry points contributing node kinds, services, workflow packs, namespaced HTTP API routes, and declarative UI widget specs plus prebuilt component bundles; notification providers as reference plugins; real boxed agentic autonomy with ngen-weave itself exposed over MCP loopback. Built-ins register through the same surface plugins use. The collaboration slice (multi-reviewer, roles, tickets) moved to v0.8; external document links moved to v0.7.

Files touched:

- `packages/ngen-weave-core/src/ngen_weave/`: new `plugins.py`, `nodekinds.py`, `widgetspec.py`, `notify.py`; extensions to `provenance.py`, `config.py`, `workflow.py`, `storage.py`
- `packages/ngen-weave-server/src/ngen_weave_server/`: new `pluginroutes.py`, `pluginstate.py`; extensions to `readmodel.py`, `api.py`, `app.py`
- `packages/ngen-weave-cli/src/ngen_weave_cli/main.py`: `plugins` and `pack` verb groups, `plugin build`
- New packages: `packages/ngen-weave-demo-shapes/`, `packages/ngen-weave-plugin-email/`, `packages/ngen-weave-plugin-text/`
- `packages/ngen-weave-mcp/src/ngen_weave_mcp/loopback.py`, **new**
- `../ngen-weave-web/`: `registries.ts`, new `src/lib/widgets/` (spec types, host component), canvas/detail wiring

Depends on: `releases/v0.5.md` (requirements), `design/plugins-and-ui.md` (why, referenced not restated), `product/PRD.md` decision log (wins on conflict), and module shapes fixed by `implementation/v0.1.md`–`implementation/v0.4.md`.

Conventions inherited from `implementation/v0.1.md` (backend) and `implementation/v0.3.md` Step 7 (web): Python ≥3.12, uv workspace, pytest, ruff, conventional commits, one commit per step unless stated, full suite green before committing, tests next to code except e2e under `tests/e2e/`, `FakeProvider`/fake transports in tests, no network (live-marked exceptions only). Web repo: pnpm, Vitest, Playwright, `pnpm lint && pnpm test && pnpm build` green before committing.

Global out of scope for every step (per `releases/v0.5.md` non-goals): real-time collaborative editing, plugin marketplace/discovery infrastructure, unbounded autonomy or self-modifying workflows, interpreter-level plugin sandboxing, hot-reload, Postgres (v0.6), auth principals (v0.8), rich client-side interactivity in spec widgets (client state, dependent inputs, streaming bindings), host-build compilation of plugin frontend source.

## Goals

1. Third-party plugins install via pip, register through the `ngen-weave.plugins` entry-point group, and contribute node kinds, services, notifiers, workflow packs, namespaced API routes, and widget specs; capability grants are explicit in project config and enforced at resolution time; everything is validated when a plugin is enabled, so malformed specs fail there with actionable errors.
2. Every built-in node kind registers itself through the same API plugins use, so the plugin surface is exercised by ngen-weave's own code.
3. The web app renders any enabled plugin's widgets through one generic host that knows the spec contract and no plugin; core's simple field renderers consume the same host.
4. Notification providers consume the run event stream under per-project filter rules, retry best-effort, and never disturb a run; every attempt lands in provenance.
5. An AgentNode runs a real tool loop against ngen-weave over MCP loopback while composed `PermissionSets` (tool and workflow allow/deny, budget caps, call ceilings, checkpoints, path territories) are enforced engine-side at the gate, with every blocked action recorded.

## Success criteria

From `releases/v0.5.md`, verbatim in intent:

1. A third-party demo plugin defining one new node kind plus a spec-driven widget backed by its own namespaced API route installs via pip, passes enable-time validation, appears correctly in editor/canvas/detail views, and its runs carry plugin-tagged provenance.
1b. A malformed plugin (spec referencing a nonexistent route, dynamically built class string) fails enable-time validation with an actionable error; disabling it removes its widget and restores the page without residue.
2. An email notification fires on human-review-waiting within seconds of the event, and a failed SMTP host never disturbs the run.
3. A boxed AgentNode attempting a denied workflow launch is blocked engine-side with a recorded event, while an allowed sub-workflow launch completes and attributes cost to the parent.
4. The same MCP surface serves both the internal AgentNode and an external client driving the identical workflow.

## Abstractions and what they absorb

One sentence each; these are the load-bearing choices.

- **One entry-point group with a single `setup(PluginContext)` hook** absorbs every future contribution kind: a new kind is a new method on `PluginContext`, and existing plugins ignore it.
- **`NodeKindRegistry` holding `(base class, NodeMeta)` pairs, with the built-ins registering themselves** absorbs new node kinds everywhere at once: validation, storage parsing, read-model serialization, and the frontend all read the one registry, so a plugin kind needs no core edits.
- **A service registry keyed by `(kind, name)` with factories taking their config dict** absorbs new model backends, artifact stores, and diff renderers: a plugin registers a factory, config names it, neither the engine nor `create_app` learns the concrete class.
- **A route table assembled once at startup, mounted under `/api/plugins/<plugin-id>/`** absorbs new plugin endpoints without touching core routing, and makes auth inheritance structural (one mount point, middleware already wrapped around it).
- **The widget spec: a typed element-tree dict validated once at enable time against a JSON Schema in `widgetspec.py`** absorbs every new visual: plugins ship data, the host renders whatever validates, and a new spec feature is a schema change plus a host case, never a host release per plugin.
- **`pluginstate.sync()` as the single hook run at enable/disable/startup** absorbs future per-registry derived artifacts (the v1.0 container mounts, cached aggregates): safelist writing is just the first thing it does.
- **`NotificationDispatcher` as a poller over `RunStore.list()` with per-rule dedupe state** absorbs new event kinds and providers: events derive from run-file transitions in one scanner, providers implement one two-argument method.
- **Composed `PermissionSet` fields checked inside the existing `PermissionGate`** absorbs new denial reasons and territories: the gate stays the only wrapper around every agent action, and a new rule is one branch in its ordered evaluation.
- **MCP loopback as an in-memory transport client of the *same* registrar the stdio/HTTP servers use** absorbs new exposed surfaces: internal agents and external hosts see byte-identical tools because there is only one registrar.

### A2 — Plugin loading and capability grants

`packages/ngen-weave-core/src/ngen_weave/plugins.py` (**new**). This module owns discovering and admitting plugins; every later branch consumes it.

```python
@dataclass(frozen=True)
class PluginMeta:
    name: str            # normalized distribution name, e.g. "ngen-weave-demo-shapes"
    version: str         # from importlib.metadata

class PluginContext:
    """Registration surface handed to each plugin's setup(). Grows one method per contribution kind."""
    def register_node_kind(self, kind: str, base: type[Workflow], meta: "NodeMeta") -> None
    def register_service(self, kind: Literal["completion_provider", "artifact_store", "diff_renderer"],
                         name: str, factory: Callable[[dict], Any]) -> None
    def register_notifier(self, name: str, factory: Callable[[dict], "Notifier"]) -> None
    def register_pack(self, name: str, directory: Path) -> None
    def register_api_routes(self, prefix: str, router: "APIRouter") -> None     # Branch C
    def register_widget(self, name: str, spec_path: Path) -> None               # Branch D

@dataclass(frozen=True)
class RegisteredPlugin:
    meta: PluginMeta
    capabilities: tuple[str, ...]     # granted capability strings, empty when ungranted

class PluginRegistry:
    node_kinds: dict[str, tuple[type[Workflow], NodeMeta]]
    services: dict[tuple[str, str], Callable[[dict], Any]]     # (kind, name) -> factory
    notifiers: dict[str, Callable[[dict], Notifier]]
    packs: dict[str, Path]                                     # "<plugin>.<pack>" -> dir
    routers: dict[str, tuple[str, APIRouter]]                  # plugin id -> (prefix, router)
    widgets: dict[str, Path]                                   # "<plugin>.<widget>" -> spec file
    owners: dict[str, str]                                     # node kind or service name -> plugin id
    plugins: tuple[RegisteredPlugin, ...]

def load_plugins(*, group: str = "ngen-weave.plugins",
                 injected: Mapping[str, Callable[[PluginContext], None]] | None = None) -> PluginRegistry
def granted(registry: PluginRegistry, config_section: dict) -> PluginRegistry
```

Decisions, fixed here:

- Entry-point contract: group `ngen-weave.plugins`, each entry resolving to a module attribute `setup(ctx: PluginContext) -> None`. `load_plugins` iterates `importlib.metadata.entry_points(group=group)` sorted by name, builds a fresh `PluginContext` per plugin, calls `setup`, collects `PluginMeta` from distribution metadata. `injected` exists purely for tests (mapping plugin name to setup callable); production callers never pass it. `register_api_routes`/`register_widget` raise `ConfigError("unknown registration")` until Branches C/D implement them — the methods exist from day one so plugin authors see one stable surface.
- Failure modes are all `ConfigError` naming the plugin: import or setup raises; a kind/service/notifier/pack/widget/route-prefix name is registered twice by anyone including core; `register_node_kind` receives a non-`Workflow` base; a route prefix fails `[a-z][a-z0-9-]*`.
- Capability grants: `granted(registry, section)` filters to plugins listed under `enabled:` and, per plugin, drops registrations whose capability kind is not in that plugin's `grants:` list. Ungranted registrations vanish from lookup but stay visible in `plugins`, so diagnostics can explain why something did not resolve. Config shape parsed by `config.py`:

```yaml
plugins:
  enabled: [ngen-weave-demo-shapes]
  grants:
    ngen-weave-demo-shapes: ["node_kinds", "api_routes", "widgets"]
```

- `config.py`: `load_config` accepts the optional top-level `plugins:` key with exactly the keys `enabled` (list of str) and `grants` (map str -> list of str); unknown keys rejected as usual. Unknown plugin names in `enabled` cannot be checked inside `load_config` (it does not see the registry); the check lives in `granted()`, which raises `ConfigError("plugin not installed: {name}")`. `ResolvedConfig` gains `plugins: dict = {}`.

Tests (`test_plugins.py`): injected setup registers kinds/services/notifiers/packs/routes/widgets; duplicate name across two plugins raises naming both; non-workflow base raises; bad prefix raises; calling `register_api_routes` before Branch C raises the placeholder error (delete this assertion in C1); `granted()` drops ungranted lookups, keeps diagnostics visibility, and raises on unknown-enabled; a plugin raising in setup produces `ConfigError` carrying the plugin name. Config happy path extends `test_config.py`.

Absorbs: new contribution kinds (one `PluginContext` method) and the v0.6 packaging story (same entry points, no code change).

Out of scope: hot-reload or reloading after process start (registry is static per `releases/v0.5.md`), dependency constraints between plugins, marketplace metadata, uninstall flows.

Verify: `uv run pytest src/ngen_weave/test_plugins.py src/ngen_weave/test_config.py`.

Commit: `feat(core): entry-point plugin loading with capability grants`

### B1 — Node-kind registry, built-ins as reference registrations

Two modules: `packages/ngen-weave-core/src/ngen_weave/nodekinds.py` (**new**) and small edits to `workflow.py`, `storage.py`, `readmodel.py`, and the engine.

`nodekinds.py`:

```python
@dataclass(frozen=True)
class NodeMeta:
    label: str        # human label, e.g. "Review"
    icon: str         # icon name token from the web icon set
    color_var: str    # theme token name, e.g. "--edge-control"
    summary: str      # plain-language template; "{field}" placeholders index input fields

class NodeKindRegistry:
    def register(self, kind: str, base: type[Workflow], meta: NodeMeta) -> None
        # kind must match [a-z][a-z0-9_]*; duplicate kind raises ConfigError
    def base(self, kind: str) -> type[Workflow]   # unknown kind -> KeyError
    def meta(self, kind: str) -> NodeMeta         # unknown kind -> KeyError
    def known(self, kind: str) -> bool

NODE_KINDS = NodeKindRegistry()
# ngen_weave.workflow imports this module and registers Worker, Control, Human,
# Agent, and the composite handling right after defining them, through
# NODE_KINDS.register(...). No special casing anywhere: built-ins go through
# exactly the API a plugin uses (release-doc rule).
```

Edits:

- `workflow.py`: node-kind validation checks `NODE_KINDS.known(...)` instead of membership in the hardcoded subclass set; the five built-ins remain as classes for type hints. Discovery accepts any registered kind.
- `storage.py` (`definition_from_dict`): the kind-to-class choice reads `NODE_KINDS.base(kind)` instead of a hardcoded map; unknown kind raises `ConfigError` naming the kind, unchanged message style.
- `readmodel.py` (`workflow_detail`): every node dict gains `"type_meta": {"label", "icon", "color_var", "summary"} | null`, populated from `NODE_KINDS.meta(node_type)` when registered, `null` otherwise. Content hashes shift as a consequence; the hash-skip machinery tolerates that.
- Engine (`runner.py`): when emitting any provenance record for an activation, resolve the record's `source` by looking up the activating class's module in a plugin ownership map carried on the engine, constructed as `PluginRegistry.owners` filtered to node kinds and passed as an optional `Engine.__init__` keyword `plugin_sources: Mapping[str, str] | None = None` (default empty). Resolution is one prefix match on `cls.__module__` recorded at registration time; miss yields `None`.

Tests: built-ins present in `NODE_KINDS` right after importing `ngen_weave` with correct bases; duplicate registration raises; `validate_structure` accepts an invented kind once registered and rejects it before; a definition file with a plugin kind parses after registration and fails before; `workflow_detail` carries `type_meta` for a fixture kind; engine test with injected `plugin_sources` asserts `record.source` on activations of a plugin-kind class and `None` for workers.

### B2 — Service resolution and workflow packs

Services. Builtin registration: `ngen_weave.models.provider` registers `("completion_provider", "litellm")` at import, factory `lambda cfg: LiteLLMProvider(ModelRegistry.load(cfg["models_file"]))`. Resolution sites change together:

- CLI `context._build_engine` and server `create_app`: accept `registry: PluginRegistry | None`; when the project config's `services:` section names a service, resolve `registry.services[(kind, name)]` and call the factory with the config's `service_config[name]` dict; unresolved or ungranted lookups raise `ConfigError("service not available: {kind}/{name}")`. When `services:` is absent, current behavior stands (LiteLLM direct).
- `config.py`: optional top-level `services:` (map kind -> name) and `service_config:` (map name -> arbitrary dict passed verbatim to the factory). Unknown `services` kinds raise `ConfigError`.

```yaml
services:
  completion_provider: litellm
service_config:
  s3_store: {bucket: reviews}
```

Packs. `PluginContext.register_pack(name, directory)` stores packs under the key `"<plugin-meta-name>.<name>"`. Pack directories contain `*.yaml` definition files in the v0.4 format. CLI in `ngen_weave_cli/main.py`:

```
ngen-weave pack list                       # prints "<key>: <n> definitions"
ngen-weave pack install <key> [--root PATH] [--force]
    # copies each yaml into <root>/.ngen-weave/definitions/ via DefinitionStore.save;
    # existing name without --force aborts listing collisions, exit 1
```

Install goes through `DefinitionStore.save`, so validation and collision rules apply unchanged; a broken pack fails loudly per file.

Tests: litellm builtin resolvable; a fake plugin service replaces the provider in `_build_engine` and the engine uses it (asserted via a recording fake completing a run); ungranted service raises; unknown `services` kind raises; `pack list` output; `pack install` writes canonical files, refuses overwrite without `--force`, and an invalid pack fails with the validator's message.

Absorbs: new service categories (one Literal value plus one registry kind string, changed together in `plugins.py`) and Postgres-era stores (another factory).

# Branch C: Namespaced plugin API routes

PR title: `feat(server): namespaced plugin api routes under /api/plugins/<plugin-id>/`

### C1 — Route registration, mounting, and auth inheritance

New `packages/ngen-weave-server/src/ngen_weave_server/pluginroutes.py`; edits to `plugins.py`, `app.py`.

- Replace the A2 placeholder: `PluginContext.register_api_routes(prefix: str, router: APIRouter)` stores `(prefix, router)` keyed by plugin id. Prefix is a subpath segment appended to the mount; full path becomes `/api/plugins/<plugin-id>/<prefix>/...`. Import `APIRouter` from fastapi inside a TYPE_CHECKING-guarded annotation in core so core does not gain a runtime FastAPI dependency; the type is checked, never instantiated, there.
- `create_app(*, ..., registry: PluginRegistry | None = None)`: after building core routes, for each granted plugin with routes, `app.include_router(router, prefix=f"/api/plugins/{plugin_id}/{prefix}")`. One include site means server-level middleware (including the v0.8 auth middleware, whenever it lands) wraps plugin routes structurally; there is no second dispatch path to forget.
- `pluginroutes.py` holds one helper with the whole policy: `mount_plugin_routes(app, registry) -> None`, called from `create_app` alone. Collision safety comes from namespacing, asserted by test rather than enforced by code.
- Diagnostics: `GET /api/plugins` returns `[{"plugin": str, "routes": [{"path", "methods"}]}]` for granted plugins only, built from `app.routes` filtering by prefix. Read-only, no new state.

Tests (`test_pluginroutes.py`): a fake plugin registering two routes serves both at the namespaced path; two plugins may reuse the same prefix without collision; ungranted `api_routes` capability mounts nothing while `GET /api/plugins` still lists the plugin with empty routes; a plugin route raising returns the standard error envelope, proving middleware/error handling wraps plugin handlers identically to core ones.

Absorbs: any future plugin endpoint (the plugin ships a router; nothing else changes) and the v0.8 auth middleware (already wrapped at the single mount site).

Out of scope: plugin-controlled middleware or dependencies outside their own router, websocket routes, route-level auth overrides, serving static assets (F1 handles bundles separately).

Verify: `uv run pytest packages/ngen-weave-server/`.

### D1 — Spec format and enable-time validator

`packages/ngen-weave-core/src/ngen_weave/widgetspec.py` (**new**). This module defines the whole spec contract; nothing else may grow the format ad hoc.


### G1 — Notification framework

`packages/ngen-weave-core/src/ngen_weave/notify.py` (**new**) plus server startup wiring.

```python
EventKind = Literal["waiting_human", "failed", "cost_crossed", "completed"]

@dataclass(frozen=True)
class NotificationEvent:
    run_id: str
    workflow: str
    kind: EventKind
    detail: dict   # waiting_human: {"node_path"}; failed: {"error"};
                   # cost_crossed: {"cost_usd","limit"}; completed: {}

class Notifier(Protocol):
    async def deliver(self, event: NotificationEvent, target: dict) -> None  # raises InfraError on failure

@dataclass(frozen=True)
class NotifyRule:
    name: str
    kind: EventKind
    workflow: str | None = None          # exact-match filter
    cost_usd_above: float | None = None  # cost_crossed rules only
    provider: str = ""
    target: dict = {}                    # provider-specific, passed to deliver verbatim

class NotificationDispatcher:
    def __init__(self, rules: list[NotifyRule], notifiers: dict[str, Notifier],
                 store: RunStore, state_path: Path, *,
                 attempts: int = 3, backoff_ms: int = 500, interval_s: float = 2.0)
    async def run_forever(self) -> None
    def scan_once(self) -> int           # deliveries attempted this scan; unit-test seam
```

Behavior, decided here so no later step weighs it:

- Event derivation: each scan loads `store.list()`, compares each run's `(status, cost bucket, waiting node_path)` fingerprint against per-(run, rule) state in `state_path` (JSON, atomic write, same pattern as `RunStore.save`). A rule fires when the fingerprint enters its trigger state: `waiting_human` on entering that status, `failed` on entering `failed`, `completed` on entering `completed`, `cost_crossed` on summed `model_call` cost first crossing `cost_usd_above`. Each (rule, run) fires once per run lifetime; state records the firing.
- Delivery: up to `attempts` calls to `deliver`, sleeping `backoff_ms * 2**(n-1)` between failures. Every attempt appends a `notification_attempt` provenance record via `RunStore.append` with the A1 payload and per-attempt `outcome`. After final failure the rule counts as fired (no infinite retry across scans); no exception escapes `scan_once`.
- Provider resolution: `notifiers` maps names built at startup from `PluginRegistry.notifiers` filtered by the notifier capability grant; unknown `provider` in a rule raises `ConfigError` at dispatcher construction.
- Config: optional top-level `notifications:` list of rules parsed into `NotifyRule` (keys `name`, `when: {kind, workflow?, cost_usd_above?}`, `provider`, `target`); unknown keys rejected; `when.kind` must be one of the four literals.
- Server wiring: `create_app` starts `dispatcher.run_forever()` as an asyncio task on startup and cancels it on shutdown (FastAPI lifespan) when the resolved config has rules. CLI: `ngen-weave notify --once` runs a single `scan_once` and prints attempted deliveries, giving local users and tests a synchronous path.

Tests (`test_notify.py`): fake Notifier records deliveries; entering `waiting_human` fires a matching rule once, a second scan does not refire; `workflow` filter excludes mismatches; `cost_crossed` fires exactly at the crossing scan; failing notifier retried three times with three provenance records, outcome `failed` on the last, no exception escaping; state file survives a dispatcher restart without refiring; unknown provider raises at construction; config parse cases.

Absorbs: new event kinds (one more derivation branch in the fingerprint comparator) and new channels (providers register; nothing here knows SMTP from Twilio).

Out of scope: push/webhook channels, per-user subscriptions, digesting/batching, HTML formatting, delivery-order guarantees between rules.

Verify: `uv run pytest src/ngen_weave/test_notify.py packages/ngen-weave-server/`.

Commit: `feat(core,server): notification dispatcher over the run stream`

```python
class PermissionSet:

    denied_tools: tuple[str, ...] = ()       # deny wins over allow
    allowed_workflows: tuple[str, ...] = ()  # applies to workflow-launch tools only
```

Gate behavior, fully specified:

- Call accounting increments before any check; exceeding `max_calls` denies with reason `"call_ceiling"`. When `review_every_n_calls` is set and the incremented count is a multiple of it, the gate raises `ReturnToReviewError` (existing exception) after emitting `permission_denied` with reason `"checkpoint"`; the engine's existing handler interrupts at the nearest review point.
