# v0.5 implementation plan

## Context

After v0.4 (per `implementation/v0.4.md`) the distribution ships five workspace packages: core (workflow classes with data-only YAML/JSON definition serialization, `DefinitionStore`, LangGraph engine with budgets and mid-run overrides, human review, observers, content-addressed artifacts with a `VersionLog`, PROV-JSON export, agent harness behind a `PermissionGate`), cli, server (FastAPI `RunService`, read/mutation API, projects reader), mcp (workflow-as-tool over stdio and HTTP), and the sibling `ngen-weave-web` repo (list, canvas, detail, projects, run screens, review screen, editor, diff viewer). Nothing extends ngen-weave yet except by writing Python inside the registry's reach.

v0.5 makes ngen-weave extensible, period: plugins via entry points (new node kinds with UI metadata, services, workflow packs), notification providers as reference plugins, and real boxed agentic autonomy with ngen-weave itself exposed over MCP loopback. The collaboration slice (multi-reviewer, run roles, tickets) moved to v0.6, where auth gives roles principals; external document links moved to v0.7.

Files touched:

- `packages/ngen-weave-core/src/ngen_weave/`, new `plugins.py`, `nodekinds.py`, `notify.py`; extensions to `provenance.py`, `config.py`, `workflow.py`, `storage.py`, `agent.py`, `agent/gate.py`
- `packages/ngen-weave-server/src/ngen_weave_server/`, `readmodel.py`, `api.py`, `app.py`, `service.py` extensions; dispatcher startup
- `packages/ngen-weave-cli/src/ngen_weave_cli/main.py`, `pack install/list`, `notify --once`
- `packages/ngen-weave-demo-shapes/`, **new**: reference plugin exercising the whole API
- `packages/ngen-weave-plugin-email/`, `packages/ngen-weave-plugin-text/`, **new**: notification providers
- `packages/ngen-weave-mcp/src/ngen_weave_mcp/loopback.py`, **new**
- `../ngen-weave-web/`, node-kind metadata rendering (small)

Depends on: `releases/v0.5.md` (requirements), `product/PRD.md` (decision log, wins on conflict), and module shapes fixed by `implementation/v0.1.md` through `implementation/v0.4.md` (referenced, never restated). No design docs exist under `design/`; choices this plan makes get lifted there when those docs are written.

Conventions inherited from `implementation/v0.1.md` (backend) and `implementation/v0.3.md` Step 7 (web): Python ≥3.12, uv workspace, pytest, ruff, conventional commits, one commit per step unless stated, full suite green before committing, tests next to code except e2e under `tests/e2e/`, `FakeProvider`/`FakeTools` in tests, no network (live-marked exceptions only). Web repo: pnpm, Vitest, Playwright, `pnpm lint && pnpm test && pnpm build` green before committing.

Global out of scope for every step (per `releases/v0.5.md` non-goals): real-time collaborative editing, plugin marketplace/discovery infrastructure, unbounded autonomy or self-modifying workflows, interpreter-level plugin sandboxing, Postgres/auth tokens (v0.6), plugin hot-reload, Google Docs sync adapters, any claim about exploration quality beyond budgets bounding damage.

## Goals

1. Third-party plugins install via pip, register through the `ngen-weave.plugins` entry-point group, and contribute node kinds, services, notifiers, and workflow packs; capability grants are explicit in project config and enforced at resolution time.
2. Every built-in node kind registers itself through the same API plugins use, so the plugin surface is exercised by ngen-weave's own code.
3. Notification providers consume the run event stream under per-project filter rules, retry best-effort, and never disturb a run; every attempt lands in provenance.
5. An AgentNode runs a real tool loop against ngen-weave over MCP loopback while composed `PermissionSets` (tool and workflow allow/deny, budget caps, call ceilings, checkpoints, path territories) are enforced engine-side at the gate, with every blocked action recorded.

## Success criteria

From `releases/v0.5.md`, verbatim in intent:

1. A third-party demo plugin defining one new node kind installs via pip, passes validation, appears correctly in editor/canvas/detail views, and its runs carry plugin-tagged provenance.
2. An email notification fires on human-review-waiting within seconds of the event, and a failed SMTP host never disturbs the run.
3. A boxed AgentNode attempting a denied workflow launch is blocked engine-side with a recorded event, while an allowed sub-workflow launch completes and attributes cost to the parent.
4. The same MCP surface serves both the internal AgentNode and an external client driving the identical workflow.

## Abstractions and what they absorb

One sentence each; these are the load-bearing choices.

- **One entry-point group with a single `setup(PluginContext)` hook** absorbs every future plugin contribution kind: a new contribution type is a new method on `PluginContext`, and existing plugins ignore it.
- **`NodeKindRegistry` holding `(base class, NodeMeta)` pairs, with the built-ins registering themselves** absorbs new node kinds everywhere at once: validation, storage parsing, read-model serialization, and the frontend all read the one registry, so a plugin kind needs no core edits.
- **UI metadata traveling inside the workflow-detail payload (`type_meta`)** absorbs new plugin visuals without frontend releases: the web registry consults payload metadata first and keeps its own table only as fallback.
- **A service registry keyed by `(kind, name)` with factories taking their config dict** absorbs new model backends, artifact stores, and diff renderers: a plugin registers a factory, config names it, and neither the engine nor `create_app` learns the concrete class.
- **`NotificationDispatcher` as a poller over `RunStore.list()` with per-rule dedupe state** absorbs new event kinds and providers: events derive from run-file transitions in one scanner, providers implement one two-argument method.
- **Composed `PermissionSet` fields checked inside the existing `PermissionGate`** absorbs new denial reasons and territories: the gate is still the only wrapper around every agent action, and new rules are new branches in its one `call`.
- **MCP loopback as an in-memory transport client of the *same* registrar the stdio/HTTP servers use** absorbs new exposed surfaces: internal agents and external hosts see byte-identical tools because there is only one registrar.

### Step 2: Plugin loading and capability grants

`packages/ngen-weave-core/src/ngen_weave/plugins.py` (new). This module owns everything about discovering and admitting plugins; Steps 3–7 consume it.

```python
@dataclass(frozen=True)
class PluginMeta:
    name: str            # normalized distribution name, e.g. "ngen-weave-demo-shapes"
    version: str         # from importlib.metadata

class PluginContext:
    """Registration surface handed to each plugin's setup(). Grows one method per contribution kind."""
    def register_node_kind(self, kind: str, base: type[Workflow], meta: "NodeMeta") -> None
    def register_service(self, kind: Literal["completion_provider", "artifact_store", "diff_renderer"],
                         name: str, factory: Callable[[dict], Any]) -> None
    def register_notifier(self, name: str, factory: Callable[[dict], "Notifier"]) -> None
    def register_pack(self, name: str, directory: Path) -> None

@dataclass(frozen=True)
class RegisteredPlugin:
    meta: PluginMeta
    capabilities: tuple[str, ...]     # granted capability strings, empty when ungranted

class PluginRegistry:
    node_kinds: dict[str, tuple[type[Workflow], NodeMeta]]
    services: dict[tuple[str, str], Callable[[dict], Any]]     # (kind, name) -> factory
    notifiers: dict[str, Callable[[dict], Notifier]]
    packs: dict[str, Path]                                     # "<plugin>.<pack>" -> dir
    owners: dict[str, str]                                     # node kind or service name -> plugin id
    plugins: tuple[RegisteredPlugin, ...]

def load_plugins(*, group: str = "ngen-weave.plugins",
                 injected: Mapping[str, Callable[[PluginContext], None]] | None = None) -> PluginRegistry
```

Decisions, fixed here:

- Entry-point contract: group `ngen-weave.plugins`, each entry resolving to a module attribute `setup(ctx: PluginContext) -> None`. `load_plugins` iterates `importlib.metadata.entry_points(group=group)` sorted by name, builds a fresh `PluginContext` per plugin, calls `setup`, and collects `PluginMeta` from the distribution metadata. The `injected` parameter exists purely for tests (mapping plugin name to setup callable); production callers never pass it.
- Failure modes are all `ConfigError` naming the plugin: import or setup raises, a kind/service/notifier/pack name is registered twice (by anyone, including core), `register_node_kind` receives a base that is not a `Workflow` subclass.
- Capability grants: `PluginRegistry.granted(config_section: dict) -> PluginRegistry` filters the registry to plugins listed under `enabled:` and, per plugin, drops registrations whose capability kind is not in that plugin's `grants:` list. Ungranted registrations vanish silently from lookup but stay visible in `plugins` (so diagnostics can explain why something did not resolve). Config shape, parsed by `config.py` (below):

```yaml
plugins:
  enabled: [ngen-weave-demo-shapes]
  grants:
    ngen-weave-demo-shapes: ["artifact_store", "node_kinds"]
```

- `config.py`: `load_config` accepts the new optional top-level `plugins:` key with exactly the keys `enabled` (list of str) and `grants` (map str -> list of str); unknown plugin names in `enabled` raise `ConfigError("plugin not installed: {name}")` at load time; other unknown keys rejected as usual. `ResolvedConfig` gains `plugins: dict = {}`.

Tests (`test_plugins.py`): injected setup registers kinds/services/notifiers/packs; duplicate name across two plugins raises with both names; non-workflow base raises; `granted()` drops ungranted service lookups and unknown-enabled raises; a plugin raising in setup produces `ConfigError` carrying the plugin name; config parse happy path and unknown-plugin error extend `test_config.py`.

Absorbs: new contribution kinds (one `PluginContext` method) and the v0.6 packaging story (same entry points, no code change).

Out of scope: hot-reload or re-loading after start (registry is static per the release doc), dependency constraints between plugins, marketplace metadata, uninstall flows.

Verify: `uv run pytest src/ngen_weave/test_plugins.py src/ngen_weave/test_config.py`.

Commit: `feat(core): entry-point plugin loading with capability grants`

### Step 3: Node-kind registry, built-ins as reference registrations

Two modules: `packages/ngen-weave-core/src/ngen_weave/nodekinds.py` (new) and small edits to `workflow.py`, `storage.py`, `readmodel.py`, and the engine.

`nodekinds.py`:

```python
@dataclass(frozen=True)
class NodeMeta:
    label: str                  # human label, e.g. "Review"
    icon: str                   # icon name from the web icon set, plain token
    color_var: str              # theme token name, e.g. "--edge-control"
    summary: str                # plain-language template; "{field}" placeholders index input fields

class NodeKindRegistry:
    def register(self, kind: str, base: type[Workflow], meta: NodeMeta) -> None
        # kind must match [a-z][a-z0-9_]*; duplicate kind raises ConfigError
    def base(self, kind: str) -> type[Workflow]        # unknown kind -> KeyError
    def meta(self, kind: str) -> NodeMeta              # unknown kind -> KeyError
    def known(self, kind: str) -> bool

NODE_KINDS = NodeKindRegistry()
# ngen_weave.workflow imports this module and, immediately after defining
# Worker/Control/Human/Agent/composite handling, registers all five built-ins
# through NODE_KINDS.register(...) with their NodeMeta. No special casing:
# the built-ins go through exactly the API a plugin uses (release-doc rule).
```

Edits:

- `workflow.py`: `validate_structure` rule 0 becomes "`cls.node_type` must satisfy `NODE_KINDS.kinds.known(...)`" replacing membership in the hardcoded literal; the `NodeType` Literal remains for type hints of the five built-ins but no longer guards validation. The decorator accepts any registered kind.
- `storage.py` (`definition_from_dict`): the `kind`-to-class choice reads `NODE_KINDS.base(kind)` instead of a hardcoded map; unknown kind raises `ConfigError` naming the kind, unchanged message style.
- `readmodel.py` (`workflow_detail`): every node dict gains `"type_meta": {"label", "icon", "color_var", "summary"} | null`, populated from `NODE_KINDS.meta(node_type)` when registered, `null` otherwise. Content hash changes as a consequence; the hash-skip machinery already tolerates that.
- Engine (`runner.py`): when emitting any provenance record for an activation, resolve the record's `source` by looking up the activating class's module in the plugin ownership map carried on the engine (constructed as `PluginRegistry.owners` filtered to node kinds, passed as an optional `Engine.__init__` keyword `plugin_sources: Mapping[str, str] | None = None`, default empty). Resolution is one prefix match on `cls.__module__` recorded at registration time; miss yields `None`.

Tests: built-ins present in `NODE_KINDS` right after importing `ngen_weave` with correct bases; duplicate registration raises; `validate_structure` accepts an invented kind once registered and rejects it before; a definition file with a plugin kind parses after registration and fails before; `workflow_detail` carries `type_meta` for a fixture kind; engine test with an injected `plugin_sources` asserts `record.source` on activations of a plugin-kind class and `None` for workers.

Absorbs: every future node kind (registration only) and richer UI metadata later (fields join `NodeMeta`, one place feeds all consumers).

Out of scope: web rendering changes (Step 5), plugin installation of kinds end to end (Step 5), kind-specific execution behavior (plugin kinds subclass an existing base and inherit its executor), per-kind validation hooks beyond structural validation.

Verify: `uv run pytest src/ngen_weave/test_nodekinds.py src/ngen_weave/test_workflow.py src/ngen_weave/test_storage.py packages/ngen-weave-server/src/ngen_weave_server/test_readmodel.py src/ngen_weave/engine/`.

### Step 4: Service resolution and workflow packs

Three pieces: service lookup in engine/app construction, pack registration, and the pack CLI.

Services. Builtin registration: `ngen_weave.models.provider` registers `("completion_provider", "litellm")` at import, factory `lambda cfg: LiteLLMProvider(ModelRegistry.load(cfg["models_file"]))`. Resolution sites change together:

- CLI `context._build_engine` and server `create_app`: accept `plugins: PluginRegistry | None`; when the project config's `services:` section names a service, resolve `registry.services[(kind, name)]` and call the factory with the config's `service_config[name]` dict; unresolved or ungranted lookups raise `ConfigError("service not available: {kind}/{name}")`. When `services:` is absent, current behavior stands (LiteLLM direct).
- `config.py`: optional top-level key `services:` (map kind -> name) and `service_config:` (map name -> arbitrary dict passed verbatim to the factory). Unknown `services` kinds (not one of the three literals) raise `ConfigError`.

```yaml
services:
  completion_provider: litellm
service_config:
  s3_store: {bucket: reviews}
```

Packs. `PluginContext.register_pack(name, directory)` stores packs under the key `"<plugin-meta-name>.<name>"`. Pack directories contain `*.yaml` definition files in the v0.4 format. CLI in `ngen_weave_cli/main.py`:

```
ngen-weave pack list                       # prints "<key>: <n> definitions"
ngen-weave pack install <key> [--root PATH] [--force]
    # copies each yaml into <root>/.ngen-weave/definitions/ via DefinitionStore.save;
    # existing name without --force aborts listing the collisions, exit 1
```

Install goes through `DefinitionStore.save`, so validation and collision-with-registry rules apply unchanged; a broken pack fails loudly per file.

Tests: litellm builtin resolvable; a fake plugin service replaces the provider in `_build_engine` and the engine uses it (assert via a recording fake completing a run); ungranted service raises; `services:` unknown kind raises; `pack list` output; `pack install` writes canonical files, refuses overwrite without `--force`, and a definition-invalid pack fails with the validator's message.

Absorbs: new service categories (one Literal value plus one registry kind string, changed together in this module) and Postgres-era stores (another factory).

Out of scope: per-node service overrides, service health checks, uninstall/downgrade of packs (delete the file by hand; no route or command), remote pack URLs.

Verify: `uv run pytest src/ngen_weave/test_config.py packages/ngen-weave-cli/tests/ && uv run ngen-weave pack list`.

Commit: `feat(core,cli): plugin service resolution and workflow pack install`

### Step 6: Notification framework

`packages/ngen-weave-core/src/ngen_weave/notify.py` (new) plus server startup wiring. Providers plug in; the dispatch machinery is core.

```python
EventKind = Literal["waiting_human", "failed", "cost_crossed", "completed"]

@dataclass(frozen=True)
class NotificationEvent:
    run_id: str
    workflow: str
    kind: EventKind
    detail: dict        # waiting_human: {"node_path"}; failed: {"error"}; cost_crossed: {"cost_usd","limit"}; completed: {}

class Notifier(Protocol):
    async def deliver(self, event: NotificationEvent, target: dict) -> None   # raises InfraError on failure

@dataclass(frozen=True)
class NotifyRule:
    name: str
    kind: EventKind
    workflow: str | None = None          # exact-match filter
    cost_usd_above: float | None = None  # applies to cost_crossed rules only
    provider: str = ""
    target: dict = {}                    # provider-specific, passed to deliver verbatim

class NotificationDispatcher:
    def __init__(self, rules: list[NotifyRule], notifiers: dict[str, Notifier],
                 store: RunStore, state_path: Path, *,
                 attempts: int = 3, backoff_ms: int = 500, interval_s: float = 2.0)
    async def run_forever(self) -> None
    def scan_once(self) -> int           # deliveries attempted this scan; unit-test seam
```

Behavior, decided here so no later step weighs it:

- Event derivation: each scan loads `store.list()`, compares each run's `(status, cost bucket, waiting node_path)` fingerprint against per-(run, rule) state in `state_path` (JSON, atomic write, same pattern as `RunStore.save`). A rule fires when the fingerprint enters its trigger state: `waiting_human` on entering that status, `failed` on entering `failed`, `completed` on entering `completed`, `cost_crossed` on the summed `model_call` cost first crossing `cost_usd_above`. Each (rule, run, kind) fires once per run lifetime; state records the firing.
- Delivery: for each firing, up to `attempts` calls to `deliver`, sleeping `backoff_ms * 2**(n-1)` between failures. Every attempt appends a `notification_attempt` provenance record to the run file via `RunStore.append` with the Step 1 payload, `outcome` set per attempt. After final failure the rule is marked fired (no infinite retry across scans); a failed notify never raises out of `scan_once`.
- Provider resolution: `notifiers` maps names built at startup from `PluginRegistry.notifiers` filtered by the `notifications` capability grant; unknown `provider` in a rule raises `ConfigError` at dispatcher construction.
- Config: optional top-level `notifications:` key in project config, a list of rules parsed into `NotifyRule` (keys `name`, `when: {kind, workflow?, cost_usd_above?}`, `provider`, `target`); unknown keys rejected; `when.kind` must be one of the four literals.

Server wiring: `create_app` gains `enable_notifications: bool = True`; when the resolved config has rules, the app starts `dispatcher.run_forever()` as an asyncio task on startup and cancels it on shutdown (FastAPI lifespan). CLI: `ngen-weave notify --once` runs a single `scan_once` and prints attempted deliveries, giving local users and tests a synchronous path.

Tests (`test_notify.py`): a fake Notifier records deliveries; entering `waiting_human` fires a matching rule once, a second scan does not refire; `workflow` filter excludes mismatches; `cost_crossed` fires exactly at the crossing scan; failing notifier retried three times with three provenance records, outcome `failed` on the last, and no exception escapes; state file survives a dispatcher restart without refiring; unknown provider raises at construction; config parse cases.

Absorbs: new event kinds (one more derivation branch in the fingerprint comparator) and new delivery channels (providers register; nothing here knows SMTP from Twilio).

Out of scope: push/webhook channels, per-user subscription management, digesting/batching, HTML formatting, delivery-order guarantees between rules.

Verify: `uv run pytest src/ngen_weave/test_notify.py packages/ngen-weave-server/src/ngen_weave_server/test_api.py`.

Commit: `feat(core,server): notification dispatcher over the run stream`

### Step 7: Email and text provider plugins

Two new workspace packages, deliberately shaped like third-party code: they touch core only through `PluginContext.register_notifier`.

`packages/ngen-weave-plugin-email/`:

- Entry point in group `ngen-weave.plugins`; `setup` registers notifier name `email`.
- Factory takes the target dict `{"to": [str], "subject_prefix": str?}` plus environment configuration: `NGW_SMTP_HOST`, `NGW_SMTP_PORT` (default 587), `NGW_SMTP_USER`/`NGW_SMTP_PASSWORD` optional. Missing host raises `InfraError` at deliver time, not import time, so misconfiguration shows up as a recorded failed attempt.
- `deliver` sends one plain-text message summarizing the event (subject `"[ngw] {workflow}: {kind}"`, body with run id, node path or error, cost) using stdlib `smtplib`; connection and SMTP errors wrap as `InfraError`.

`packages/ngen-weave-plugin-text/`:

- Registers notifier `text`. Target `{"to": ["+1555..."]}`, env `NGW_TWILIO_SID`, `NGW_TWILIO_TOKEN`, `NGW_TWILIO_FROM`. Deliver posts to Twilio's REST messages endpoint via `httpx`; transport errors wrap as `InfraError`. Body truncated to 160 chars.

Both packages' unit tests inject a fake transport/threaded fake SMTP server; network-touching paths are `@pytest.mark.live` and excluded by default. Dev deps: `aiosmtpd` for the email fake (stdlib `smtpd` is gone in 3.12).

E2E (criterion 2) in `packages/ngen-weave-plugin-email/tests/e2e/test_notify_flow.py`: run a workflow to its human node under a dispatcher configured with the email rule pointed at the in-process fake SMTP server; assert a message arrives and the run file carries a `notification_attempt` record with `outcome: "delivered"`; repeat with the host pointing at a closed port, assert the run still completes when resumed and the last attempt records `outcome: "failed"`.

Absorbs: further channels (clone either package; core unchanged) and provider config evolution (env/target dicts are the whole surface).

Out of scope: templates beyond the fixed plain-text body, attachments, OAuth SMTP, SMS delivery reports, rate limiting.

Verify: `uv run pytest packages/ngen-weave-plugin-email packages/ngen-weave-plugin-text`.

Commits: `feat(email-plugin): smtp notifier`, `feat(text-plugin): twilio notifier`

### Step 8: PermissionSet composition and gate enforcement

`packages/ngen-weave-core/src/ngen_weave/agent.py` (dataclass growth) and `agent/gate.py` (branches). The gate remains the only wrapper around every agent action; nothing in the harness loop learns the new rules.

`PermissionSet` after this step (full shape; existing fields keep meanings):

```python
@dataclass(frozen=True)
class PermissionSet:
    allowed_tools: tuple[str, ...] = ()          # empty allows nothing (unchanged v0.1 rule)
    denied_tools: tuple[str, ...] = ()           # deny wins over allow
    allowed_workflows: tuple[str, ...] = ()      # applies to workflow-launch tools only
    denied_workflows: tuple[str, ...] = ()
    budget_usd: float | None = None              # per activation (existing)
    max_calls: int | None = None                 # per activation (existing)
    review_every_n_calls: int | None = None      # forced checkpoint cadence
    forbidden_paths: tuple[str, ...] = ()        # glob patterns over path-shaped arguments
    denied_policy: Literal["fail_node", "return_to_review"] = "fail_node"   # existing
```

Gate behavior, fully specified:

- Call accounting increments before any check; exceeding `max_calls` denies with reason `"call_ceiling"`. When `review_every_n_calls` is set and the incremented count is a multiple of it, the gate raises `ReturnToReviewError` (existing exception) after emitting `permission_denied` with reason `"checkpoint"`; the engine's existing handler interrupts at the nearest review point. The counted call does not execute.
- Denial evaluation order, first match wins: tool in `denied_tools` → reason `"denied_tool"`; tool not in `allowed_tools` → `"not_allowed"`; workflow-launch tool (name prefixed `workflow:`) whose suffix is in `denied_workflows` or not in `allowed_workflows` (when that list is non-empty) → `"denied_workflow"`; any string argument whose key is in `{"path", "root", "dir", "file"}` or whose value looks path-like (contains `/` and the key ends with `_path`) matched by `fnmatch` against `forbidden_paths` → `"path_territory"`.
- Every denial emits `permission_denied` with the Step-1-style payload extended additively: `{"tool", "node_path", "policy", "reason", "detail"?}` where `detail` carries the offending workflow name or matched pattern. Then `denied_policy` translates as today (`fail_node` → `DeniedToolError`, `return_to_review` → `ReturnToReviewError`).
- Per-activation `budget_usd` check unchanged; run-subtree caps remain the engine's run-level budget (`_check_budget`), which already sums descendant costs, so "budget caps per activation and per run subtree" decomposes into the two existing mechanisms with no new code.

Tests extend `agent/test_permissions_engine.py`: each denial reason with its payload assertion; deny-beats-allow precedence; workflow launch allowed and completing (fake tool launching a real child run via the loopback registry stub) versus denied and recorded; `review_every_n_calls=2` interrupts on the second call and resumes; path territory matches nested paths and ignores non-path arguments; combinations (ceiling hit during a checkpoint turn) resolve in the stated order.

Absorbs: new policies (a branch in the ordered evaluation list, one Literal-adjacent reason string) and stricter defaults later (constructor presets, no gate changes).

Out of scope: prompting the model about its limits (boxing is engine-side by design), semantic path analysis beyond globs, per-tool argument schemas beyond the path heuristic, concurrent-call interleaving (the harness loop is sequential).

Verify: `uv run pytest src/ngen_weave/agent/ src/ngen_weave/engine/`.

Commit: `feat(agent): composed permission sets enforced in the gate`

### Step 9: MCP loopback and boxed autonomy wiring

`packages/ngen-weave-mcp/src/ngen_weave_mcp/loopback.py` (new) plus AgentNode wiring in core.

Loopback, the criterion-5 mechanism:

```python
async def loopback_registry(service: RunService, *, poll_interval_s: float = 0.25) -> ToolRegistry
    # 1. builds the standard MCP server via register_workflow_tools over the discovered
    #    workflows and the given service, the same registrar the stdio/HTTP servers use
    # 2. connects an in-process MCP client session over the SDK's memory transport
    # 3. adapts every listed tool to a ToolSpec: name/description/schema copied verbatim,
    #    fn proxies the call through the client session and returns the parsed result dict
```

Because internal agents and external hosts consume the same registrar, the tool surface cannot drift between them; a new exposed workflow appears to both simultaneously. The blocking-dispatch semantics from v0.2 Step 8 (poll to terminal or paused) apply identically on both sides.

Core wiring:

- `AgentNode` gains `tool_source: ClassVar[Literal["none", "loopback"]] = "none"`. `"none"` preserves today's harness behavior exactly (provider-only turns). With `"loopback"`, engine construction of the node's executor builds `HarnessAgentExecutor(provider, tools=PermissionGate(loopback_registry(service), cls.permissions))`; the engine already holds a `RunService` (or constructs a `LocalRunService` over itself when embedded, as the CLI path does). The gate wraps whatever registry arrives, so boxing composes with the loopback without either knowing the other.
- Cost attribution: sub-workflow launches are ordinary runs; their `model_call` costs land in their own run files. The parent's attribution covers its own provider turns; parent-to-child rollup is recorded as a known limitation here rather than new machinery (the release doc requires the allowed sub-workflow to complete and the *parent* activation to carry its own cost, both of which hold).

E2E (`packages/ngen-weave-mcp/tests/e2e/test_loopback.py`): one workflow `outer_boxed` with an AgentNode (`tool_source="loopback"`, permissions allowing only `workflow:inner_safe`, denying `workflow:inner_secret`) launched internally; assert the denied launch attempt yields a `permission_denied` record with reason `"denied_workflow"` and policy routing, the allowed launch completes, and the parent run file shows its own `model_call` cost. Criterion 5's parity half: list tools over stdio as an external client and over the loopback inside one process; assert identical tool-name sets and identical result for invoking `inner_safe` through each.

Absorbs: future tool sources (another `ToolRegistry` handed to the same gate; `tool_source` gains a value) and remote RunService targets (the loopback takes any `RunService`).

Out of scope: parallel tool calls, cross-run parent/child cost rollup, streaming results into the agent loop, agent memory across activations, letting agents register tools.

Verify: `uv run pytest packages/ngen-weave-mcp/ src/ngen_weave/agent/`.
