# v0.2 implementation plan

## Context

v0.1 ships `ngen-weave` as a uv workspace with two packages, `ngen-weave-core` and `ngen-weave-cli`: `Workflow` subclasses validated at import, discovery through entry points plus the project manifest `ngen-weave.json` (loaded today by `ngen_weave_cli/context.py`, key `"modules"`), a LangGraph-backed `Engine` in `engine/runner.py` with `run/resume` over per-level checkpoint threads, an atomic-file `RunStore` in `engine/store.py` writing flat files at `.ngen-weave/runs/<run-id>.json`, review artifacts under `.ngen-weave/runs/<run-id>/artifacts/<node>.yaml`, provenance records with a six-field `RunMetadata` object per scope, thin YAML/JSON config, content-addressed artifacts, and two canonical examples passing e2e under root `tests/e2e/`. There is no `store.list` filtering, no budget check, no observer surface, no `AgentNode`, no server, no MCP.

v0.2 makes runs reachable and supervisable: SQLite behind the unchanged `RunStore` methods with single-file JSON demoted to an export, a `RunService` protocol with one owned FastAPI implementation, budget enforcement and author-declared observers at the activation boundary the engine already owns, workflows exposed as MCP tools, run-management CLI verbs, and `AgentNode` declared together with a real-model harness. No UI, no new node vocabulary.

Files touched:

- `packages/ngen-weave-core/src/ngen_weave/` — `engine/store.py` rewrite, new `export.py`, new `service.py`, new `observers.py`, budget checks in `engine/runner.py`, `provenance.py` Kind widening, `config.py` Budget, new `agent/` tree, manifest loader moved out of the CLI into core
- `packages/ngen-weave-cli/src/ngen_weave_cli/` — `context.py` loses its inline manifest parsing, `main.py` gains `workflows`, `runs`, `cancel`, `note`
- `packages/ngen-weave-server/` — **new** package: FastAPI `LocalRunService`, HTTP routes, `HttpRunService` client
- `packages/ngen-weave-mcp/` — **new** package: workflow-as-tool registration, stdio and HTTP transports

Depends on: `releases/v0.2.md` (requirements), `product/PRD.md` (decision log; wins on conflict), `design/constants.md` (where tunables go), and the shapes defined in `implementation/v0.1.md`. Conventions inherited from `implementation/README.md` and v0.1: Python ≥3.12, uv workspace, pytest, ruff, conventional commits, docstrings under defs with module headers capped at two lines, tests next to code except e2e, no network in tests (`FakeProvider`, extended here), full suite green before every commit.

Global out of scope for every step (v0.2 non-goals per `releases/v0.2.md`): web UI, parallel execution within a workflow, plugins or third-party node registration, artifact diffing/display, PROV-JSON export, collaboration and notifications, REST surface beyond the serving path itself, MCP loopback, any claim that the agent harness is smart.

## Goals

1. Every caller reaches runs through one `RunService` protocol with one implementation, our FastAPI service. Nothing outside the protocol imports LangGraph serving.
2. Runs append to SQLite behind the unchanged five `RunStore` methods; the single-file run JSON is an on-demand export produced by one serializer whose bytes match the v0.1 key set plus the two new defaulted keys.
3. Budgets pause runs instead of killing them; author-declared observers evaluate structured predicates at the same activation boundary and fire pause-only actions.
4. Workflows become MCP tools over stdio and HTTP, driven by the existing `ngen-weave.json`, validated loudly at startup.
5. A real model drives `AgentNode` through `CompletionProvider` while `PermissionSet` constraints are enforced engine-side, never by prompting.
6. `list_runs`, `cancel`, and notes reach users through a thin CLI that talks only to a `RunService`.
7. Remote JSON review submission resumes a paused run identically to the local YAML path, proven by one shared test.

## Success criteria

From `releases/v0.2.md`, mapped to where each is proven:

1. A workflow called through MCP from an external client completes or pauses correctly → Branch F e2e, both transports.
2. Remote JSON review resumes identically to the local file path → Branch G parity test.
3. A completed run exports faithfully: every transition, firing, and usage record present exactly once, ordered, bytes matching the v0.1 format → Branch A step A2 plus Branch G e2e.
4. A deny-listed tool attempted mid-run is blocked, recorded, and routed per policy → Branch E unit tests plus Branch G e2e replay.
5. A run exceeding its cost budget pauses; resume after raising the cap completes it → Branch C step C1 plus Branch G e2e.
6. The conformance suite passes green against the FastAPI implementation → Branch D, re-run in Branch G.

## Abstractions and what they absorb

One sentence each. These are the load-bearing choices.

- **`RunService` protocol living in core** absorbs new callers (v0.4 UI, plugins): they program against six methods, and adding or swapping backends touches only the backend's own package.
- **SQLite behind the existing `RunStore` methods** absorbs the Postgres swap at v0.6: callers never learn the backing changed.
- **One pure export writer (`dump_run_json`) over the loaded `RunFile`** absorbs format evolution and new backends: CLI, HTTP route, and any future exporter emit identical bytes because there is exactly one serializer.
- **A shared conformance suite parametrized over service factories** absorbs backend changes: run semantics are asserted once, and every implementation must satisfy the same assertions.
- **Budget and observer checks inside one engine activation-boundary hook** absorbs new cap dimensions (tokens, wall-clock) and new observer actions: both read accumulated provenance at one site, so a new dimension or predicate builder is one more entry in one module.
- **Observer predicates as structured builders that render their own descriptions** (per the PRD decision log) absorbs new comparison operators and UI display: a descriptor is mechanically generated from the evaluated object and cannot drift from it.
- **`ToolRegistry` of `ToolSpec` entries wrapped by a `PermissionGate`** absorbs new tool sources (MCP loopback at v0.5) and new denial policies: tools register themselves, the gate wraps whatever registry it is given, and a new policy is one Literal value plus one gate branch.
- **The MCP registrar taking `(workflows, service)`** absorbs new example packs (one manifest line) and a remote backend (pass a different `RunService`); transport is orthogonal.
- **Manifest loading moved into core (`ngen_weave/manifest.py`)** absorbs future manifest consumers (server multi-project routing, editor): the CLI keeps calling the same function instead of owning the parse.

### A2 — SQLite run store and run-JSON export

Branch A. Rewrite `packages/ngen-weave-core/src/ngen_weave/engine/store.py` behind its existing method set (`create/load/save/append/set_status/list`), add `packages/ngen-weave-core/src/ngen_weave/export.py`, add one CLI verb.

Why: v0.1's store rewrites the whole record stream atomically per transition, quadratic in run length. Serving keeps long-lived runs alive, so the backing moves and the interface stays.

Database file `.ngen-weave/runs.db`:

```sql
CREATE TABLE runs (
  run_id TEXT PRIMARY KEY,
  workflow TEXT, status TEXT,
  input_json TEXT, output_json TEXT, error_json TEXT,
  attempts INTEGER, submissions_json TEXT,
  started_at TEXT, notes_json TEXT NOT NULL DEFAULT '[]',
  cost_usd REAL NOT NULL DEFAULT 0, activations INTEGER NOT NULL DEFAULT 0);
CREATE TABLE records (
  run_id TEXT REFERENCES runs(run_id), seq INTEGER NOT NULL,
  ts TEXT, node_path TEXT, kind TEXT, payload_json TEXT,
  PRIMARY KEY (run_id, seq));
```

Behavior:

- `append` becomes one INSERT plus a totals update in a single transaction. `model_call` payloads add their `cost_usd` to `runs.cost_usd`; `node_activation` payloads increment `activations`. No load-modify-save anywhere on the hot path.
- `load` assembles the versioned-envelope `RunFile` from the row plus ordered records. Resume semantics unchanged.
- `list()` reads headers from `runs` without touching `records`.
- Legacy import at init: every `.ngen-weave/runs/<run-id>.json` (the actual v0.1 layout, flat files) whose id is absent inserts via `load_run_json`. Idempotent by primary key.
- `save_review_artifact` / `read_review_artifact` move with the store unchanged (they are file-based and stay file-based).

Export (`export.py`):

```python
def dump_run_json(run: RunFile) -> bytes   # the only serializer; emits the v0.1 key set plus started_at and notes
def load_run_json(data: bytes) -> RunFile  # inverse; tolerant of missing defaulted keys
```

CLI: `ngen-weave export-run <run-id> [--out PATH]` in `packages/ngen-weave-cli/src/ngen_weave_cli/main.py`; stdout when `--out` omitted.

Tests (`engine/test_store_sqlite.py`, `test_export.py`): create/append/load/list round trip against a tmp db; mid-run kill yields exactly the committed records ordered; legacy flat-file fixture imports once, second init is a no-op; dump/load round trip; exported bytes equal a recorded fixture defined as the v0.1 key set plus the two new keys (started_at, notes); pre-1.0 the format may reshape, no backwards-compat promise; export CLI smoke.

Absorbs: Postgres at v0.6 (same five methods, different driver), PROV-JSON export at v0.4 (pure function over the loaded RunFile).

Out of scope: async stores, migration tooling, deleting imported legacy files, sharing the checkpointer's database file, list filters (B2 adds those).

Verify: `uv run pytest src/ngen_weave/engine/ src/ngen_weave/test_export.py packages/ngen-weave-cli && uv run ngen-weave export-run --help`.

Commit: `feat(core): sqlite run store with run-json export`

### B2 — RunService protocol and run-summary types

Branch B. New `packages/ngen-weave-core/src/ngen_weave/service.py`. These shapes are the contract for D, F, and the CLI; later steps implement, never amend.

```python
@dataclass(frozen=True)
class RunHandle:
    run_id: str
    status: RunStatus                       # from engine/state.py

@dataclass(frozen=True)
class RunSummary:
    run_id: str
    workflow: str                           # fully-qualified class path
    status: RunStatus
    started_at: str                         # UTC ISO-8601, ts of the first record
    cost_usd: float
    waiting_on_human: bool                  # status == "waiting_human"

@dataclass(frozen=True)
class RunFilters:
    workflow: str | None = None
    status: RunStatus | None = None

class RunService(Protocol):
    async def launch(self, workflow: str, input: BaseModel) -> RunHandle
    async def resume(self, run_id: str, payload: dict | None = None) -> RunHandle
    async def status(self, run_id: str) -> RunFile
    async def cancel(self, run_id: str) -> None
    async def list_runs(self, filters: RunFilters | None = None) -> list[RunSummary]
    async def attach_note(self, run_id: str, note: str) -> None
```

Decisions fixed here so no later step weighs them:

- `launch` takes the registered workflow's fully-qualified class path as `str`, because remote callers cannot hold class objects and class paths are the only identity (PRD decision log). Implementations resolve through the same merged discovery map the CLI builds.
- `status` returns the whole `RunFile`: the record stream must be the one thing any future UI reads, so the API returns it whole. Summaries exist only for listing.
- Add `"cancelled"` to the `RunStatus` Literal in `engine/state.py` in this step.
- Add `started_at: str` and `notes: list[str]` fields to `RunFile` (defaulted; `to_dict`/`from_dict` extended). Envelope `format` stays 1; the change widens, not breaks.
- `UnknownRunError(KeyError)` defined here replaces ad-hoc unknown-run handling; `store.load` starts raising it (its message text unchanged). Both backends raise it for missing ids. Implementers must update existing `store.load` callers and tests that expect `ConfigError` (CLI `_fail`, status command tests, store tests) in the same commit.

Also in this module: `summaries(files: Iterable[RunFile]) -> list[RunSummary]`, a pure projection used by the service, the CLI listing path, and any second implementation. Listing cost is accepted: summaries projects over loaded RunFile objects and therefore reads full record streams; no header-only summary constructor ships in v0.2, and the O(records) listing is the documented default until a profiling complaint exists.

Tests (`test_service_types.py`): projection numbers (cost summed from fake `model_call` records, waiting flag), filter behavior, `UnknownRunError` raised by `store.load` for a bogus id.

Absorbs: the v0.4 UI (consumes exactly these six methods), new run states (widen the Literal once).

Out of scope: HTTP serialization (D2), what `cancel` does to a running graph (C1 wires the mechanics; until then cancel on a running run takes effect at the next await point).

Verify: `uv run pytest src/ngen_weave/test_service_types.py src/ngen_weave/engine/test_store_sqlite.py`.

Commit: `feat(core): RunService protocol, run summaries, cancelled status`

### C1 — Budget enforcement and cooperative cancel

Branch C. Edits in `packages/ngen-weave-core/src/ngen_weave/`.

`config.py`: extend `RunSettings` with `budget: Budget | None = None`:

```python
@dataclass(frozen=True)
class Budget:
    cost_usd: float | None = None
    steps: int | None = None
```

Parsed from YAML/JSON under `run.budget:`; both fields optional, at least one required when the key is present (else `ConfigError`); unknown budget keys rejected like all config keys.

`provenance.py`: widen `Kind` with `"budget_exhausted"` and `"permission_denied"` (the latter consumed by Branch E; declared now so the Literal changes once). Payload contracts, written here and nowhere else:
- `budget_exhausted`: `{"dimension": "cost_usd" | "steps", "limit": float | int, "observed": float | int}`
- `permission_denied`: `{"tool": str, "node_path": str, "policy": str}`

`engine/runner.py`: introduce one private activation-boundary hook and route both consumers through it:

```python
def _at_boundary(self, run_file: RunFile, node_path: str,
                 metadata: RunMetadata | None) -> bool:
    # returns True when the driver must stop before the next activation
    # order: cancel flag first, then budget, then observers (H2); first breach wins
```

- Called after each node activation completes and its records commit, before the next superstep is consumed. The hook receives the boundary record's `RunMetadata`; observers (step H2) plug into the same call site.
- Cancel: the Engine owns a per-run-id cancel flag set by a new `Engine.cancel(run_id) -> None` method. `_at_boundary` sees the flag, sets run status `"cancelled"`, and the driver stops consuming the stream. A running node finishes; the next boundary stops. Cancelling an already-terminal run is a no-op. Cancellation is same-process only in v0.2: `LocalRunService` reaches the engine because it runs in the same process; cancelling a run driven by another process is out of scope.
- Budget: compare `cost_usd` and activation counts against `self._settings.budget`, reading the store totals columns via the loaded run file metadata, never rescanning records. On breach: emit `budget_exhausted`, set status paused, and stop consuming the stream.
- Stop mechanism, pinned so no implementer weighs it: the driver does not raise through the graph and does not call `interrupt()`. A boundary pause is a driver-loop stop: `_drive` consumes the graph stream superstep by superstep; when `_at_boundary` returns True after a node update event commits, `_drive` breaks out of its consumption loop. The stream must be consumed with `subgraphs=True, stream_mode="updates"`, so nested activations (depth 2 and deeper) surface as boundary events; without it the driver sees only top-level supersteps and nested budget checks and observers never fire. The last checkpoint already sits at the boundary because the superstep completed cleanly. Resume then invokes the graph with None seed on the SAME checkpoint namespace (`attempt-<n>` is not incremented, no fresh namespace), which is LangGraph resume-from-latest-checkpoint path: it schedules the next node from persisted channel state. This is deliberately not the human-interrupt path: no pending task, no `Command(resume=...)`, no replay, because a cleanly completed superstep needs no replay.
- Resume-after-breach: limits live in engine settings, which the CLI already rebuilds per invocation, so raising the cap works by resuming with a freshly built Engine from updated settings. `resume()` gains a `"paused"` branch that calls `_drive` with None seed and no namespace bump. One sentence in the hook docstring; no special payload path.
- Budget breach short-circuits any observer predicate at the same boundary; one sentence noting this in `runner.py`, no priority system.

On breach the run does not fail; `RunResult` gains a `waiting: dict | None` field (default None) in this step (verify it exists in `engine/state.py`; add it if absent) and the budget pause returns `status == "paused"` with `waiting = {"node_path", "reason": "budget_exhausted"}`.

Tests (`engine/test_budget.py`): cost breach pauses mid-chain with exactly one `budget_exhausted` record; steps breach likewise; under-budget runs never emit it; fresh Engine with a raised cap resumes to completion (criterion 5 at unit level); cancel between transitions ends `"cancelled"` even while work remains; double-cancel idempotent; paused run resumed with None seed on the same namespace continues from the boundary without re-executing completed nodes, asserted by record counts rather than timestamps.

Out of scope: per-node budgets (PermissionSet keeps its own per-call cap in Branch E), live dashboards, refunding spent cost.

Verify: `uv run pytest src/ngen_weave/engine/ src/ngen_weave/test_config.py`. Also verify `engine/state.py` `RunResult` carries the new `waiting` field; a constructing test is enough.

Commits: `feat(core): widen provenance kinds for v0.2 events`, `feat(engine): budget enforcement and cooperative cancellation`

### H1 — Observer predicate module

Branch H, after C1. New `packages/ngen-weave-core/src/ngen_weave/observers.py`; small edit in `workflow.py` for the `observations` ClassVar. Per the PRD decision log: predicates are structured builders with self-rendering descriptions, actions start at pause only. No `observe()` override, no bare lambdas, no expression strings.

```python
@dataclass(frozen=True)
class ObserverPredicate:
    """Structured comparison over a scope's RunMetadata field."""
    field: Literal["iterations", "tokens_in_context", "tokens_total",
                   "cost_usd", "elapsed_ms"]     # last_output_valid excluded: bool, not comparable
    op: Literal["gt", "lt", "ge", "le", "eq"]
    value: float | int
    def evaluate(self, meta: RunMetadata) -> bool: ...
    def describe(self) -> str        # mechanically rendered, e.g. "cost_usd > 0.50"

def gt(field: str, value: float) -> ObserverPredicate: ...   # and lt/ge/le/eq module functions

@dataclass(frozen=True)
class Observer:
    predicate: ObserverPredicate
    action: Literal["pause"] = "pause"           # stop may join later; reroute stays post-1.0

# on Workflow:
observations: ClassVar[Sequence[Observer]] = ()
```

Predicates are user-declared data validated at import time by `validate_structure` (unknown field or op is a `ConfigError` naming the class); bodies need no policing because there are no bodies.

Tests (`test_observers.py`): predicate evaluation truth table per op; `describe()` output exact strings; import-time rejection of bad field/op.

Absorbs: stop and reroute actions (extend `action` Literal and the one dispatch point), richer predicates (combinators compose `ObserverPredicate`s; `and_`/`or_` arrive when a workflow needs them, the dataclass shape does not change).

Out of scope: `and_`/`or_` combinators until something declares them, stop/reroute actions, predicate serialization into config (code-bearing members stay class-path references per the PRD), observer editing in any UI, engine wiring (H2).

Verify: `uv run pytest src/ngen_weave/test_observers.py`.

Commit: `feat(core): structured observer predicates with self-rendering descriptions`

### H2 — Observer evaluation in the engine boundary

Branch H, needs H1 and C1. Small edit in `engine/runner.py`; evaluation happens at the activation boundary C1 created.

Engine wiring in `runner.py`, inside `_at_boundary`'s call site after the cancel/budget checks pass:

- One evaluation per committed `node_activation` record, against that record's `metadata` payload. The engine already produces that object for every activation of every kind (`_node_fn` emits it, composites carry their subtree aggregate), so supervision reads these records and introduces none of its own. No new evaluation sites, no second mechanism.
- An observer on a leaf class evaluates against that leaf's own activation metadata at its own boundary. An observer on a composite evaluates against the composite's subtree-aggregated metadata at its completion boundary; composite metadata is a completion artifact, so mid-scope subtree checks do not exist in v0.2 and mid-run cost control belongs to budgets (C1). Recursion is explicit: an observer applies only to the class that declares it, never implicitly to nested subgraphs; watching a child means declaring the observer on the child.
- Root observers fire at run completion in `_drive`, after the whole graph succeeded; they are structural or informational and cannot pause anything. Run-level caps belong to budgets (C1).
- On fire: emit provenance kind `"observer_firing"` with payload `{"predicate": pred.describe(), "field": ..., "op": ..., "value": ..., "observed": <evaluated number>, "action": "pause"}`, set status paused, stop consuming the stream (same driver-loop stop and None-seed same-namespace resume as C1's budget pause), and return `RunResult.status == "paused"` with `waiting = {"node_path", "reason": "observer_firing", "observer": pred.describe()}`. Multiple observers firing at one boundary emit one record each, ordered by declaration; the run pauses once.
- No special cases for humans or retries, one docstring line each: a Human activation's metadata has empty usage (cost 0, iterations 1), and a leaf's `iterations` equals its retry attempt count, so `gt(iterations, n)` on a leaf watches retries.

Widen `Kind` with `"observer_firing"` in this branch.

### D1 — LocalRunService

Branch D, needs A2 + B2. New `packages/ngen-weave-server/src/ngen_weave_server/local.py`, the reference implementation of the protocol:

```python
class LocalRunService:
    def __init__(self, engine: Engine, store: RunStore,
                 discovery_map: dict[str, type[Workflow]])
```

Per-method behavior:

- `launch`: look up the class path in `discovery_map` (`UnknownRunError` if absent), validate input against `input_type` with `format_validation_error` messaging, call `engine.run(wf, input)`, return `RunHandle`.
- `resume`: delegate to `engine.resume`; unknown id raises `UnknownRunError`.
- `status`: `store.load`.
- `cancel`: delegate to `engine.cancel(run_id)`; the engine owns the flag and the terminal write (see C1). Cancelling an already-terminal run is a no-op.
- `list_runs`: `summaries(store.list())` filtered by `RunFilters` fields.
- `attach_note`: load, append, save through the store only.

Construction mirrors the CLI's `_build_engine` wiring; share it rather than duplicating: extend `ngen_weave_cli.context._build_engine` or lift an equivalent `build_service(...)` helper into `ngen_weave_server/local.py` and let the CLI call it. Prefer the latter; the CLI keeps its thin wrapper.
