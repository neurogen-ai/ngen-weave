# v0.1.3 implementation plan

## Context

ngen-weave v0.1.x compiles `Workflow` classes into LangGraph graphs. Collected
fan-in assembles a collector's list input as `[state[src] for src in sources]`
in `g.add_edge()` declaration order (`runner.py`, `_assembly_plan` /
`_assemble_input`). That order is deterministic but contractual by accident:
nothing declares it, nothing documents it, and authors have no way to control
it. v0.1.3 adds one optional `collect_order` ClassVar to the collector and
promotes declaration order to a documented, test-pinned contract.

Files touched:

- `packages/ngen-weave-core/src/ngen_weave/workflow.py`: `collect_order`
  ClassVar, import-time path validation
- `packages/ngen-weave-core/src/ngen_weave/test_workflow.py`: validation tests
- `packages/ngen-weave-core/src/ngen_weave/engine/runner.py`: sort key in the
  assembly plan, stable sort in `_assemble_input`
- `packages/ngen-weave-core/src/ngen_weave/engine/test_engine.py`: un-xfail
  the pinned reorder test; resume-determinism test
- `plans/product/PRD.md`: declared-structure principle
- `docs/engine/execution.md`: collect form ordering contract
- `packages/*/pyproject.toml`: version 0.1.3

Depends on: `../releases/v0.1.3.md` (requirements; read first). The fan-in
rules the new check extends live in the PRD decision-log bullet "Fan-in is
explicit and compile-checked"; there is no separate design doc. The marker
fan-in fixtures this release pins are already merged (`test_engine.py`,
`_build_marker_fanin`, commit d21982f), including the `xfail(strict=True)`
reorder test this release turns green.

## Goals

1. A collector may declare `collect_order = "<dotted path>"`. Assembly
   stable-sorts collected entries by that path into each element's output
   dump; ties keep edge-declaration order.
2. Bad paths fail at import time with a ConfigError naming every parent whose
   `output_type` cannot resolve the path. Nothing fails at run time that can
   be known at import time.
3. Default behavior (declaration order) is documented in
   `docs/engine/execution.md` and pinned by existing tests, now promoted from
   incidental to contractual.
4. The PRD states the general principle; `collect_order` is one consequence,
   not the definition.

## Tests

Import-time validation cases go in `test_workflow.py` beside the other fan-in
tests (around `test_named_slot_fan_in_passes`). Runtime behavior goes in
`engine/test_engine.py` using `_build_marker_fanin` and the existing
`make_engine` helper; exact assertions are specified per step. No new test
files.

## Abstractions

One abstraction enters: the dotted schema path, resolved twice against two
representations of the same data.

- `_resolve_schema_path(model_type, path)` (workflow.py, import time) walks a
  pydantic model's fields; `_sort_value(dump, path)` (runner.py, run time)
  walks the matching dump dict. Both accept plain field names and numeric
  segments into lists. Future change absorbed: any new consumer of "point at
  a value inside an output dump by dotted string" (observer predicates in
  v0.2 predate their own need for this) reuses these instead of growing a
  third resolver. If path grammar ever widens (bracket indexing, defaults),
  both functions live one call away from each other and widen together.
- The assembly-plan tuple gains a fourth slot (`sort_key`) rather than a new
  plan kind. Future change absorbed: another ordering or filtering knob on
  collection edits `_plan_form` and `_assemble_input` only; callers of
  `_assembly_plan` never learn about it.

## Branches and decision tree

Two feature branches plus release. Branch B touches only a test file and can
start immediately in parallel with all of A; its assertion depends on runtime
behavior that already exists (declaration-order determinism), so it never
waits on A. Branch A2 needs A1 because the reorder fixture sets
`collect_order` on a generated class, which fails import-time validation
until A1 teaches the checker about the attribute.

### Step A1: `collect_order` ClassVar and import-time path validation

Branch: `feat/v0.1.3-collect-order`.

File: `packages/ngen-weave-core/src/ngen_weave/workflow.py`.

1. On `Workflow`, after `artifacts`:

```python
# Collected fan-in only: dotted path sorted on when assembling this
# node's list input. None keeps edge-declaration order. See _check_multi_parent.
collect_order: ClassVar[str | None] = None
```

2. Module-level helper, placed near `_check_collect_form`:

```python
def _resolve_schema_path(model: type[BaseModel], path: str) -> bool:
    """Whether path resolves on model's fields; segments name fields or index lists."""
    current: Any = model
    for segment in path.split("."):
        if isinstance(current, list) or get_origin(current) is list:
            elem = get_args(current)[0] if get_origin(current) is list else current[0]
            if not segment.isdigit():
                return False
            current = elem
            continue
        if not (isinstance(current, type) and issubclass(current, BaseModel)):
            return False
        field = current.model_fields.get(segment)
        if field is None:
            return False
        current = field.annotation
    return True
```

A bare-list annotation arrives as `list[X]`; a fully instantiated nested list
is out of scope until a real workflow declares one (see out-of-scope).

3. In `_check_declarations`, add one line after `_check_prompt_and_artifacts`:

```python
if not (
    getattr(cls, "collect_order", None) is None
    or isinstance(getattr(cls, "collect_order"), str)
):
    raise ConfigError(f"{path}: collect_order must be None or a dotted path string")
```

4. In `_check_multi_parent`, replace the else-branch body:

```python
else:
    _check_collect_form(path, dst, len(ordinary), child_cls.input_type)
    order = child_cls.collect_order
    if order is not None:
        offenders = [
            workflow_class_path(w.nodes[src])
            for src, _f in ordinary
            if src in w.nodes and not _resolve_schema_path(w.nodes[src].output_type, order)
            ]
        if offenders:
            raise ConfigError(
                f"{path}: collect_order {order!r} on {dst} does not resolve "
                f"against output_type of: {', '.join(offenders)}"
            )
```

The error names every offending parent class, per the release doc.

Out of scope for this step:

- Any runtime sorting (step A2).
- Rejecting `collect_order` on single-parent or non-collector nodes. It is
  inert there; inventing a second error case buys nothing.
- Path syntax beyond names and numeric list indices: no bracket forms, no
  defaults-on-missing. Import-time rejection of missing keys is the whole
  point; a default would reintroduce silent nondeterminism.
- Validating the path against the element type of the collector's own list
  field. Parents' output types are what feed entries; checking them covers it.

Tests, appended near the fan-in tests in
`packages/ngen-weave-core/src/ngen_weave/test_workflow.py`, reusing the file's
existing generated-class helpers:

- A valid three-parent collector with `collect_order = "text"` imports clean.
- Same wiring, `collect_order = "nope"` raises ConfigError whose message
  contains the composite path, the destination name, and every parent class
  path (three parents all offending).
- One parent emits a model without the field, two emit models with it: the
  message names exactly the one offender.
- A numeric segment resolves: parents emitting `list[Inner]` with
  `collect_order = "items.0.name"` where `items: list[Inner]` and `Inner`
  has `name` imports clean; `"items.x"` raises.
- `collect_order = 42` (non-string) raises via the `_check_declarations` guard.

### Step A2: Stable sort at assembly time, un-xfail the reorder test

Branch: `feat/v0.1.3-collect-order`, after A1.

File: `packages/ngen-weave-core/src/ngen_weave/engine/runner.py`.

1. In `_plan_form`'s collect branch, carry the sort key as a fourth tuple
   element. `dst_cls` is already fetched there for the field lookup:

```python
if ordinary:
    dst_cls = wiring.nodes.get(dst)
    field_name = _single_list_field(dst_cls.input_type) if dst_cls is not None else None
    order = dst_cls.collect_order if dst_cls is not None else None
    return ("collect", field_name, [s for s, _f in ordinary], order)
```

Update the `_assembly_plan` docstring's kinds list:
`("collect", field, srcs, sort_key)`.

2. Module-level helper above `_assemble_input`:

```python
def _sort_value(dump: dict, path: str, node_path: str):
    """Read a dotted path off one parent's output dump."""
    value: Any = dump
    try:
        for segment in path.split("."):
            value = value[int(segment)] if isinstance(value, list) else value[segment]
    except (KeyError, IndexError, TypeError) as exc:
        raise DataError(f"{node_path}: collect_order {path!r} missing on an entry") from exc
    return value
```

3. In `_assemble_input`, replace the collect form body:

```python
if form == "collect":
    field_name, sources, order = kind[1], kind[2], kind[3]
    missing = [src for src in sources if state.get(src) is None]
    if missing:
        raise DataError(f"{node_path}: collector parents not yet written: {missing}")
    entries = [state[src] for src in sources]
    if order is not None:
        entries.sort(key=lambda dump: _sort_value(dump, order, node_path))
    return {field_name: entries}
```

Python's sort is stable, so ties keep source order, which is edge-declaration
order. That sentence is the whole tie-breaking rule; no extra code.

Out of scope for this step:

- Sorting slots, dispatch, or single forms. They have no list to order.
- Sorting inside composites differently; the plan is per compiled graph, so
  nesting inherits the behavior with zero code.
- Sorting anything at render time. Templates render entries; they never
  decide sequence (release doc, "templates stay data").

### Step B1: Resume-determinism e2e (release scenario 5)

Branch: `feat/v0.1.3-resume-determinism`. Start any time; parallel with A.

File: `packages/ngen-weave-core/src/ngen_weave/engine/test_engine.py` only.

Append one test after `test_collected_fanin_is_deterministic_across_fresh_engines`.
Mechanism: a failed drive re-executes from the top on resume under a fresh
checkpoint namespace (`Engine.resume` docstring documents this), so killing a
run mid-way must reproduce byte-identical prompts on replay.

1. Define a provider that dies once:

```python
class _DyingProvider(FakeProvider):
    async def complete(self, messages, *, variant=None):
        if len(self.calls) == 0:
            raise InfraError("provider died mid-run")
        return await super().complete(messages, variant=variant)
```

2. Test body:

```python
async def test_kill_and_resume_reproduces_byte_identical_prompts(tmp_path):
    chain = _build_marker_fanin(
        {"prompt": "{reviews[0].text} | {reviews[1].text} | {reviews[2].text}"}
    )
    dead = _DyingProvider(replies=list(_REPLIES))
    engine = Engine(dead, RunStore(tmp_path / "killed"), checkpointer="memory",
                    max_retries=1, retry_backoff_ms=0)
    failed = await engine.run(chain, Root(text="hi"))
    assert failed.status == "failed"

    resumed_provider = FakeProvider(replies=[*_REPLIES])
    engine2 = Engine(resumed_provider, RunStore(tmp_path / "killed"),
                     checkpointer="memory")
    result = await engine2.resume(failed.run_id)
    assert result.status == "completed"

    fresh_provider = FakeProvider(replies=[*_REPLIES])
    engine3 = Engine(fresh_provider, RunStore(tmp_path / "fresh"), checkpointer="memory")
    await engine3.run(chain, Root(text="hi"))

    # The collector saw identical bytes whether the run went straight
    # through or was killed after the first level and replayed.
    assert resumed_provider.calls[3][0][0]["content"] == fresh_provider.calls[3][0][0]["content"]
```

Match the store/tmp_path conventions of neighboring tests (`make_engine`
wraps exactly this construction; reuse it where it fits and construct
manually only for the dying-provider engine). Call index 3 is the collector:
three parents then the collector, matching `_REPLIES` layout used by the
merged marker tests.

Out of scope for this step:

- Testing resume of a waiting_human interrupt; human resume determinism is
  covered by existing review-flow tests and adds nothing here (the collector
  prompt is assembled fresh either way).
- Comparing provenance records across attempts. Records legitimately differ
  (attempt namespaces); prompts must not.
- Any production-code change. If this test fails, the bug is in the engine;
  fix nothing in this branch except the test environment setup.
